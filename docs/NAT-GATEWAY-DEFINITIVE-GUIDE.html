Part I

Architecture & Design

What a NAT gateway pool actually is on Akamai Cloud, the one networking fact that shapes every other design decision in this book, and why every node carries three interfaces instead of one.

1.1 What This Is

A NAT gateway pool is a set of independently active compute instances, each holding its own public egress IP, that a whole private subnet shares for outbound internet access — the same job AWS NAT Gateway or GCP Cloud NAT do, built instead from primitives you own and operate directly: Compute Instances, a VPC, a VLAN, Cloud Firewall, and BGP-based IP Sharing.

Every node in a pool forwards real customer traffic all the time — there is no active/passive pair and no idle standby capacity waiting for a failure. Private-subnet instances run a small routing agent that spreads their outbound traffic across every currently healthy node in the pool using ordinary Linux multipath routing (ECMP). A separate control-plane service continuously health-checks the fleet, hands out the current node list to every client, and grows or shrinks the pool automatically as load changes.

A purpose-built metrics exporter gives every node full visibility into its own connection-tracking table, port allocation, throughput, and packet drops — considerably more granular than either hyperscaler's own NAT monitoring.

Why a shared, static IP pool matters

Every VPC-member instance already gets a private interface and, if it wants one, its own individual 1:1 NAT to a public address — a clean building block, but not what most real deployments need. A partner or vendor firewall allow-list, or a compliance regime that requires all egress to be auditable and traceable to a small, known set of addresses, needs a whole private subnet funneled through a small, shared, static pool of egress IPs instead of one address per instance. That single requirement — a shared, controllable, observable egress boundary — is the reason this whole system exists.

1.2 The Constraint That Shapes Everything

A VPC fabric will not transit-route a packet through a peer VPC instance out to a non-VPC destination. A private instance sitting in the same VPC as a NAT node cannot simply add a route pointing at that node's VPC address and expect its traffic to reach the internet through it — the fabric drops it.

What that looks like at the packet level

Say a private instance, Server A — VPC address 10.0.1.20, no public IP of its own — wants to reach google.com. Its default route points at a NAT node's VPC address, 10.0.1.5, hoping that node will forward the packet out to the internet the way an ordinary router would. Server A builds the packet exactly as any router setup would expect:

Why the fabric behaves this way

Akamai Cloud doesn't publish the exact internal mechanism, so this is the general, well-understood pattern this behavior matches rather than a confirmed internal detail: a cloud VPC is a software-defined overlay network, and the underlying fabric typically only programs a delivery path for traffic that stays consistent with what it already knows about each port — the address(es) actually assigned to that port, and destinations that are either inside the same VPC or leaving through that same instance's own public/NAT boundary. A packet whose destination is the public internet, but which is being handed to a different instance's interface to forward on its behalf, doesn't match that model, so the fabric has nothing to do with it — it's simply never delivered, the same class of behavior public documentation for AWS, GCP, and Azure VPCs describes as source/destination validation on hairpin or transit traffic.

What was actually verified, not just assumed Two real instances were used to test this directly, rather than trusting a general expectation: one with a public IP and NAT/forwarding configured (playing the router), one with only a VPC address and its default route pointed at the first. Packet captures ran on both instances at the same time. The sender's own capture showed every outbound packet leaving correctly; the would-be router's capture never showed any of them arriving — and its own firewall's forward-chain counters stayed at zero the entire time, meaning it wasn't even reaching a point where something local could reject it. Akamai Cloud's VPC fabric does not forward a packet through a peer VPC instance to a non-VPC destination, confirmed directly rather than assumed from documentation.

This single fact is why the private client fleet rides a completely separate Layer-2 fabric — a Linode VLAN — instead of VPC. A VLAN has no such restriction: any device attached to it can forward traffic through any other device on the same segment, exactly the behavior a NAT gateway needs from its clients. It is also why every node in the fleet carries not one but three purpose-built interfaces, each doing exactly one job, described next.

1.4 Active-Active, Pools, and Isolation

Every node in a pool is independently active — there is no master, no standby, no shared floating IP that all traffic funnels through. A pool is the unit of both scaling and isolation: the default shared pool serves every tenant that doesn't need dedicated capacity, and a tenant that does gets its own dedicated pool — its own VLAN, its own scaling bounds, fully isolated from every other tenant's traffic, but built from the exact same mechanism, not separate code.

Because every node is active all the time, one heavy tenant's traffic can burst across the entire pool rather than being capped at whatever a single pair could carry — the direct fix for the single biggest limitation of an active/passive design.

2.1 The Fleet Controller

The fleet's brain is a single service called natctl, packaged as one systemd service (natctl.service) that runs continuously and repeats the same fixed sequence of work — a pass — over and over on a timer.

What a "pass" actually is

A pass (also called a reconcile pass) is one full run through natctl's control loop, repeating every 15 seconds by default. Each pass does the same five things, always in the same order:

  1. Discover — ask the cloud provider which instances currently belong to this pool (see "Discovery" below).
  2. Health-check — probe every discovered node (see "The health check" below).
  3. Compute buddy pairings — decide which healthy nodes back each other up (preview below, full detail in Part IV).
  4. Evaluate autoscaling — decide whether the pool needs to grow or shrink (Part V).
  5. Publish the roster — recompute the JSON snapshot every client reads (Part II, 2.2).

Every one of those five steps is redone from scratch, every single pass — nothing about steps 2–5 depends on what happened in a previous pass beyond the live state that step 1 just re-discovered.

Discovery — what the tags are, who creates them, where to see them

Every node in a pool — whether it's a fixed floor node or one natctl provisioned itself — carries the same three cloud-provider tags: lng, lng-fleet, and lng-pool-<pool-name> (for example, lng-pool-shared). A node natctl provisioned itself also gets a fourth tag, lng-elastic, which is how the controller tells its own capacity apart from the fixed floor.

The infrastructure-as-code that creates floor nodes applies these tags at creation time; natctl applies the identical tags itself the moment it provisions an elastic node. Discovery, every pass, is one API call asking the cloud provider "give me every instance tagged lng-pool-shared" — a plain tag filter, not a database lookup against anything natctl owns. You can see these tags yourself the same way: in the cloud provider's own console under each instance's tag list, or from the command line with something like linode-cli linodes list --tag lng-pool-shared.

The health check — what it actually does

Every node runs a small metrics/health service of its own on port 9200. Once per pass, natctl makes one plain HTTP request — GET http://<node's private IP>:9200/healthz — with a short timeout, and that endpoint runs three real checks on the node itself before answering:

  1. Is IP forwarding actually turned on in the kernel?
  2. Is the node's own NAT firewall ruleset actually loaded?
  3. Does a real outbound HTTPS request, sent from the node's own public interface, actually succeed?

All three must pass for the node to be reported healthy — any single one failing (or the request timing out at all) reports the node unhealthy immediately. The third check is the important one: a node can be perfectly reachable on the network while its actual NAT path is quietly broken underneath, and only a real end-to-end request catches that — see Part VII, 7.5 for the full detail on why this specific design choice matters.

Buddies — a preview (full detail in Part IV)

A "buddy" is another node this one continuously mirrors live connection state with, and stands ready to take over the public IP for if it dies. Buddies exist to shrink how much traffic a single node's failure actually disrupts. Every node normally has exactly one buddy — an ordinary pair — except when the pool's healthy node count is odd, in which case one extra node is folded into a three-node group instead of being left with no partner at all (Part IV, 4.2). The sync itself runs as its own process per pairing, entirely independent of natctl — natctl only computes who's paired with whom, every pass; it never does the actual syncing itself. If a buddy relationship breaks, the affected node is still completely healthy and still fully in rotation — it's a mitigation for connection loss on a future failure, not a health signal on its own. Exactly how sync works, what protocol/port it uses, how to check it, and how to restart it if it breaks are all covered in full in Part IV, 4.3 — this paragraph is just enough to make the rest of this chapter make sense.

Provisioning and removing elastic capacity

Within the bounds an operator configures for the pool (a minimum and a maximum), natctl decides every pass whether to add or remove elastic nodes — the exact algorithm is Part V, 5.2. A few practical questions worth answering here directly:

  • What happens when a floor node goes down, and how do you recover it? natctl never deletes or replaces a floor node under any circumstance — that's a hard boundary, not a bug. Instead, it provisions extra elastic capacity to compensate for the missing floor capacity, so the pool keeps serving traffic at full strength while the broken floor node sits there unhealthy. Recovering it is a manual step: SSH in and fix whatever's wrong, or replace the instance yourself through your infrastructure-as-code (a targeted re-apply of just that one node). Once it passes its health check again, the extra elastic capacity that was compensating for it drains back down automatically on a later pass.
  • How does an operator raise the floor? Change the floor node count in your infrastructure configuration and re-apply it — see Part IX and Part X for the exact command. Every connected client picks up the new node automatically on its next roster read; no restart of anything is required anywhere.
  • Does raising the floor interact with reserved IPs? Only if reserved IPs are already turned on for the pool (Part IV, 4.6) — in that case, every new floor node created by raising the count automatically gets its own reserved address the same way every existing floor node already has one; there's no separate "grow the reserved-IP pool first" step. The only time you'd act on the reserved-IP pool directly is if you want a specific, already-owned address reused for a new node instead of a fresh one being minted — that's the "bring your own reserved IPs" list, supplied ahead of raising the floor count.

The roster — what it is, concretely

The roster is the JSON snapshot natctl computes as the very last step of every pass — nobody else generates it, and it isn't a separate service or a stored file anywhere durable. It lives entirely in memory and is rebuilt from scratch every 15 seconds; served over plain HTTP as plain JSON, no special protocol involved. The next chapter covers exactly what's in it, with a real example.

Nothing about the fleet controller is read back from a database. Every pass rebuilds the entire fleet's state from scratch, directly from live cloud-provider discovery (the tag lookup above) and each node's own health probe (the /healthz request above) — never from anything natctl itself wrote down earlier. This single design choice is what makes the control plane genuinely disposable: if it restarts, or is temporarily unavailable, it has nothing to recover — the very next pass reconstructs an accurate picture of the fleet on its own, the same way every other pass always has.

What actually stops if the control plane goes down Already-provisioned nodes keep forwarding traffic untouched — they don't ask permission to do their job. What pauses is new decisions: provisioning or removing elastic nodes, reassigning failover buddies, replacing a persistently unhealthy node, and roster freshness beyond whatever every client already cached.

2.2 The Roster URL

Every routing decision in the system — which nodes a client should send traffic through, which peer a node should mirror connection state with, which target Prometheus should scrape — ultimately traces back to one HTTP endpoint: GET /fleet/<pool>, served by the fleet controller.

What it actually is

It is a plain HTTP endpoint, not a separate service or a piece of infrastructure that gets "provisioned." The moment natctl starts and binds its listening port (8099), that endpoint exists — creating the roster URL is simply a byproduct of deploying and starting the control plane itself, nothing more.

A concrete example

Say the control plane is reachable at private address 10.60.32.5 (the control-plane host's own private IP in the single-host placement, or any one NAT node's private IP once natctl runs on every node — Part II, 2.3). The roster for the shared pool is:

How it's kept fresh

Every reconcile pass — discover instances, health-check each one, recompute buddy pairings, evaluate whether the pool should scale — ends with the controller recomputing this exact JSON document in memory and diffing it against the previous pass. Only a real change bumps roster_version and wakes anyone waiting on it; a pass with nothing new to report is a no-op from the roster's point of view. There is no separate "update the roster" step to remember — publishing the roster is simply what every reconcile pass ends in.

Long-polling: near-instant reaction, near-zero idle traffic

A plain GET /fleet/shared always returns immediately with whatever the current snapshot is — nothing about that behavior changes. Add ?wait=true&since=42 (the roster_version the client already has), and the request is handled completely differently: the server holds that one connection open — without answering yet — until either roster_version actually changes, or roughly 25 seconds pass, whichever happens first. It's still a perfectly ordinary HTTP request; the only difference is the server delays its own reply.

  • Nobody "pushes" anything. There's no separate push channel or open socket the server writes into on its own initiative — the client always makes the request first, and the server simply waits before responding instead of answering immediately. This is a long-poll, not a WebSocket or a server push.
  • Why near-zero idle traffic. With plain polling, a client sends a brand-new request every few seconds forever, whether anything changed or not. With long-polling, a client sends one request and that single connection just sits there — no new requests, no new bytes on the wire — until there's actually something worth reporting. The "traffic" that disappears is every one of those repeated, mostly-pointless requests during a quiet period.
  • How many connections can the control plane hold open at once? Honestly: this hasn't been load-tested to a specific number, and it's worth knowing that rather than trusting a made-up figure. Each held-open long-poll ties up one thread and one file descriptor on whichever host is answering it — so the real ceiling is that host's own thread/file-descriptor limits, not anything special in the roster logic itself. If you're planning for a genuinely large client count, load-test at that count before trusting it blindly, the same way you'd load-test any thread-per-connection HTTP service.
  • How does a client know which IP to connect to in the first place? There's no auto-discovery — an operator sets this explicitly, once, when a client is onboarded (Part IX): the client's routing agent is configured with the control plane's private address and port (NATCTL_ROSTER_URL=http://10.60.32.5:8099/fleet/shared), the same way you'd configure any client to point at a known server address.

Health is authoritative here, not advisory

The roster's healthy field is the control plane's own computed verdict from its /healthz check (Part II, 2.1) — not a raw "is the node reachable" ping. Every routing agent trusts that verdict by default rather than independently re-probing every node on its own. This is a deliberate, structural simplification, not a shortcut: every node and every client sit on the same physical VLAN Layer-2 segment, so reachability is essentially uniform across every client — there is no realistic scenario where a client's own probe would see something the control plane's own health check missed.

An operator who wants the old belt-and-suspenders behavior anyway can turn on an additional local probe per client — "belt and suspenders" simply means using two independent safety mechanisms at once even though either one alone would normally be enough, as extra insurance against the first one being wrong. When that opt-in probe is on, a node only counts as usable if both the control plane's verdict and the client's own direct check agree it's healthy.

How the roster URL itself stays available

This depends entirely on where the control plane runs (see the next chapter). Run on a single dedicated host, there is exactly one instance answering roster requests — a control-plane single point of failure for freshness, not for traffic already flowing. Run on every node instead, every single node answers roster reads identically and correctly regardless of which one currently holds write authority over the fleet — at that point the roster URL is effectively as available as the fleet itself, since any surviving node can answer it.

What happens if a client can't reach it

A routing agent that fails to reach the roster URL never blackholes existing traffic. It keeps serving whatever roster it last successfully fetched, and if the set of healthy nodes it's holding onto is ever completely empty, it deliberately leaves the existing route in place rather than tearing egress down entirely. The failure mode of an unreachable control plane is "traffic keeps flowing on stale information," never "traffic stops."

Running the controller on every node is possible because it is entirely stateless — everything it computes is derived fresh from live discovery and health checks each pass, never read back from storage. The one real problem this placement introduces is the one every active-active control plane has to solve: more than one instance could try to mutate cloud state at the same moment. That problem, and how it's solved, is the next chapter.

Can you switch this on an already-live fleet?

Yes, but treat it as a maintenance-window change, not a zero-impact toggle. This setting changes what's embedded in every floor node's own boot configuration, and the infrastructure tooling has no way to update that in place on a running instance — so applying the change destroys and recreates every floor node to pick up the new configuration. Reserved IPs and the deterministic address scheme (Part IV) mean every recreated node comes back with the exact same address it had before, so nothing downstream needs to be reconfigured — but every floor node does go through a real boot cycle to get there.

The "writer" node, and how a client knows who to talk to

In every-node mode, exactly one instance at a time is elected leader — the only one currently allowed to make cloud-mutating calls (create/delete a node, update a BGP IP-sharing assignment). Every other instance is a follower: it still runs the full read-only pipeline every pass — discovery, health checks, computing what it would do — but stops short of actually performing any mutating action.

From a client's point of view, there is no difference between talking to the leader or a follower at all. Every instance's roster read reflects the same underlying discovered state, since discovery and health-checking run identically everywhere — only the write path is restricted to one instance. An operator picks any one node's private address to configure into a client (Part II, 2.2) — not necessarily the current leader, since leadership can change over time and every instance answers reads identically regardless. There's no built-in load-balancing across nodes for roster reads today; every client you onboard is pointed at whichever one address you give it.

How a node checks its own health

In every-node mode, each instance health-checks every node in the pool, including itself. Checking yourself deserves a second mechanism, not just the plain network check every other node gets: a request aimed at your own private address is delivered by the kernel's own local routing table rather than the physical network interface, so a plain self-check can never observe a fault in that interface's reachability from anyone else's point of view — the one thing it would actually need to catch.

So a node's self-check that reports healthy is corroborated before it's trusted: every currently known peer is asked for its own, independently computed opinion of that same node — each peer already has one, since it health-checks every node in the pool too. A single peer vouching healthy is enough to trust the self-check immediately, biased toward keeping a genuinely healthy node in service. Only when every reachable peer unanimously disagrees, and that disagreement holds for two consecutive reconcile passes in a row, does the self-check get overridden. A peer that can't be reached to ask at all is never treated as evidence either way — a transient hiccup querying one peer can't flip a healthy node's status on its own.

A pool running with a single node has no peer to corroborate against, so it leans on a different safety net instead: the client's own independent reachability check (Part II, 2.2's fallback probe) switches on automatically whenever a pool's live node count is exactly one, unless an operator has explicitly set it otherwise. The moment a second node joins, peer corroboration takes back over.

2.4 Leader Election and Fencing

When the controller runs on every node, read-only work — discovery, health checks, buddy-pairing computation, serving the roster — runs on every instance all the time, regardless of leadership. Only the calls that actually change cloud state (provisioning a node, updating a BGP IP-sharing assignment) are gated to a single leader at a time.

The lease is a bulletin board, not the safety mechanism

Leadership is tracked via a lease record — a small JSON object naming the current leader's node id, its term number, and when it was last renewed — stored durably in Object Storage so every instance can read the same value. A leader must renew this record at least once every 45 seconds (its configured lease lifetime) or the lease is considered expired. That record is deliberately treated as a best-effort hint, never as the actual source of correctness: a lease alone cannot guarantee only one writer is active at a time under every possible network condition — nothing about writing it is an atomic compare-and-swap.

A worked example: what happens when the leader disappears

Node A is leader, term 5, renewing its lease every 15-second pass — comfortably inside the 45-second lifetime. Node A crashes.

  1. No renewal happens. Once 45 seconds pass since Node A's last renewal, Nodes B and C — both followers — each independently notice on their own next pass that the lease has expired.
  2. To avoid both racing into an election at once, each first waits a random delay of up to 10 seconds (the election jitter) before doing anything else.
  3. Say Node B's random wait happens to be shorter. It wakes first, re-reads the lease record one more time to confirm nobody else already claimed it during its wait, sees it's still expired, and begins fencing: it calls the cloud provider's power-off API against Node A, then polls — up to 60 seconds — until Node A is confirmed either genuinely offline or no longer exists.
  4. Only once that's confirmed does Node B write itself into the lease record as the new leader, term 6.
  5. When Node C wakes up a few seconds later, it re-reads the lease record first — this "always re-check before acting" behavior is deliberate — sees Node B already claimed term 6, and simply backs off, resuming as a follower without ever attempting its own fencing.

The real safety mechanism: fencing

Before a candidate ever claims leadership, it powers off the previous leader through the cloud provider's own instance power-management API and polls until that shutdown is confirmed — either a genuinely offline status, or a not-found response meaning the instance no longer exists. If the power-off call fails, or confirmation never arrives in time, the candidate aborts the election outright rather than proceeding — an unconfirmed fence provides no real guarantee, so the system fails closed instead of optimistically continuing. A fenced node is left powered off, not automatically rebooted — an operator needs to investigate and boot it back up deliberately, the same as any other unhealthy node needing attention.

Layered on top: the randomized jitter above (reducing the odds of two candidates colliding at once), a write-then-reverify step immediately after claiming leadership, and a fresh leadership check immediately before every individual mutating call — not just once per pass — so a node that loses leadership mid-cycle stops mutating within one call's window, not one whole cycle's.

What if two nodes really do try to write at the exact same moment?

Since the lease record isn't an atomic compare-and-swap, two candidates could, in a narrow and short-lived window, both briefly believe they've won the same election — the design doesn't claim to make that mathematically impossible, only rare. What actually prevents both from mutating cloud state is the separate, per-call check described above: immediately before either one attempts a real mutating action (not once per pass, but freshly for that one specific call), it re-reads the lease record one more time. Only whichever one's check runs first against the current record is allowed to proceed; the other's check will already see the new leader and refuses to act.

Honest limit, with a concrete scenario This is defense in depth, not mathematically perfect mutual exclusion the way a hardware-fenced active/passive pair would be. Concretely: imagine Node A can still reach the cloud provider's API — so it's still capable of making real mutating calls — but has lost its network path specifically to the Object Storage bucket holding the lease record, so it can't renew its lease and can't see anyone else has claimed leadership either. From Node B's side, Node A's lease simply looks expired, so Node B fences it (powers it off) and takes over — this is exactly the scenario fencing exists to handle safely, since Node A is physically powered off before Node B ever starts mutating anything. The genuinely unclosed gap is much narrower than a full node-vs-node race: it's the brief window between Node A's own last leadership re-check (which passed) and the moment the fencing power-off command actually reaches and takes effect on Node A. If Node A happened to fire a mutating call inside that exact narrow window, both could very briefly be acting on the fleet at once. That window is measured in seconds — bounded by how often a node re-verifies its own leadership, which is immediately before every mutating call, not once per pass — not minutes, but it is real and not claimed to be zero.

The trade-off fencing accepts

A fenced node is powered off, not just demoted. Once the controller runs on the NAT nodes themselves rather than an isolated dedicated host, the node being fenced is also, at that moment, forwarding real NAT traffic — so a fencing event briefly interrupts that node's own data-plane role too. Buddy IP failover (Part IV) is what limits the blast radius of that specific interruption, exactly the same way it limits any other single node's failure.

2.5 Credentials

The control plane's cloud API token needs three scopes: read/write on instances, read/write on VPC, and read/write on networking — the last one specifically because buddy IP failover calls the provider's IP-sharing API, and because fencing uses the same instance power-management endpoints already covered by the instance scope.

Secrets are resolved from a narrowly-permissioned local file or an environment variable — never written into the shared, widely-distributed configuration file itself. In the single-host placement, this token lives on exactly one tightly firewalled instance. Once the controller runs on every node, the same token exists everywhere the controller runs — a real increase in how many places a sensitive credential lives, worth weighing deliberately against the single point of failure that placement removes.

Part III

The Data Plane

The pieces that actually touch a customer's packets: the NAT node itself, and the client-side agent that decides which node to send traffic through.

3.1 NAT Nodes

A NAT node is an ordinary compute instance running a kernel-level packet filter and connection tracker (nftables), configured to masquerade — rewrite the source address of — every packet arriving on its VLAN interface out through its public interface. This is the literal thing a customer pictures when they hear "NAT gateway"; every other component in this book exists purely to deploy, scale, secure, or observe a fleet of these.

Nothing about a node's own state is durable. Its connection-tracking table, its firewall counters, and its interface statistics are all in-kernel and rebuilt fresh on every boot from configuration fetched at start time. A broken node is treated as fully disposable — destroyed and replaced by the fleet, never repaired from a backup, because there is nothing on it worth restoring.

What happens if a node stops

With no additional protection layered on, whichever connections were actively flowing through that node at the moment it died are lost — a client detects the loss and reroutes within seconds, but the in-flight TCP state itself is gone. With buddy conntrack sync and BGP IP failover both enabled (Part IV), a meaningful share of that traffic can instead continue through the node's live buddy.

3.2 The Client Routing Agent

A small, dependency-free agent runs on every private-subnet instance that needs NAT egress. It long-polls the roster URL and maintains a resilient multipath ("ECMP") route pointed at every node the control plane currently reports healthy.

Consistent hashing, not round-robin

The nexthop group it installs uses the kernel's resilient hashing mode, which is what gives the system its most important routing property: when a node leaves the healthy set, only the roughly 1/N share of flows that were hashed to that specific node get reshuffled — every other flow, on every other node, is completely undisturbed. A naive route replacement would instead reshuffle every flow on every membership change, resetting far more connections than the actual failure warranted.

Setting the hash policy itself

Getting real distribution out of that mechanism also requires the kernel to hash on enough of each packet to tell separate connections apart. The agent sets this itself at every startup — hashing on source and destination port in addition to the address pair — so that many separate connections to the very same destination spread across the whole pool instead of all landing on one node, the same five-tuple approach used by every hardware router and both hyperscalers' own NAT implementations.

The one thing it manages, and the one thing it never touches

The agent manages exactly one thing: the default route. By default, it installs one only on an instance that has no other path to the internet of its own; an instance that already has a public address or its own NAT path is left completely alone, since something else already owns that route. An operator can override this with the onboarding script's --force option (Part III, 3.3), which installs and starts the agent — and hands it the default route — regardless of what other path the instance already has, for a deliberate dual-path egress policy where NAT-fleet routing is wanted no matter what else the instance can reach. The agent never touches a VLAN or VPC interface's own connected route either way — those come from the kernel the instant the interface gets an address, independent of anything the agent does.

Fail-safe by design On a roster-fetch failure, the agent keeps its last-known-good membership rather than guessing. If the healthy set it holds ever becomes completely empty, it deliberately leaves the existing route in place rather than tearing egress down — a stale route beats no route at all.

3.3 Connecting a Client Instance

Overriding the auto-detection: --force By default, the configuration script skips installing the routing agent on an instance that already has its own path to the internet — "Public + VLAN" and "VPC (1:1 NAT) + VLAN" in the table above are left untouched. A real constraint worth knowing before relying on --force The routing agent still needs to actually reach the roster URL to do anything, and that endpoint is deliberately scoped to the fleet's own private network — not the public internet. On a "Public + VLAN" instance with no VPC interface of its own, there is no network path to a roster URL given as a private address, and the fetch (or the agent's own later polling) will simply fail. Two ways around this: give the instance a VPC interface too so it has a real path to the control plane, or fetch the agent binary via --artifact-base-url (the object-storage bucket directly, reachable from the public internet) — but the agent still can't build a working route without eventually reaching the roster itself. If it can't, its own fail-safe leaves the existing route alone rather than guessing — a safe failure, but not a working one, so plan the network path before reaching for --force, not after.

3.4 Static VLAN Addressing

A VLAN carries no address-assignment mechanism of its own — there is nothing like DHCP running on it. Every address, on every node and every client, is a static assignment applied directly to the interface.

For client instances specifically, the address is chosen by an operator (or the operator's own provisioning automation) and applied by a short configuration step run directly against the already-existing instance. Immediately before applying it, that step runs a live duplicate-address probe against the exact address on the exact VLAN segment — a last-moment collision check that catches an address already answering on the segment, whether it belongs to a node or another client, at the one moment it actually matters, rather than relying on a human to remember to check first.

A block of VLAN address space, sized by however many client addresses are expected to be hand-assigned over the deployment's lifetime, is reserved immediately above the range the fleet uses for its own nodes — this guarantees the fleet's own automatic address allocation can never wander into space meant for a manually assigned client, even though there is no per-client bookkeeping of which specific address inside that block is actually in use at any moment. The duplicate-address probe is what protects against colliding with another already-assigned client; the reserved block is what protects against colliding with a future node.

4.2 Buddy Pairing: the 2-Node Pair and the 3-Node Triangle

Every reconcile pass, the currently healthy node set is sorted deterministically and paired up two at a time. With an even number of nodes, this produces exactly what it sounds like: ordinary mutual pairs, each member backing up the other. An odd number of nodes is where the interesting behavior lives.

The ordinary pair

Two nodes, A and B. Each independently: (1) announces its own public IP as primary, (2) stands ready to take over the other's IP as secondary, and (3) mirrors connection-tracking state with the other. This relationship is fully symmetric and fully bidirectional — there is no primary/backup role assigned to either member; both are simultaneously each.

The 3-node triangle

With three or more nodes and an odd count, the trailing three nodes — call them A, B, and C in sorted order — form a triangle instead of leaving one node with no partner at all:

  • A and B form a completely ordinary mutual pair, exactly as above.
  • B — the "hub" — additionally takes on C as a one-directional backup: B is ready to announce C's public IP and mirrors C's connection state, but the reverse is not true. C does not back up B, and does not back up anyone.

Every node in the pool ends up with at least one live backup this way — nobody is left fully exposed just because the pool's node count happens to be odd.

Why the hub relationship is directional for IP failover, but not for state sync

These are two different underlying constraints, and the triangle handles them differently on purpose:

  • IP failover is governed by the cloud provider's own IP-sharing rule: two different nodes may never both claim to be the secondary announcer for the same primary address — but nothing stops a single node from being the secondary for two different primaries at once. The triangle exploits exactly that: B can legitimately back up both A's and C's addresses simultaneously, while C backs up no one. This relationship stays directional by design.
  • Connection-state sync needs a real, two-way relationship on both ends — each side runs its own sync process pointed at the other, and either side may need the other's mirrored state at any moment. So for state sync specifically, the same underlying triangle shape is symmetrized: C also gets a real, live sync relationship pointed back at B. The hub node ends up running two completely independent, simultaneous sync processes — one per peer, each with its own configuration, lock, and control socket — while the odd node out ends up with exactly one real peer instead of none at all.

What happens as the pool scales

Pairings are recomputed from the current healthy node set on every single pass — deliberately simple rather than sticky or consistent-hashed, since a buddy resync only costs a few seconds of state-sync freshness for the affected nodes, not a routing disruption for every in-flight flow the way a client-facing membership change would.

4.3 Connection-State Sync

A daemon called buddy-sync (lng-buddy-sync.service) runs on every node, watching the roster for buddy reassignment and reconciling both the BGP announcer's secondary-route configuration and the connection-tracking sync process's peer configuration whenever a pairing changes.

While active, it continuously mirrors the node's live kernel connection-tracking table to its current peer or peers — usually one, two for a triangle's hub node running two independent sync processes at once.

The protocol, concretely

The actual state-mirroring is done by conntrackd, a standard Linux connection-tracking sync daemon — UDP, over the node's private VPC interface (eth1), one independent process per peer relationship (a triangle's hub runs two at once). Each relationship's exact port is derived deterministically from a base of 3780 plus a hash of the two peers' node IDs, so both ends always agree on the same port without needing to coordinate it. Each relationship runs as its own systemd instance, conntrackd@<peer-node-id>.service — systemctl list-units 'conntrackd@*' on any node shows every currently active relationship.

Where to check buddy health

The Grafana dashboard's buddy-pairing panel (Part VII, 7.3) shows paired-node coverage across the whole fleet at a glance. On a specific node, systemctl status lng-buddy-sync shows the daemon itself, and systemctl status conntrackd@<peer-node-id> shows one specific peer relationship; journalctl -u lng-buddy-sync -f logs every roster poll and every peer change live.

What happens if it stops

A node with no active sync peer is still completely healthy and still fully participating in ECMP rotation — this is a session-continuity mitigation, not a health signal, and should never be treated as equivalent to a node being down. The only practical consequence of losing sync is that a future failure of that specific node will reset in-flight connections outright instead of possibly continuing through a buddy that had a mirrored copy of the state.

How to restart it

systemctl restart lng-buddy-sync on the affected node. It carries no state of its own worth preserving — on restart, it re-derives its current peer assignment fresh from the roster on its very next check and re-establishes sync from there (each individual conntrackd@<peer> process is started and stopped automatically by buddy-sync itself as peers come and go — there's normally no reason to touch those directly). There is nothing to migrate and no manual reconciliation step.

What it stores

Only its own regenerable configuration — the BGP announcer's running configuration is rewritten on every pairing change, and a small status file exists purely for observability and is never read back by anything. The actual mirrored connection-tracking table lives only in kernel memory on both ends and is never written to disk anywhere.

4.4 BGP-Based IP Failover

A BGP routing daemon called FRR (frr.service) runs on every node, paired with the cloud provider's own IP-Sharing capability — together, this is what actually lets a buddy take over a dead node's public IP, not just its connection state.

The mechanism

From the moment it boots, every paired node is simultaneously doing two things: announcing its own public IP as the primary route, and — once buddy-paired — announcing its buddy's/buddies' public IP(s) as a secondary backup route. This is fully bidirectional and active from boot, not something that only activates once a failure is detected.

A short activation delay is deliberately built into forming a brand-new pairing before the cloud provider's IP-sharing API is actually called — this guarantees the announcing side is genuinely up and its BGP session already established before the share takes effect, which is the mechanism that actually protects against a real outage during pairing formation rather than a bare hope that timing works out.

What happens when a node dies

Its buddy's already-standing secondary announcement is what lets traffic addressed to the dead node's public IP keep reaching a live host — typically within a single BGP convergence cycle, with proven zero packet loss in both directions during a live failover exercise. Any TCP connection that was actively open through the dead node at the moment it died still resets; that is connection-state loss, a separate concern that only connection-state sync (previous chapter) addresses.

How to restart it

systemctl restart frr on the affected node is enough — its own self-announcement resumes automatically at boot with no manual step, and its buddy assignment is entirely independent of the daemon's own lifecycle, since that assignment is recomputed by the control plane, not stored locally. Check current session state with vtysh -c "show bgp summary" on the node itself.

Operational caution Changing a node's BGP router identity while sessions are already established forces a full session reset on every peer. The router identity is set once, at boot, and is never touched again during normal operation — there is no supported reason to change it live.

4.5 Anti-Affinity Placement

Buddy sync and BGP failover both assume the two members of a pair can actually fail independently. If both happen to land on the same underlying physical host, that assumption breaks — a single physical-host failure takes out an entire buddy relationship at once, with nothing left to fail over to.

Placement groups spread a pool's nodes across separate physical hosts to close exactly this gap. This is safe to turn on for an already-running pool without replacing a single node — existing nodes are simply updated in place to join a group. A pool larger than one group's node cap is split into multiple contiguous groups; this leaves one honest, structural residual gap: a buddy pair that happens to straddle the boundary between two groups gets no anti-affinity protection from each other, since group boundaries are drawn by creation order, not by buddy-pairing awareness. This is a deliberate trade-off that minimizes rather than eliminates that specific exposure, not an oversight.

4.6 Reserved (Sticky) Public IPs

By default, a replaced node comes back with a brand-new, ephemeral public address. For a deployment whose downstream partners whitelist specific IPs, that churn is unacceptable — reserved IPs fix a node's primary public address to one that survives instance replacement.

When a node backed by elastic (automatically provisioned) capacity is removed, its reserved address is deliberately not released — it stays reserved but idle, and the next node the pool provisions reuses it instead of minting a fresh one. Over a pool's lifetime this settles into a small, stable address set bounded by the pool's maximum elastic size, not by however many replacements have happened — exactly the stability a downstream whitelist needs. A durable per-pool ownership record is what makes reuse provably safe rather than a guess based on "currently unattached," since an unattached address elsewhere on the same account could easily belong to something unrelated.

4.7 Handling a Persistently Unhealthy Node

The count that actually matters against a pool's minimum node requirement is the number of currently healthy nodes, never the raw node count — a node that exists but is failing its own health check does not count toward satisfying the floor.

An elastic node that stays unhealthy past a configured threshold is drained and replaced automatically, with no human intervention required. A Terraform-managed floor node is treated completely differently and deliberately never auto-replaced under any circumstance — instead, the system compensates by provisioning additional elastic capacity to make up for the lost floor capacity, while leaving the actual broken floor node for an operator to investigate and fix by hand. This is a hard safety boundary, not an inconsistency: an automated system should never delete infrastructure a human explicitly declared should always exist.

4.8 The Trade-Off This Design Accepts

Worth stating plainly rather than glossing over: the active-active model trades away the simplicity of a fixed master/standby pair — where one continuously mirrored relationship gives genuinely zero session loss on failover — in exchange for horizontal scaling and full utilization, with no idle standby capacity sitting around unused.

Buddy connection-state sync combined with bidirectional BGP IP failover (this Part) narrows that gap substantially — a buddy takes over both a dead node's connection state and its public identity, in both directions of every pairing. It remains, honestly, a mitigation rather than an absolute guarantee: propagation carries real if small lag, and a genuinely correlated failure of both members of a pair at once has nothing left to fail over to unless anti-affinity placement (4.5) is also in use. A workload that truly cannot tolerate any connection reset under any circumstance at all has a real reason to weigh a simpler, pair-based model's stronger session-loss guarantee against this design's better scaling and utilization — they are optimized for different priorities, and that trade-off deserves to be made deliberately rather than assumed away.

Scaling

How the pool grows and shrinks automatically, the exact formula behind every scaling decision, and how to right-size a pool from real, calculable numbers instead of guesswork.

Start the floor minimal — a single node is a perfectly reasonable starting point — and let real, observed demand justify raising it. Elastic capacity exists precisely so the floor doesn't need to be sized for a burst that may never come.

5.2 The Autoscaling Algorithm

Every reconcile pass, four independent capacity signals are checked. Any single one crossing its line is enough to trigger a scaling evaluation — a single exhausted resource degrades real traffic regardless of what the others look like.

SignalScale-out triggerMeaning
Connection-tracking utilization≥ 70%The node's fixed-size connection table is nearly full — past 100%, new connections start failing outright.
Port headroom≤ 15%Fewer than 15% of usable source ports per destination remain free. Note the direction — low is the bad reading here, the mirror image of the others.
Throughput ratio≥ 85%The node is using 85% of its real, measured network bandwidth ceiling for its specific instance plan.
CPU / softirq ratio≥ 80%The single busiest CPU core, anywhere in the pool, is spending 80%+ of its time on network packet-processing work — catches packet-rate-driven saturation neither of the other signals sees coming.

Why CPU/softirq gets its own signal

A NAT gateway is fundamentally network-I/O-bound, and the busiest-core reading is deliberately not an average across cores or nodes. Which CPU core handles a given network card's packets is generally fixed by interrupt/queue affinity, not the ordinary process scheduler — so a flood of small packets can pin one specific core near 100% while every other core, on that node and every other node in the pool, sits comfortably idle. A node in that state can look completely healthy on connection-tracking, port usage, and even total throughput in bytes per second, while its actual packet-forwarding capacity is already maxed out. Averaging across cores or nodes would wash that signal out entirely; taking the single worst core anywhere in the pool is what actually catches it. This trigger only ever adds capacity — unlike connection-tracking utilization, it has no low-watermark side and never independently drives scale-in, since a quiet core for a pass or two is a much weaker signal that it's safe to shrink the pool than a sustained drop in connection count is.

The sizing formula

Required Capacity  =  Current Capacity  ×  (Current Metric ÷ Target Metric)

The whether-to-trigger decision uses the single worst node in the pool. The how-big-an-action decision, once triggered, uses the pool-wide aggregate instead — sizing off one hot node alone would over-provision for what might really be an uneven distribution problem on a single node rather than a genuine pool-wide shortfall.

Two guards against an overcorrection

  • Sustained-breach window. A metric has to stay past its threshold across two consecutive passes before it's trusted enough to size an action on — one noisy reading only starts a counter, it never triggers an action by itself.
  • Maximum step size. Even once trusted, a single scale-out action is capped at doubling current capacity, and a single scale-in action is capped at removing half of current elastic capacity — deliberately more conservative in the remove-capacity direction, since draining a node that turns out to still be needed is a worse mistake than a slightly slow scale-out. A formula result larger than the cap is fulfilled gradually, over more than one cycle, instead of taken in a single uncontrolled jump.

A cooldown period after every scaling action, independent of both guards above, blocks re-evaluation entirely for a while — giving freshly added capacity real time to start absorbing load before the next decision is made.

A scale-out, start to finish

A pool at two nodes sees connection-tracking utilization spike to 90% on its hottest node. That single reading isn't enough on its own — the sustained-breach counter only reaches one. The load persists on the next pass; the counter is now satisfied, and the pool-wide aggregate works out to 85%. Against a 50% target, the formula computes 2 × (0.85 ÷ 0.50) = 3.4, rounded up to 4 nodes — a delta of two, which the doubling cap comfortably allows in one action. Two new nodes are provisioned in that single decision rather than two separate five-minute cycles of one node each. Cooldown then blocks any further evaluation while the new capacity boots, passes its own health checks, and starts absorbing real traffic.

Real capacity, not an assumption

The throughput signal is measured against the real, published network capacity of whichever instance plan the pool actually runs — looked up directly from the cloud provider rather than hardcoded, and cached since a plan's specification is effectively static. If that lookup itself ever fails, the fallback assumes a conservative, lower capacity figure rather than a generous one — a failure here makes the system slightly more eager to scale out, never blind to a real shortage.

5.3 Right-Sizing: Instance Types and Node Count

When in doubt, prefer more nodes over bigger ones. The active-active model makes horizontal growth genuinely cheap — there's no coordination overhead the way there would be with a fixed pair, where adding capacity meant standing up a whole new pair.

Sizing the connection-tracking table

nf_conntrack_max  ≥  1.3 × expected peak concurrent connections per node

The 30% headroom above the expected peak is what keeps a normal traffic spike from ever reaching the hard connection-tracking ceiling before the autoscaler has a chance to react.

Sizing for port exhaustion

Every public IP supports roughly 55,000 simultaneous connections to any single destination — the same structural ceiling AWS documents for its own NAT Gateway. A node can hold more than one public egress IP specifically to multiply this ceiling; only a node's primary address participates in IP failover, so additional addresses are a straightforward per-node allocation with no shared-failover behavior of their own.

Estimating the node count you actually need

Calculate two independent numbers and take the larger one as your floor:

  • Throughput-bound: peak aggregate expected traffic, divided by one node's real, published network-out capacity for the instance plan you intend to run.
  • Connection-bound: peak aggregate expected concurrent connections, divided by (per-node conntrack ceiling × 0.70) — the trigger threshold, not the raw maximum, since you want headroom before the alarm fires, not right up against it.

Add at least one extra node beyond that calculated minimum so that a single node's failure doesn't itself immediately push the pool over its own scale-out trigger.

Choosing an instance plan

Dedicated-CPU compute plans on Akamai Cloud scale up to roughly 40 Gbps inbound and 12 Gbps outbound per instance at the top end — a mid-tier dedicated-CPU plan is a reasonable, realistic default for a genuine production NAT node rather than the smallest available size, since a NAT gateway is fundamentally a networking-bound workload, not a compute-bound one. The system itself never guesses at a plan's real capacity — it queries the provider's own instance-type data directly, so whatever plan is actually chosen is what the autoscaling formula sizes against, not an assumption baked in ahead of time.

5.4 Vertical Scaling

Changing a node's instance plan — up or down — is always a deliberate, operator-initiated action naming one or more specific nodes by identifier; nothing in the system ever decides on its own that a node's size, as opposed to the pool's node count, should change.

What happens, step by step

  1. A disk-fit check runs first, before ever calling the resize API — comparing the target plan's disk allowance against the node's actual allocated disk. If it won't fit, nothing risky is attempted: the operator gets the exact manual remediation steps instead of a surprise mid-resize failure.
  2. The node is drained — excluded from the roster immediately, with existing connections given time to empty out naturally.
  3. A warm resize is attempted first (the instance stays up during migration, then reboots once complete) — automatically falling back to a cold resize if the provider rejects the warm attempt.
  4. The controller polls until the instance is confirmed running again, then un-drains it — it rejoins the roster once its own health checks pass, exactly like any node recovering from a transient failure.

Multiple named nodes are always processed one at a time, never in parallel, and the whole operation stops at the first node that fails rather than continuing to remove capacity from an already-short pool. A resized floor node needs a matching, explicit override recorded in the infrastructure-as-code configuration so a future apply doesn't silently revert the resize; an elastic node needs no such step, since it was never declared there to begin with.

5.5 Multi-Tenant Pools

A pool is the unit of both scaling and isolation. A tenant that needs guaranteed, isolated capacity — rather than sharing the default pool with everyone else — gets its own dedicated pool: its own VLAN, its own independent minimum/maximum bounds, completely isolated traffic, built from exactly the same mechanism as the shared pool, just under a different name.

6.2 Fetched-at-Boot Artifacts

A cloud provider's own boot-time configuration payload — the data handed to a fresh instance the moment it boots, sometimes called "user data" or "cloud-init" — has a hard, fixed size ceiling: 16,384 bytes, decoded. This project's own agent source code, on its own, already exceeds a meaningful fraction of that ceiling before a single optional feature is even turned on — the metrics exporter alone is around 32KB, the connection-sync daemon around 30KB, and the full control-plane package around 230KB. None of that fits inside a 16KB budget no matter how it's arranged.

What this actually is, concretely

Every file that's identical across every node — the metrics exporter, the connection-sync daemon, and the control-plane package itself — is uploaded to Object Storage exactly once per deployment, as a plain, public-read file, and re-uploaded automatically only when its actual content changes (so a redeploy that changes nothing skips the upload entirely). Instead of that content being embedded in a node's boot payload, the boot payload just contains one line telling the node where to fetch it from — something like:

curl -fsSL https://lng-artifacts.us-east-1.linodeobjects.com/lng-artifacts/exporter.py -o /opt/lng/exporter.py

Every node runs that same curl command at boot, for each of the shared files it needs, and only then starts the corresponding service. The boot payload itself shrinks from "the whole file" to "one short line," which is what actually solves the size problem.

Why public, not signed

These specific files — the exporter, the sync daemon, the control-plane package — never contain secrets. Actual secrets (API tokens, passwords) are always handled a completely different way: written directly into a small, narrowly-permissioned file on the node itself at boot, never uploaded anywhere. So making these particular files public-read isn't a security trade-off — it's what avoids a real practical problem: fetching a private file from Object Storage normally requires a signing client (credentials, a signature calculation) already installed on the machine doing the fetching. A brand-new, bare cloud image doesn't have that installed yet, and installing it just to pull the project's own non-secret source code would be extra complexity for no real security benefit — a plain public URL and a plain curl, as shown above, is the simplest thing that actually works on a fresh image.

What's compressed instead of uploaded separately

Not every file can go through this shared-upload path — some content is different for every single node and can't be uploaded once and reused. The clearest example is each node's own firewall ruleset: it embeds that node's own specific addresses, so node A's ruleset isn't node B's ruleset. Content like that has to stay directly inside that one node's own boot payload rather than being fetched from a shared file. To keep it from blowing the same 16KB budget, it's compressed (gzip) before being embedded — cloud-init already knows how to transparently decompress gzip'd boot payloads, so nothing extra needs to run on the node to unpack it. Compression alone shrinks a typical per-node configuration file dramatically (plain text compresses very well), which is normally enough to fit it comfortably inside the remaining budget after the shared files above have already been moved out.

6.3 The Leader-Election Lease

Only relevant when the control plane runs on every node: a small record naming the current leader, its term, and an expiry, readable by every controller instance. As covered in Part II, this record is a best-effort coordination hint, never the actual safety mechanism — that role belongs entirely to fencing. Losing this record costs, at most, one election cycle; it never represents a safety violation on its own.

6.4 Reserved-IP and Live Configuration Manifests

A pool's reserved-IP ownership manifest is a durable, per-pool list of every address that pool has ever reserved — the only thing that makes address reuse across node replacements provably safe rather than a guess, since an address being merely "unattached" says nothing about whether it actually belongs to this pool or to something completely unrelated sitting idle on the same account.

A separate, small live-configuration object lets an operator change certain fleet-wide operational behavior — for example, whether client instances should also independently double-check node health rather than trusting the control plane's computed view alone — instantly and durably, with every connected client and every controller instance picking up the change within one round trip and with zero restarts required anywhere in the fleet.

7.5 What the Health Check Actually Verifies

Every node's own health endpoint runs a genuine end-to-end check every single time it's called, not a cached result: IP forwarding is confirmed enabled, the NAT ruleset is confirmed loaded — and, the check that actually matters most, a real outbound request is sent out through the node's own public interface and its success is confirmed.

That last check is what makes both client routing decisions and the fleet's roster genuinely trustworthy. A node can be perfectly reachable on the network while its NAT path is quietly broken underneath — a plain reachability check would completely miss that; only an actual end-to-end request catches it. The per-check breakdown metric exposes exactly which individual check failed, so a diagnosis never requires logging into the node itself.

Part VIII

Security

The firewall boundary on every interface, and exactly what credential scope every moving part actually needs.

8.1 The Firewall Model

Every node's public and VPC interfaces sit behind a default-deny cloud firewall — inbound_policy = DROP as the catch-all, with only the specific ports below explicitly allowed. Nodes never accept an inbound connection initiated from the internet at all; NAT and forwarding are unidirectional by construction, not merely by firewall policy. Outbound traffic is unrestricted from every node (outbound_policy = ACCEPT) — nothing here limits what a node itself can reach.

The VLAN interface is handled completely differently, because the cloud provider's own firewall layer never inspects VLAN traffic at all — it simply isn't in that path. The node's own local packet-filter ruleset (nftables, not the cloud firewall) is the entire security boundary for VLAN traffic instead, and it's written accordingly: it keeps the metrics port open there (client instances need to reach it) while explicitly excluding administrative access from that interface.

Every rule, exactly as created

Three separate firewalls are created — one per role. Every rule below is scoped to the narrowest source it can be; the two CIDR groups referenced are admin_cidrs (an operator-supplied list — your office/VPN egress address, never left open to the whole internet) and "VPC-internal" (every subnet in the VPC this deployment uses, public and private alike).

How to change these rules

These firewalls are ordinary Terraform resources in your own copy of the infrastructure code, not a managed setting hidden behind a control panel — you're expected to read, audit, and modify them like any other part of your own infrastructure.

  • Narrowing or widening who counts as an admin is the one change most operators will ever need, and it needs no code edit at all: set admin_cidrs in your Terraform variables to whatever office/VPN/bastion address range should have SSH and dashboard access, and re-apply.
  • Opening an additional port (say, a custom monitoring agent you run yourself): add another inbound { ... } block to the relevant linode_firewall resource in terraform/modules/vpc/main.tf, following the exact same shape as the rules above — a label, a protocol, a port, and an explicit ipv4 source list. Never widen a rule's source to 0.0.0.0/0 unless you specifically intend to expose that port to the entire internet.
  • Attaching a completely separate firewall to just one instance (rather than editing the shared one every node uses) is also fully supported — Terraform's linode_firewall_device resource attaches any firewall to any instance independently; nothing about this project's own firewalls prevents an additional one from also being attached.

Whatever you change, re-run terraform plan first and read it — a firewall rule is exactly the kind of change worth reviewing before it goes live.

8.2 Credential Scope

The control plane's own cloud API token needs exactly three scopes — read/write on instances, read/write on VPC, and read/write on networking — and nothing broader. The networking scope specifically is what allows both BGP IP-sharing calls and the fencing mechanism's instance power-management calls; no additional scope beyond it is required for fencing.

The client routing agent needs one elevated local capability on the instance it runs on — the ability to manage the kernel's own routing table — and nothing else; it never needs any cloud API credential of its own at all.

Part IX

Deployment

What's required before the first deploy, the deployment sequence itself, and how a real customer instance gets connected once the fleet exists.

9.1 Prerequisites

  • A cloud account with API access, and a token scoped exactly as described in the Security part above.
  • An existing VPC and at least one subnet, sized with headroom for every pool's own address range — this project intentionally never creates the VPC itself, only reads it back.
  • An object storage bucket, created ahead of time — required for every deployment, since fetched-at-boot artifacts (Part VI) depend on it unconditionally, not only in the every-node control-plane placement.
  • An SSH key pair for administrative access, and an explicit administrator address range for the control-plane host's dashboard and SSH access.

9.2 Deployment Sequence

  1. Provision the fleet: the floor nodes for each pool, the control-plane host (or, if the every-node placement is chosen, nothing dedicated at all), and the two firewalls covering the node and control-plane traffic.
  2. Confirm the fleet is healthy: every floor node passes its own health check and appears in the roster with a healthy status.
  3. Install the routing agent on every private-subnet instance that needs egress, pointed at the pool's roster URL.
  4. Open the monitoring dashboard and confirm every node is reporting metrics and showing healthy.

9.3 Onboarding a Client Instance

Once a private instance exists and has its VLAN interface attached at the account level, a single configuration step against that instance finishes the job: it applies the operator-supplied static VLAN address (after the duplicate-address safety probe described in Part III), installs and starts the routing agent only if the instance genuinely needs one, and points it at the correct pool's roster URL. The instance is now a fully participating client, spreading its egress traffic across every currently healthy node in that pool.

Part X

Day-2 Operations

The checklist worth reviewing before calling a deployment production-ready, the procedures for the operational tasks that come up routinely, and where to look first when something looks wrong.

10.1 Pre-Production Checklist

  • Metrics are being scraped from every node, the dashboard is loaded, and alert rules are active.
  • The control plane is running with a valid, correctly scoped API token.
  • Every private-subnet instance that needs egress has a healthy routing agent installed.
  • Minimum/maximum node bounds are reviewed per pool — these are the real safety limits on automatic scaling, not defaults to leave unexamined.
  • The connection-tracking table size is sized against expected peak concurrent connections per node.
  • Firewall rules are reviewed: default-deny confirmed, only documented ports open — remembering the cloud firewall never covers VLAN traffic, only the node's own local ruleset does.
  • If buddy sync is wanted, the roster URL configuration matches consistently everywhere it's referenced; if it isn't wanted, it's left empty everywhere so the sync daemon is never installed at all.
  • The unhealthy-node replacement threshold is reviewed per pool — the default is a reasonable starting point, not something to leave unexamined for a workload sensitive to brief capacity dips.
  • If BGP IP failover is enabled, the correct BGP data-center identifier is confirmed for the region, and automatic IP-share configuration is left on unless there's a specific reason to run the first pairing by hand.
  • Every manually assigned client address falls inside its pool's reserved window and was applied through the configuration script's duplicate-address safety check, never picked and applied blind.
  • Anti-affinity placement is considered for any pool where a correlated physical-host failure taking out a whole buddy pair is a real, meaningful concern.
  • If reserved IPs are in use and addresses already exist from a prior deployment, they're handed to the pool explicitly rather than letting it mint entirely new ones.

10.2 Common Procedures

Every procedure below assumes nothing beyond a working deployment — each command is the exact, complete step, not a paraphrase of one.

Raise the floor

  1. From the Terraform environment directory: 
    terraform apply -var 'shared_pool_floor_nodes=<new-count>'
  2. Confirm the new node(s) reach a running state and pass their own health check (Part VII).

Every connected client picks up the new node automatically on its next roster refresh — no other action is needed anywhere.

Adjust elastic bounds (min_nodes / max_nodes)

  1. From the Terraform environment directory: 
    terraform apply -var 'shared_pool_max_nodes=<new-value>'
    (or shared_pool_floor_nodes for the pool's minimum — the same variable "Raise the floor" above uses).

This writes the new value to a small, dedicated object the control plane rereads every reconcile pass — the very next pass, roughly 15 seconds later, is already sizing against it. No restart, and — unlike changing the floor node count's own boot-time settings below — no existing node of any kind is touched: the apply is a plain, in-place update to that one object, nothing else.

Adjust other autoscaling tuning (watermarks, sustained-breach window, step caps, cooldown)

  1. Edit the relevant autoscale: setting (Part V, 5.2) in the control plane's own configuration file (natctl.yaml).
  2. Restart the service so it re-reads the file: 
    systemctl restart natctl

These settings are genuinely boot-time configuration, unlike a pool's min_nodes/max_nodes above — a restart is required for a change to take effect.

Manually drain and remove an elastic node

python -m natctl.natctl_cli drain --config natctl.yaml --pool shared --node-id shared-elastic-103

The named node is immediately excluded from the roster and deleted once its live connection count empties out, or once a configured drain timeout elapses, whichever comes first. A floor node can never be drained this way by design — the command refuses; reduce the floor's declared count instead (above).

Resize a node's instance plan

python -m natctl.natctl_cli resize --config natctl.yaml --pool shared \
  --node-id shared-3 --instance-type g6-dedicated-8

--node-id can be repeated for more than one node — see the full mechanics (drain, warm/cold resize, rejoin) in Part V, 5.4. Nodes are always processed one at a time, and the operation stops at the very first failure rather than continuing against a pool that's already short a node.

Add an extra egress IP to a running node

  1. Raise egress_ips_per_node in Terraform and apply — this allocates the address but does not yet wire it into the node's live NAT rules.
  2. SSH into the specific node and run: 
    /path/to/scripts/add-egress-ip.sh --ip <new-ip> --bucket-index 1 --bucket-count 2
  3. Confirm with nft list table inet lng_nat on that node.

This currently only works for floor nodes — elastic nodes are provisioned single-IP.

Enable BGP IP failover for a pool

This is the one procedure in day-2 operations that carries real reachability risk if rushed.

  1. Confirm buddy sync (Part IV, 4.3) is already active for the pool.
  2. Look up the correct BGP data-center identifier for your region and set it, along with ip_failover_enabled = true, in Terraform for the pool.
  3. terraform apply. This installs and starts FRR on every node in the pool with self-announcement already active — it does not yet call the cloud provider's IP-sharing API.
  4. Watch buddy-sync take over from here automatically (its default activation delay lets the announcing side come up first): journalctl -u lng-buddy-sync -f on a paired node should show its buddy assignment, then shortly after, journalctl -u natctl should log that it called the IP-sharing API.
  5. Confirm sessions actually establish: vtysh -c "show bgp summary" on a paired node — peers should show Established, not stuck on Active.
  6. Test a real failover from an external host before trusting it in production: ping a node's public IP continuously, then systemctl stop frr on that node and confirm the ping keeps answering (now via its buddy). systemctl start frr to fail back.

Enable the every-node control-plane placement

  1. Confirm the API token already has the scopes in Part II, 2.5 — no new scope is needed for this specifically.
  2. Set natctl_on_node_enabled = true in Terraform and apply. This recreates every floor node (Part II, 2.3) and turns natctl off on the dedicated observability host.
  3. Confirm exactly one leader: journalctl -u natctl -f on any node should show exactly one node logging that it's now the leader, and every other node logging that it's a follower.
  4. Confirm every node still answers reads regardless of leadership: curl http://<any node's private IP>:8099/status.

10.3 Troubleshooting Playbook

Each entry assumes you're starting from zero context on this specific alert — what it means, and the exact steps to actually resolve it.

A port-exhaustion alert fires

  1. Open the dashboard's port-headroom panel (Part VII, 7.3) to identify the specific node and public IP that's actually saturated.
  2. If the whole pool is under pressure (every node's headroom is low, not just one): the autoscaler should already be scaling out on its own. Check journalctl -u natctl for whether it's blocked — either still inside its cooldown window after a recent scaling action, or already at the pool's configured maximum node count (Part V, 5.2). If it's at maximum and still under pressure, raise max_nodes for the pool (see "Adjust elastic bounds" above).
  3. If only one node is hot while others have headroom: this is expected at low connection counts — ECMP hashing isn't perfectly even across a small number of flows, and it self-corrects as volume grows. If it persists under real sustained load, give that specific node an extra egress IP ("Add an extra egress IP" above) to multiply its own port ceiling.

A pool-below-floor alert fires

  1. Run python -m natctl.natctl_cli nodes --config natctl.yaml --pool shared — this shows every node and whether it's actually healthy, not just present. The floor check is against healthy count specifically, so a node that exists but is failing its health check doesn't count.
  2. If an elastic node is missing or unhealthy: it should self-heal automatically once it's been unhealthy past the configured threshold (default 90 seconds) — watch for a log line like "elastic node ... has failed health checks for >=Ns — draining for replacement" in journalctl -u natctl. If that line never appears, check the API token's scope and any provisioning errors in the same log (a bad instance type, a region quota, etc.).
  3. If a floor node is unhealthy: this is never auto-replaced by design — the pool instead runs with extra elastic capacity compensating for it, which is expected, not an error. Fix the actual floor node yourself: SSH in and investigate (check systemctl status nat-exporter and journalctl -u nat-exporter first, since that's what the health check itself depends on), or replace the instance through a targeted re-apply of just that node.
  4. If a floor node is simply missing entirely (not present at all, not just unhealthy): that's infrastructure drift, not something natctl can or should fix — run terraform plan and reconcile it the normal way.

A node has no sync buddy

  1. Confirm buddy sync is actually turned on for the pool and its roster-URL configuration matches everywhere it's referenced (Part IV, 4.3).
  2. On the node itself: systemctl status lng-buddy-sync should show it active, and journalctl -u lng-buddy-sync -f should show it polling the roster. If the service isn't running at all, systemctl restart lng-buddy-sync and watch the log for it picking up a peer assignment.
  3. Remember this is a mitigation, not a health signal — an unpaired node is still fully healthy and fully in ECMP rotation. Don't page on this alone; it only means a future failure of that node won't have a warm buddy to fail over to yet.

A client isn't picking up a fleet change

  1. Confirm the client can reach the roster URL at all: curl http://<control-plane private IP>:8099/fleet/<pool> from the client instance itself. If this fails outright, it's a network/firewall problem, not a routing-agent problem.
  2. On the client: systemctl status lng-client-agent and journalctl -u lng-client-agent -f — it logs every roster refresh and every change to its healthy-node set live.
  3. Remember a node present in the roster but reporting unhealthy is excluded from routing regardless of how fresh the roster itself is — check the node's own health first (Part II, 2.1) before assuming the client is the problem.

Rolling a security patch across the fleet

  1. Elastic nodes: drain-and-replace is simplest — drain each one ("Manually drain and remove an elastic node" above) and let the pool provision fresh, already-patched replacement capacity as it naturally scales.
  2. Floor nodes: patch one at a time, since there's no automatic drain for these. For each node: drain it manually (there's no built-in command for this on a floor node — coordinate it yourself, e.g. a temporary firewall rule, or SSH in and stop nat-exporter so its health check starts failing, which the routing agents pick up within seconds), patch and reboot it, confirm curl http://<node>:9200/healthz reports healthy again, then move to the next node.

10.4 Where to Look First

In rough order of likelihood: a private-subnet instance's routing agent isn't running or can't reach the roster URL; the control plane's API token has expired or lost a scope; or the minimum/maximum bounds are misconfigured for actual current load. The architecture and this book describe exactly how the system is supposed to behave — when real behavior diverges from that, that gap is always the right starting point for debugging, not a sign the design itself is wrong.
