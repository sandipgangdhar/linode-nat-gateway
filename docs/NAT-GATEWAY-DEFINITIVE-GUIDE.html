0.1 What a NAT Gateway Actually Is, and Why You Need One

A machine with a private-only address cannot talk to the internet on its own — no router anywhere in the world knows how to send a reply back to 192.168.100.42, because millions of networks use that exact address internally. Network Address Translation (NAT) is the mechanism that fixes this: a device sitting between the private machine and the internet swaps the private source address for a real, internet-routable one on the way out, remembers the swap, and reverses it when the reply comes back. A NAT gateway is that device, built as a service a whole private network shares.

What NAT does, one packet at a time

Say a private instance at 192.168.100.42 opens an HTTPS connection to a public web server at 142.250.72.14. It picks an unused local port — say 51234 — and sends the first packet toward its default route, which points at the NAT gateway. The gateway holds a real public address, 172.236.173.125. Here is what the packet looks like before and after it passes through:

Source port5123451234 — or a different free port if another private client is already using this one toward the same destination
Destination IP142.250.72.14142.250.72.14 — unchanged
Destination port443443 — unchanged

From the web server's point of view, the connection came from 172.236.173.125:51234 — it never sees the private address at all, and its reply is addressed to the gateway's public IP. The gateway is the only party that knows this reply belongs to 192.168.100.42:51234, because it wrote that fact down when the first packet went out. It rewrites the destination back to the private address and forwards the reply inward, and the private instance receives a perfectly ordinary response to the connection it opened. That per-connection memory — the table of "this outbound connection was translated to this public address and port" — is the entire heart of NAT, and Part 0.2 (i) below describes the actual Linux kernel structure that holds it.

Three properties follow directly from this design and matter for everything else in the book. First, NAT is outbound-initiated: a private instance can open connections to the internet, but nothing on the internet can open a connection to the private instance, because there is no table entry to reverse until the private side sends first. Second, a translation is per-connection state that lives on one specific gateway — if that gateway disappears, every open connection whose table entry it held is lost, even if a second gateway is standing right next to it. Third, every public IP has a finite number of source ports (a 16-bit field, so at most 65,535, fewer in practice), which caps how many simultaneous connections one public address can carry toward any single destination. Parts IV and V exist largely to address the second and third properties.

Why cloud workloads are kept on private addresses in the first place

If every instance could simply be given its own public IP, none of this would be necessary. Deliberately withholding one is a design choice most production environments make, for reasons that reinforce each other:

  • Security posture. An instance with no public address is unreachable from the internet by construction — not because a firewall rule blocks inbound traffic, but because there is no route to it at all. A misconfigured firewall, a service accidentally bound to 0.0.0.0, or a vulnerable daemon nobody remembered was running are all non-events on a machine the internet cannot address.
  • Blast radius. A fleet of a hundred instances with a hundred public IPs is a hundred separately exposed surfaces to inventory, patch, and monitor. The same fleet behind a NAT gateway has exactly one class of internet-facing surface — the gateway — and that surface is small, purpose-built, and can be hardened once.
  • A small, known egress footprint. When every outbound connection from the fleet leaves through a handful of static public addresses, those addresses become something a partner or vendor can allow-list on their own firewall, something a compliance auditor can point at as "all egress from this environment comes from here," and something a security team can watch as a single chokepoint. One IP per instance gives you none of these — a partner will not allow-list a hundred addresses that change every time an instance is replaced.
  • Address scarcity. Public IPv4 addresses are a finite, billed resource. Private ranges are free and effectively unlimited.

The NAT gateway as a product category

Once a private subnet needs internet egress without public IPs of its own, something has to perform the translation described above for the whole subnet — with enough capacity to handle every instance's connections at once, enough redundancy that a single failure does not cut the entire fleet off, and enough visibility that port exhaustion or a saturated link is noticed before it becomes an outage. That "something" is what every major cloud provider now offers as a managed product, and what this book describes building and operating yourself. The two products the rest of this book uses as reference points are AWS NAT Gateway and GCP Cloud NAT, both described here factually so later comparisons have context.

AWS NAT Gateway is a fully managed, per-availability-zone service: you create one gateway in a public subnet, attach one or more Elastic IPs to it, and point a private subnet's route table at it. AWS documents a 5 Gbps baseline that scales automatically up to 100 Gbps, a ceiling of 55,000 simultaneous connections per attached IP toward any single unique destination (raised by attaching more IPs, up to a quota-adjustable maximum of 8, for 440,000 to one destination), and up to 10 million packets per second. Its internals are opaque and redundant within the zone; cross-zone resilience means deploying one gateway per zone yourself. Monitoring is a set of roughly eight CloudWatch metrics — bytes and packets in and out, dropped packets, port-allocation errors, idle timeouts, and connection counts — and port exhaustion surfaces as silent connection failures unless you are specifically alarming on the ErrorPortAllocation metric. Pricing is a per-gateway-hour charge plus a per-gigabyte charge on every byte processed.

GCP Cloud NAT takes a different architectural approach: it is a distributed, software-defined service with no proxy instances or gateway appliances in the traffic path at all, configured regionally rather than per zone. Ports are handed to each VM through Dynamic Port Allocation — a minimum and maximum per VM, grown in power-of-two increments with a cooldown between changes — against an effective ceiling of roughly 64,512 usable ports per NAT IP. Bandwidth scales with the number of VMs behind it, with no fixed published cap. It integrates with Cloud Monitoring and offers optional NAT logging that records individual connection opens, closes, and drops — port exhaustion, when logging is enabled, appears as a specific log event. Pricing, like AWS, combines a per-gateway-hour charge with a per-gigabyte data-processing charge.

What LNG is

LNG — Linode NAT Gateway — is a self-operated NAT gateway for Akamai Cloud, built entirely from primitives you already have in your account: Compute Instances, a VPC, a VLAN, Cloud Firewall, and BGP-based IP Sharing. It is a fleet of ordinary Linux instances (the NAT nodes), each independently translating traffic for a private client fleet, coordinated by a small control-plane service (natctl) that health-checks them, tells clients which ones to use, pairs them up for failover, and adds or removes capacity as load changes. Every piece of it — the instances, the firewall rules, the routing, the control plane, the dashboards — is code you own, deploy with Terraform, and can read line by line.

0.2 A Cloud Networking Primer

The rest of this book uses nine networking concepts constantly, and assumes you know what each one is and why it exists. This chapter builds them up in order, each on top of the last, from a private address range to the kernel table that makes NAT work at the packet level. If you already know them all, the quick-reference table at the end is still worth a scan — it pins down exactly what each term means in this system.

(a) Private networks and subnets

An IPv4 address is 32 bits, conventionally written as four numbers. A subnet is a contiguous range of those addresses, written in CIDR notation as a starting address and a prefix length: 10.60.16.0/20 means "the 20 leading bits are fixed, the remaining 12 vary," which is 212 = 4,096 addresses from 10.60.16.0 through 10.60.31.255. The prefix length is not decoration — a machine uses it to decide whether a destination is on its own local network (deliverable directly) or somewhere else (must be sent to a router). Part III, 3.4 describes a failure that comes entirely from getting a prefix length wrong.

Three ranges are reserved worldwide for private use, never routed on the public internet, and free for anyone to use inside their own network:

RangeSizeWhere you'll see it in this book

192.168.0.0/1665,536 addressesVLAN segments — for example 192.168.100.0/24 as a pool's VLAN, where client instances and nodes' VLAN-side addresses live

"Private" here means exactly one thing: no router on the public internet will carry a packet addressed to one of these. It says nothing about who can reach the address from inside the same private network — that is a question for firewalls and network isolation, covered below.

(b) The VPC

A Virtual Private Cloud is an isolated private network you define inside the provider's infrastructure, with its own address space carved into one or more subnets, invisible to every other customer's VPC even if they happen to use the identical address range. An instance attached to a VPC gets a private interface with an address from one of that VPC's subnets, and can talk to other instances in the same VPC over it. On Akamai Cloud, a VPC-attached instance can additionally be given a 1:1 NAT — the provider maps a public address onto that one instance's private VPC address, giving that single instance its own individual internet path. That is a clean building block for "give this one instance internet access," and it is precisely what a shared NAT gateway is not: a 1:1 NAT address belongs to one instance, changes when that instance is replaced, and gives you one public IP per instance rather than a small shared pool.

In this book's examples, the VPC has a subnet 10.60.32.0/20 on which NAT nodes have their private addresses (10.60.32.20, 10.60.32.21, and so on) and the control plane sits at 10.60.32.5. This project never creates the VPC itself — you bring your own, and it only reads it back (Part IX, 9.1).

(c) The VLAN, and what "Layer 2" means

Networking is conventionally described in layers. Layer 3 is the IP layer — addresses like 10.60.32.20, and routers that look at a packet's destination address and forward it one hop closer. Layer 2 is the layer beneath it: the local segment on which devices address each other directly by hardware (MAC) address, with no router in between. On a Layer 2 segment, a device that wants to reach an IP address on the same segment simply asks "who has 192.168.100.20?" (an ARP broadcast), gets back a MAC address, and sends the frame straight to it. Every device on the segment hears every broadcast, which is why a Layer 2 segment is also called a broadcast domain. A router is the thing that connects one broadcast domain to another — traffic that stays within a segment never touches one.

A VLAN on Akamai Cloud is exactly such a segment: a private Layer 2 network, local to a data center, that you attach instances to by label. Every instance on the same VLAN is one broadcast domain — any of them can send a frame directly to any other, and, critically, any of them can act as a router for any other, forwarding frames it receives out a different interface. A VLAN carries no address-assignment mechanism of its own (there is no DHCP server on it), so every VLAN address in this system is a static assignment applied directly to the interface (Part III, 3.4). And because it is a raw Layer 2 segment, the provider's firewall layer does not sit in its path at all — a fact with real security consequences, discussed under (e) below.

(d) Why this product needs both a VPC and a VLAN

It would be simpler to use one or the other. The reason both appear is a specific behavior of the VPC fabric that Part I, 1.2 explains in full detail with a packet-level walkthrough; the short version, so that chapter is not your first encounter with the words, is this: a cloud VPC is a software-defined overlay, and its fabric only delivers traffic that matches what it knows about each interface. A packet whose destination is the public internet, but which a private instance has handed to a different instance's VPC interface asking it to forward on its behalf, matches nothing the fabric expects — and is silently never delivered. The one thing a NAT gateway fundamentally needs from its clients — "send your internet-bound traffic to me and I'll forward it" — is the one thing the VPC fabric will not carry between two instances.

A VLAN has no such restriction. Any device on the segment can forward for any other, exactly the behavior a NAT gateway requires. So the private client fleet and each NAT node's client-facing interface live on a VLAN. The VPC is still used, for two things it is genuinely better at: a firewalled, provider-routed private channel between NAT nodes for synchronizing connection state (Part IV, 4.3), and a path by which clients and the monitoring stack reach the control plane. Every NAT node therefore has three interfaces — public, VPC, and VLAN — each doing exactly one job. (e) Cloud Firewall

A Cloud Firewall is packet filtering performed by the provider's own infrastructure, in front of an instance's network interface — before any packet ever reaches the instance's operating system. It is stateful: when an instance opens an outbound connection that the rules allow, the replies to that specific connection are automatically allowed back in, without a matching inbound rule; only genuinely new inbound connections are checked against the inbound rule list. A firewall has a default policy for each direction (this project uses deny everything inbound, allow everything outbound on every node) plus an explicit list of exceptions, each scoped to a protocol, a port, and a source address range. The complete rule set this project creates, with the reason for every rule, is Part VIII, 8.1.

The one thing to carry forward from this chapter: on Akamai Cloud, Cloud Firewall filters an instance's public and VPC interfaces only. It does not see VLAN traffic at all — a VLAN is a Layer 2 segment the provider's filtering layer is simply not in the path of. So on every NAT node, the node's own local packet filter (nftables, running inside the operating system) is the entire security boundary on the VLAN interface, and is written accordingly. This is not a gap to fix; it is how the two mechanisms divide the work.

(f) Public IPs, egress IPs, and why a small shared pool matters

A public IP is an address routable on the internet — the address a remote server sees a connection arriving from, and the only kind of address a NAT gateway can translate private traffic to. When the address in question is specifically the one a fleet's outbound traffic appears to come from, it is called an egress IP. Every NAT node in this system holds a real public IP on its eth0 interface (never a VPC 1:1 NAT address — the distinction matters for BGP, below), and the set of those addresses across a pool is the pool's egress footprint.

Two properties of that footprint matter to the people downstream of it. Size: a partner firewall, a SaaS vendor's IP allow-list, or a compliance control that says "all egress must come from approved addresses" wants a short, fixed list. A pool of three nodes is three addresses; a hundred instances each with their own public IP is a hundred. Stability: by default, an instance's public IP is ephemeral — replace the instance and it comes back with a new one, and an allow-list somewhere silently breaks. A reserved IP is a standalone address you own independently of any instance, so a node can be replaced and come back with the same address (Part IV, 4.6). Every public IP also has a finite supply of source ports — practically on the order of 55,000 to 64,000 usable toward any single destination — which is why "how many connections can this pool carry to one destination" is a function of how many public IPs it has, not how many nodes (Part V, 5.3).

(g) BGP, and what "BGP-based IP Sharing" means here

The Border Gateway Protocol is how the internet itself decides where to send a packet. Every network on the internet — an ISP, a cloud provider, a large enterprise — is an autonomous system that announces to its neighbors, over BGP sessions, the address ranges it can deliver traffic to; neighbors pass those announcements on, and every router ends up with a table of "to reach this range, send toward that neighbor." If an announcement is withdrawn, the routes that depended on it disappear and traffic follows the next-best announcement instead. The useful mental model is the currently standing, verified announcement wins: routers do not remember where an address used to live, they forward toward whoever is announcing it right now.

IP Sharing on Akamai Cloud brings that mechanism down to the level of individual instances. Normally an instance's public IP is delivered to that instance and nowhere else. IP Sharing lets a second instance be registered as a legitimate alternative destination for the same address, after which the provider's own routers stop delivering it by fixed assignment and instead deliver it to whichever registered instance is actively announcing it over a BGP session with the provider's route reflectors. Each NAT node runs a small BGP daemon, FRR (FRRouting), that announces the node's own public IP as its primary and — once the node has been paired with a buddy — announces the buddy's public IP as a secondary, lower-preference route, from the moment the pairing exists rather than only after a failure. While both nodes are up, the primary announcement wins and traffic flows normally. If a node dies, its own announcement stops, its buddy's already-standing secondary announcement is now the best one available, and traffic addressed to the dead node's public IP arrives at the buddy instead — with no DNS change, no client reconfiguration, and no human involved. Two constraints shape how this is used: only one instance may be registered as the secondary for any given address, and only a real public IP on the instance's own interface — never a VPC 1:1 NAT address — is eligible for sharing at all. Part IV, 4.4 is the full treatment, including the safety delays that guard the moment an address is first switched into BGP-only delivery.

(h) ECMP — one route, several equally good next hops

A machine's default route is where it sends every packet whose destination it has no more specific route for — in practice, everything internet-bound. Normally a default route names exactly one next hop. Equal-Cost Multi-Path routing is an ordinary Linux kernel feature that lets a single route name several next hops of equal preference, spreading traffic across all of them — several checkout lanes instead of one, with the kernel choosing a lane per packet. In this system, every private client's default route is an ECMP route whose next hops are the VLAN addresses of every currently healthy NAT node, something like this in shape:

# illustrative — a client's default route across a three-node pool
default
    nexthop via 192.168.100.20 dev <vlan-iface> weight 1
    nexthop via 192.168.100.21 dev <vlan-iface> weight 1
    nexthop via 192.168.100.22 dev <vlan-iface> weight 1

The lane choice cannot be random per packet, because NAT state lives on one specific node — every packet of one TCP connection has to reach the same node, or the reply will be matched against a table that has no entry for it. So the kernel picks the next hop by hashing the packet's flow identity: source and destination address, and — when the kernel's multipath hash policy is set to include Layer 4 fields, which the client agent sets at every startup — source and destination port as well. That five-field key, the five-tuple, is identical for every packet of one connection, so the whole connection stays on one lane, while thousands of separate connections to the very same destination still spread across every lane. Linux's resilient nexthop group mode adds one more property this system depends on: when a next hop is removed, only the flows that were hashed to that next hop are reassigned, and every flow on every other node is left exactly where it was. Without it, any membership change would reshuffle every connection in the fleet; with it, losing one node out of N disturbs roughly 1/N of traffic and nothing else. Part III, 3.2 covers how the client agent maintains this route.

(i) conntrack — the table that makes NAT work, and why syncing it matters

The per-connection memory described in 0.1 is not an abstraction: it is a real kernel data structure called the connection-tracking table, or conntrack, maintained by the Linux netfilter subsystem on every NAT node. Every connection that passes through the node gets one entry, recording the connection as the private side sent it and as it looks after translation. The connection from the worked example in 0.1 looks like this in the table (this is the format the standard conntrack -L tool prints — the first half is the original direction, the second half is what a reply must look like to be matched back to it):

tcp  6 431999 ESTABLISHED src=192.168.100.42 dst=142.250.72.14 sport=51234 dport=443 \
                          src=142.250.72.14 dst=172.236.173.125 sport=443 dport=51234

Every reply packet arriving on the node's public interface is looked up against the reply half of every entry; a match tells the kernel exactly which private address and port to rewrite the destination back to. An arriving packet that matches nothing is not a reply to anything and is dropped — which is how NAT's outbound-only property is actually enforced. The table has a fixed maximum size (nf_conntrack_max, one million entries by default in this system); when it is full, new connections cannot be tracked and fail outright, which is why table occupancy is the headline capacity signal the autoscaler watches (Part V, 5.2) and why Part V, 5.3 tells you how to size it.

This table is also exactly what is lost when a node dies. The client-side ECMP route reroutes new connections to surviving nodes within seconds, but a connection that was mid-flight had its one and only table entry on the dead node — the survivor receiving its next packet has no idea what to do with it, and the connection resets. Connection-state sync closes this: a standard daemon, conntrackd, continuously mirrors one node's table to its buddy over the VPC interface, so that if the node dies, the buddy already holds a copy of every entry. Combined with IP Sharing (g) delivering the dead node's public IP to that same buddy, a still-open connection's next packet arrives at a node that has both the address it was sent to and the table entry to translate it — and the connection simply continues, as if nothing had happened. Neither half works alone: mirrored entries for an address that no longer arrives are useless, and a taken-over address with no entries resets every connection anyway. Part IV, 4.3 and 4.4 are the two halves in full.

0.3 Why Self-Hosted, and When It's the Right Choice

A managed NAT gateway is the correct default for most teams most of the time, and this book does not pretend otherwise. LNG exists for the cases where the managed product's opacity, cost structure, or lack of control is itself the problem — and it asks something real of you in return.

LNG is the right choice when at least one of the following is true. You need per-connection visibility — not an aggregate byte counter, but the ability to see connection-table occupancy per node, port headroom per public IP, drop reasons, and node health per individual check, and to alert on any of them before they become an outage. You need a small, static, shared egress footprint that survives instance replacement, because a partner's allow-list or a compliance control depends on it, and you want to own the addresses rather than rent them. You need full operational control: your own firewall rules on the gateway itself, isolated capacity for a tenant that cannot share, an autoscaling decision you can read the reasoning for, or infrastructure a security team can audit line by line rather than take on faith. Or your traffic volume is high enough that a per-gigabyte processing charge has become a line item worth engineering away — the compute cost of a handful of dedicated-CPU instances is fixed and predictable regardless of how many bytes pass through them.

LNG is not the right choice for a team that wants NAT to be somebody else's problem and is content with the trade-offs the managed products make. That is a legitimate position, and it is worth being honest about what self-hosting asks: you own real Linux instances, so you patch them, size them, and are on call for them. You run the occasional failover drill to confirm the mechanisms in Part IV still behave as described. You make capacity-planning judgment calls the managed products make silently on your behalf. And you accept that the active-active design this system uses — every node forwarding real traffic all the time, no idle standby — trades the simplest possible zero-session-loss guarantee of a fixed master/standby pair for horizontal scaling and full utilization; the opt-in mechanisms in Part IV narrow that gap substantially, but Part IV, 4.8 states plainly that they narrow rather than eliminate it. A workload that truly cannot tolerate a single connection reset under any circumstance should weigh that carefully.

Part X is written to make the ownership side of this as low-friction as it realistically can be — a pre-production checklist, an operator CLI, procedures for every routine task, and a troubleshooting playbook that starts from zero context on each alert. It reduces the operational load; it does not make it zero, and nothing in this book will claim that it does.

Part I

Architecture & Design

What a NAT gateway pool actually is on Akamai Cloud, the one networking fact that shapes every other design decision in this book, and why every node carries three interfaces instead of one.

1.1 What This Is

A NAT gateway pool is a set of independently active compute instances, each holding its own public egress IP, that a whole private subnet shares for outbound internet access — the same job AWS NAT Gateway or GCP Cloud NAT do, built instead from primitives you own and operate directly: Compute Instances, a VPC, a VLAN, Cloud Firewall, and BGP-based IP Sharing.

Every node in a pool forwards real customer traffic all the time — there is no active/passive pair and no idle standby capacity waiting for a failure. Private-subnet instances run a small routing agent that spreads their outbound traffic across every currently healthy node in the pool using ordinary Linux multipath routing (ECMP). A separate control-plane service continuously health-checks the fleet, hands out the current node list to every client, and grows or shrinks the pool automatically as load changes.

A purpose-built metrics exporter gives every node full visibility into its own connection-tracking table, port allocation, throughput, and packet drops — considerably more granular than either hyperscaler's own NAT monitoring.

Why a shared, static IP pool matters

Every VPC-member instance already gets a private interface and, if it wants one, its own individual 1:1 NAT to a public address — a clean building block, but not what most real deployments need. A partner or vendor firewall allow-list, or a compliance regime that requires all egress to be auditable and traceable to a small, known set of addresses, needs a whole private subnet funneled through a small, shared, static pool of egress IPs instead of one address per instance. That single requirement — a shared, controllable, observable egress boundary — is the reason this whole system exists.

1.2 The Constraint That Shapes Everything

A VPC fabric will not transit-route a packet through a peer VPC instance out to a non-VPC destination. A private instance sitting in the same VPC as a NAT node cannot simply add a route pointing at that node's VPC address and expect its traffic to reach the internet through it — the fabric drops it.

What that looks like at the packet level

Say a private instance, Server A — VPC address 10.0.1.20, no public IP of its own — wants to reach google.com. Its default route points at a NAT node's VPC address, 10.0.1.5, hoping that node will forward the packet out to the internet the way an ordinary router would. Why the fabric behaves this way

Akamai Cloud doesn't publish the exact internal mechanism, so this is the general, well-understood pattern this behavior matches rather than a confirmed internal detail: a cloud VPC is a software-defined overlay network, and the underlying fabric typically only programs a delivery path for traffic that stays consistent with what it already knows about each port — the address(es) actually assigned to that port, and destinations that are either inside the same VPC or leaving through that same instance's own public/NAT boundary. A packet whose destination is the public internet, but which is being handed to a different instance's interface to forward on its behalf, doesn't match that model, so the fabric has nothing to do with it — it's simply never delivered, the same class of behavior public documentation for AWS, GCP, and Azure VPCs describes as source/destination validation on hairpin or transit traffic.

What was actually verified, not just assumed Two real instances were used to test this directly, rather than trusting a general expectation: one with a public IP and NAT/forwarding configured (playing the router), one with only a VPC address and its default route pointed at the first. Packet captures ran on both instances at the same time. The sender's own capture showed every outbound packet leaving correctly; the would-be router's capture never showed any of them arriving — and its own firewall's forward-chain counters stayed at zero the entire time, meaning it wasn't even reaching a point where something local could reject it. Akamai Cloud's VPC fabric does not forward a packet through a peer VPC instance to a non-VPC destination, confirmed directly rather than assumed from documentation.

This single fact is why the private client fleet rides a completely separate Layer-2 fabric — a Linode VLAN — instead of VPC. A VLAN has no such restriction: any device attached to it can forward traffic through any other device on the same segment, exactly the behavior a NAT gateway needs from its clients. It is also why every node in the fleet carries not one but three purpose-built interfaces, each doing exactly one job, described next.

1.4 Active-Active, Pools, and Isolation

Every node in a pool is independently active — there is no master, no standby, no shared floating IP that all traffic funnels through. A pool is the unit of both scaling and isolation: the default shared pool serves every tenant that doesn't need dedicated capacity, and a tenant that does gets its own dedicated pool — its own VLAN, its own scaling bounds, fully isolated from every other tenant's traffic, but built from the exact same mechanism, not separate code.

Because every node is active all the time, one heavy tenant's traffic can burst across the entire pool rather than being capped at whatever a single pair could carry — the direct fix for the single biggest limitation of an active/passive design.

2.1 The Fleet Controller

The fleet's brain is a single service called natctl, packaged as one systemd service (natctl.service) that runs continuously and repeats the same fixed sequence of work — a pass — over and over on a timer.

What a "pass" actually is

A pass (also called a reconcile pass) is one full run through natctl's control loop, repeating every 15 seconds by default. Each pass does the same five things, always in the same order:

  1. Discover — ask the cloud provider which instances currently belong to this pool (see "Discovery" below).
  2. Health-check — probe every discovered node (see "The health check" below).
  3. Compute buddy pairings — decide which healthy nodes back each other up (preview below, full detail in Part IV).
  4. Evaluate autoscaling — decide whether the pool needs to grow or shrink (Part V).
  5. Publish the roster — recompute the JSON snapshot every client reads (Part II, 2.2).

Every one of those five steps is redone from scratch, every single pass — nothing about steps 2–5 depends on what happened in a previous pass beyond the live state that step 1 just re-discovered.

Discovery — what the tags are, who creates them, where to see them

Every node in a pool — whether it's a fixed floor node or one natctl provisioned itself — carries the same three cloud-provider tags: lng, lng-fleet, and lng-pool-<pool-name> (for example, lng-pool-shared). A node natctl provisioned itself also gets a fourth tag, lng-elastic, which is how the controller tells its own capacity apart from the fixed floor.

The infrastructure-as-code that creates floor nodes applies these tags at creation time; natctl applies the identical tags itself the moment it provisions an elastic node. Discovery, every pass, is one API call asking the cloud provider "give me every instance tagged lng-pool-shared" — a plain tag filter, not a database lookup against anything natctl owns. You can see these tags yourself the same way: in the cloud provider's own console under each instance's tag list, or from the command line with something like linode-cli linodes list --tag lng-pool-shared.

The health check — what it actually does

Every node runs a small metrics/health service of its own on port 9200. Once per pass, natctl makes one plain HTTP request — GET http://<node's private IP>:9200/healthz — with a short timeout, and that endpoint runs three real checks on the node itself before answering:

  1. Is IP forwarding actually turned on in the kernel?
  2. Does the node's own live NAT firewall ruleset actually contain the specific rules it's supposed to — not just that the ruleset object exists at all, which stays true even if something external stripped every rule out of it without ever putting them back?
  3. Does a real outbound HTTPS request, sent from the node's own public interface, actually succeed?

All three must pass for the node to be reported healthy — any single one failing (or the request timing out at all) reports the node unhealthy immediately. The second and third checks are the important ones: a node can be perfectly reachable on the network, and even have an nftables ruleset that technically exists, while its actual NAT path is quietly broken underneath — only checking for the specific expected rules and a real end-to-end request catches that. This proves the node can forward and NAT traffic; it deliberately does not try to prove traffic is flowing through it right now, since a correctly-configured node with no clients currently assigned would fail that test for a completely healthy reason — see nftables_accepts_total (Part VII, 7.3) for that separate question instead. See Part VII, 7.5 for the full detail on why this specific design choice matters.

Buddies — a preview (full detail in Part IV)

A "buddy" is another node this one continuously mirrors live connection state with, and stands ready to take over the public IP for if it dies. Buddies exist to shrink how much traffic a single node's failure actually disrupts. Every node normally has exactly one buddy — an ordinary pair — except when the pool's healthy node count is odd, in which case one extra node is folded into a three-node group instead of being left with no partner at all (Part IV, 4.2). The sync itself runs as its own process per pairing, entirely independent of natctl — natctl only computes who's paired with whom, every pass; it never does the actual syncing itself. If a buddy relationship breaks, the affected node is still completely healthy and still fully in rotation — it's a mitigation for connection loss on a future failure, not a health signal on its own. Exactly how sync works, what protocol/port it uses, how to check it, and how to restart it if it breaks are all covered in full in Part IV, 4.3 — this paragraph is just enough to make the rest of this chapter make sense.

Provisioning and removing elastic capacity

Within the bounds an operator configures for the pool (a minimum and a maximum), natctl decides every pass whether to add or remove elastic nodes — the exact algorithm is Part V, 5.2. A few practical questions worth answering here directly:

  • What happens when a floor node goes down, and how do you recover it? natctl never deletes or replaces a floor node under any circumstance — that's a hard boundary, not a bug. Instead, it provisions extra elastic capacity to compensate for the missing floor capacity, so the pool keeps serving traffic at full strength while the broken floor node sits there unhealthy. Recovering it is a manual step: SSH in and fix whatever's wrong, or replace the instance yourself through your infrastructure-as-code (a targeted re-apply of just that one node). Once it passes its health check again, the extra elastic capacity that was compensating for it drains back down automatically on a later pass.
  • How does an operator raise the floor? Change the floor node count in your infrastructure configuration and re-apply it — see Part IX and Part X for the exact command. Every connected client picks up the new node automatically on its next roster read; no restart of anything is required anywhere.
  • Does raising the floor interact with reserved IPs? Only if reserved IPs are already turned on for the pool (Part IV, 4.6) — in that case, every new floor node created by raising the count automatically gets its own reserved address the same way every existing floor node already has one; there's no separate "grow the reserved-IP pool first" step. The only time you'd act on the reserved-IP pool directly is if you want a specific, already-owned address reused for a new node instead of a fresh one being minted — that's the "bring your own reserved IPs" list, supplied ahead of raising the floor count.

The roster — what it is, concretely

The roster is the JSON snapshot natctl computes as the very last step of every pass — nobody else generates it, and it isn't a separate service or a stored file anywhere durable. It lives entirely in memory and is rebuilt from scratch every 15 seconds; served over plain HTTP as plain JSON, no special protocol involved. The next chapter covers exactly what's in it, with a real example.

Nothing about the fleet controller is read back from a database. Every pass rebuilds the entire fleet's state from scratch, directly from live cloud-provider discovery (the tag lookup above) and each node's own health probe (the /healthz request above) — never from anything natctl itself wrote down earlier. This single design choice is what makes the control plane genuinely disposable: if it restarts, or is temporarily unavailable, it has nothing to recover — the very next pass reconstructs an accurate picture of the fleet on its own, the same way every other pass always has.

What actually stops if the control plane goes down Already-provisioned nodes keep forwarding traffic untouched — they don't ask permission to do their job. What pauses is new decisions: provisioning or removing elastic nodes, reassigning failover buddies, replacing a persistently unhealthy node, and roster freshness beyond whatever every client already cached.

2.2 The Roster URL

Every routing decision in the system — which nodes a client should send traffic through, which peer a node should mirror connection state with, which target Prometheus should scrape — ultimately traces back to one HTTP endpoint: GET /fleet/<pool>, served by the fleet controller.

What it actually is

It is a plain HTTP endpoint, not a separate service or a piece of infrastructure that gets "provisioned." The moment natctl starts and binds its listening port (8099), that endpoint exists — creating the roster URL is simply a byproduct of deploying and starting the control plane itself, nothing more.

A concrete example

How it's kept fresh

Every reconcile pass — discover instances, health-check each one, recompute buddy pairings, evaluate whether the pool should scale — ends with the controller recomputing this exact JSON document in memory and diffing it against the previous pass. Only a real change bumps roster_version and wakes anyone waiting on it; a pass with nothing new to report is a no-op from the roster's point of view. There is no separate "update the roster" step to remember — publishing the roster is simply what every reconcile pass ends in.

Long-polling: near-instant reaction, near-zero idle traffic

A plain GET /fleet/shared always returns immediately with whatever the current snapshot is — nothing about that behavior changes. Add ?wait=true&since=42 (the roster_version the client already has), and the request is handled completely differently: the server holds that one connection open — without answering yet — until either roster_version actually changes, or roughly 25 seconds pass, whichever happens first. It's still a perfectly ordinary HTTP request; the only difference is the server delays its own reply.

  • Nobody "pushes" anything. There's no separate push channel or open socket the server writes into on its own initiative — the client always makes the request first, and the server simply waits before responding instead of answering immediately. This is a long-poll, not a WebSocket or a server push.
  • Why near-zero idle traffic. With plain polling, a client sends a brand-new request every few seconds forever, whether anything changed or not. With long-polling, a client sends one request and that single connection just sits there — no new requests, no new bytes on the wire — until there's actually something worth reporting. The "traffic" that disappears is every one of those repeated, mostly-pointless requests during a quiet period.
  • How many connections can the control plane hold open at once? Honestly: this hasn't been load-tested to a specific number, and it's worth knowing that rather than trusting a made-up figure. Each held-open long-poll ties up one thread and one file descriptor on whichever host is answering it — so the real ceiling is that host's own thread/file-descriptor limits, not anything special in the roster logic itself. If you're planning for a genuinely large client count, load-test at that count before trusting it blindly, the same way you'd load-test any thread-per-connection HTTP service.
  • How does a client know which IP to connect to in the first place? There's no auto-discovery — an operator sets this explicitly, once, when a client is onboarded (Part IX): the client's routing agent is configured with the control plane's private address and port (NATCTL_ROSTER_URL=http://10.60.32.5:8099/fleet/shared), the same way you'd configure any client to point at a known server address. This can also be a comma-separated list of several addresses — every node's own, when the control plane runs on every node (2.3) — and the agent tries each in turn, starting from whichever last succeeded. A client with only one address configured has nothing to fall back to if that one specific answering node happens to be down the moment the client starts fresh; listing every node closes that gap.

Health is authoritative here, not advisory

The roster's healthy field is the control plane's own computed verdict from its /healthz check (Part II, 2.1) — not a raw "is the node reachable" ping. Every routing agent trusts that verdict by default rather than independently re-probing every node on its own. This is a deliberate, structural simplification, not a shortcut: every node and every client sit on the same physical VLAN Layer-2 segment, so reachability is essentially uniform across every client — there is no realistic scenario where a client's own probe would see something the control plane's own health check missed.

An operator who wants the old belt-and-suspenders behavior anyway can turn on an additional local probe per client — "belt and suspenders" simply means using two independent safety mechanisms at once even though either one alone would normally be enough, as extra insurance against the first one being wrong. When that opt-in probe is on, a node only counts as usable if both the control plane's verdict and the client's own direct check agree it's healthy.

How the roster URL itself stays available

This depends entirely on where the control plane runs (see the next chapter). Run on a single dedicated host, there is exactly one instance answering roster requests — a control-plane single point of failure for freshness, not for traffic already flowing. Run on every node instead, every single node answers roster reads identically and correctly regardless of which one currently holds write authority over the fleet — at that point the roster URL is effectively as available as the fleet itself, since any surviving node can answer it.

What happens if a client can't reach it

A routing agent that fails to reach the roster URL never blackholes existing traffic. It keeps serving whatever roster it last successfully fetched, and if the set of healthy nodes it's holding onto is ever completely empty, it deliberately leaves the existing route in place rather than tearing egress down entirely. The failure mode of an unreachable control plane is "traffic keeps flowing on stale information," never "traffic stops."

That protection only applies once an agent already has something to fall back to. One that's freshly starting — or restarting, which happens far more often for a container that gets rescheduled than for a long-lived VM — has no prior roster at all, so a single configured address that happens to be down at that exact moment leaves it with zero routes until that address recovers. The multi-address list described above is what actually closes this: an agent with several addresses configured only fails its very first fetch if every single one of them is down at once.

2.3 Where the Control Plane Runs

The fleet controller — natctl — has two supported placements. What a client sends its roster request to changes between them: on a single dedicated host, the controller carries a public interface, a VPC one, and — since it now also joins the default pool's VLAN directly — a VLAN one too, so a client on that same VLAN can reach it there without needing a VPC interface at all; a client on a different VLAN (a dedicated tenant pool with its own separate VLAN) still needs its own VPC interface to reach it instead. Run on every node instead, and the roster is reachable over the fleet's VLAN everywhere too, since every NAT node already has that interface — the better choice whenever a client has one, since VLAN is a single flat network with nothing to route, where the VPC path (below) needs the fleet's own routing configured correctly first.

Running the controller on every node is possible because it is entirely stateless — everything it computes is derived fresh from live discovery and health checks each pass, never read back from storage. The one real problem this placement introduces is the one every active-active control plane has to solve: more than one instance could try to mutate cloud state at the same moment. That problem, and how it's solved, is the next chapter.

Decide your node count before you turn this on The next chapter explains the full safety mechanism this placement relies on, but the short version — worth knowing before you commit to a floor node count, not after — is that how well it protects you depends entirely on how many nodes are in the pool:
  • One node: there's no failover to speak of — it's always the leader by default, and this placement buys you nothing over the single dedicated host except one fewer instance to run. Use it only if that specific trade-off is what you want.
  • Two nodes — the genuinely risky configuration, unless you add a witness. A real network split between exactly two nodes looks, from either side, identical to the other one actually being dead — there's no third node to ask, so the extra corroboration step described in the next chapter cannot help at all here; the pool falls back to a single node's own judgment, unaided, the same as if that step didn't exist. Both nodes can end up trying to act on that judgment in the same window. Turn on the witness role (below) for a real, cheap third voter that closes this — without one, don't run two nodes in this placement for anything where continuous availability matters.
  • Three or more nodes, or two nodes plus a witness: this is the point where the extra corroboration step actually means something — a candidate needs genuine agreement from at least one other member before it can act, closing the single-point-of-judgment gap the two-node case has no way around. A witness adds nothing once a pool already has three or more real nodes.

The witness role: real quorum safety at two nodes, without a third full node

Set witness_enabled = true on a pool (alongside witness_instance_type, default g6-nanode-1, and witness_private_ip_offset) to provision one small, permanent instance that votes in leader-election corroboration and independently health-checks the pool's real nodes — without ever forwarding traffic, holding a public IP, or joining buddy pairing. It's a fully real third voter from every other node's point of view, just sized to what the role actually needs rather than to NAT-node parity. Only meaningful alongside every-node placement — a witness has nothing to vote in otherwise. Adding or removing one later is a normal terraform apply, same as any other resource.

Can you switch this on an already-live fleet?

Yes, but treat it as a maintenance-window change, not a zero-impact toggle. This setting changes what's embedded in every floor node's own boot configuration, and the infrastructure tooling has no way to update that in place on a running instance — so applying the change destroys and recreates every floor node to pick up the new configuration. Reserved IPs and the deterministic address scheme (Part IV) mean every recreated node comes back with the exact same address it had before, so nothing downstream needs to be reconfigured — but every floor node does go through a real boot cycle to get there.

The "writer" node, and how a client knows who to talk to

In every-node mode, exactly one instance at a time is elected leader — the only one currently allowed to make cloud-mutating calls (create/delete a node, update a BGP IP-sharing assignment). Every other instance is a follower: it still runs the full read-only pipeline every pass — discovery, health checks, computing what it would do — but stops short of actually performing any mutating action.

From a client's point of view, there is no difference between talking to the leader or a follower at all. Every instance's roster read reflects the same underlying discovered state, since discovery and health-checking run identically everywhere — only the write path is restricted to one instance. An operator picks any one node's private address to configure into a client (Part II, 2.2) — not necessarily the current leader, since leadership can change over time and every instance answers reads identically regardless. There's no built-in load-balancing across nodes for roster reads today; every client you onboard is pointed at whichever one address you give it.

How a node checks its own health

In every-node mode, each instance health-checks every node in the pool, including itself. Checking yourself deserves a second mechanism, not just the plain network check every other node gets: a request aimed at your own private address is delivered by the kernel's own local routing table rather than the physical network interface, so a plain self-check can never observe a fault in that interface's reachability from anyone else's point of view — the one thing it would actually need to catch.

So a node's self-check that reports healthy is corroborated before it's trusted: every currently known peer is asked for its own, independently computed opinion of that same node — each peer already has one, since it health-checks every node in the pool too. A single peer vouching healthy is enough to trust the self-check immediately, biased toward keeping a genuinely healthy node in service. Only when every reachable peer unanimously disagrees, and that disagreement holds for two consecutive reconcile passes in a row, does the self-check get overridden. A peer that can't be reached to ask at all is never treated as evidence either way — a transient hiccup querying one peer can't flip a healthy node's status on its own.

A pool running with a single node has no peer to corroborate against, so it leans on a different safety net instead: the client's own independent reachability check (Part II, 2.2's fallback probe) switches on automatically whenever a pool's live node count is exactly one, unless an operator has explicitly set it otherwise. The moment a second node joins, peer corroboration takes back over.

2.4 Leader Election and Fencing

When the controller runs on every node, read-only work — discovery, health checks, buddy-pairing computation, serving the roster — runs on every instance all the time, regardless of leadership. Only the calls that actually change cloud state (provisioning a node, updating a BGP IP-sharing assignment) are gated to a single leader at a time.

The lease is a bulletin board, not the safety mechanism

Leadership is tracked via a lease record — a small JSON object naming the current leader's node id, its term number, and when it was last renewed — stored durably in Object Storage so every instance can read the same value. A leader must renew this record at least once every 45 seconds (its configured lease lifetime) or the lease is considered expired. That record is deliberately treated as a best-effort hint, never as the actual source of correctness: a lease alone cannot guarantee only one writer is active at a time under every possible network condition — nothing about writing it is an atomic compare-and-swap. Renewing it retries a single transient read/write failure once before conceding, rather than treating one momentary storage hiccup as equivalent to actual leader death — the retry is deliberately small and bounded, since piling on more of them risks eating into the 45-second lifetime itself.

Every pool holds its own, completely separate election

A fleet with a shared pool and a dedicated tenant pool runs two independent elections, each with its own lease record, its own term counter, and its own leader — never one election deciding both. The same physical node can be leader of one pool and a plain follower of the other at the same moment; there is no such thing as "the fleet's leader," only "pool X's leader" and "pool Y's leader," decided completely separately.

This matters for who is even allowed to enter a given pool's election in the first place. Because every node's controller carries the full configuration for every pool in the fleet — not just its own — it technically knows how to compute buddy pairings and evaluate autoscaling for a pool it has no membership in at all. Left unrestricted, that node would also be a technically-eligible candidate for that other pool's leadership, and — worse — its fencing target if that pool's lease ever looked expired, despite having no actual stake in it. So candidacy is scoped: a node re-checks its own current membership in a pool (its own controller's live discovery of that pool's nodes, refreshed every pass) before ever attempting that pool's election, and steps back immediately — without ever fencing anyone — if it isn't currently a member. A node that was a member and leader, but has since been drained out of the pool, steps down the same way rather than continuing to renew a lease for a pool it's no longer part of.

A worked example: what happens when the leader disappears

Node A is leader, term 5, renewing its lease every 15-second pass — comfortably inside the 45-second lifetime. Node A crashes.

  1. No renewal happens. Once 45 seconds pass since Node A's last renewal, Nodes B and C — both followers, and both current members of this same pool — each independently notice on their own next pass that the lease has expired.
  2. To avoid both racing into an election at once, each first waits a random delay of up to 10 seconds (the election jitter) before doing anything else.
  3. Say Node B's random wait happens to be shorter. It wakes first, re-reads the lease record one more time to confirm nobody else already claimed it during its wait, sees it's still expired, and — before doing anything else — tries to reach Node A directly (below). Node A doesn't answer. Node B begins fencing: it calls the cloud provider's power-off API against Node A, then polls — up to 60 seconds — until Node A is confirmed either genuinely offline or no longer exists.
  4. Only once that's confirmed does Node B write itself into the lease record as the new leader, term 6.
  5. When Node C wakes up a few seconds later, it re-reads the lease record first — this "always re-check before acting" behavior is deliberate — sees Node B already claimed term 6, and simply backs off, resuming as a follower without ever attempting its own fencing.

A trickier case: when the lease is lying

An expired lease normally means one thing — the leader is gone — but it can also mean something else entirely: the leader is fine, and it's the lease store itself that had a problem reaching it. Those two situations look identical from a follower's point of view if all it ever checks is the lease record, and only one of them should end with a node getting powered off.

So before a candidate ever calls the power-off API, it tries one more thing first: a direct request to the previous leader's own status endpoint, over the private network, asking it point-blank whether it's still there. If that node answers — even though its lease looked completely expired — the candidate treats this as a false alarm, not a death, and backs off without fencing anyone or claiming leadership itself. Nothing about the pool is left leaderless forever by this: if the lease genuinely stays unrenewed, the next pass tries the whole thing again.

This check is deliberately one-sided. A node that answers is trusted immediately — but a node that doesn't answer (it's genuinely down, or just unreachable over that specific path, or the check itself times out) changes nothing: fencing proceeds exactly as it would have without this check at all. Silence was never proof of life to begin with, so the absence of an answer can't be allowed to block a fence that a truly dead leader needs.

A second opinion, before the power-off call

Everything so far still comes down to one candidate's own view: its own lease read, its own liveness check. Before ever calling the power-off API, a candidate takes one more step — it asks the pool's other members, over both their private-network and client-facing addresses independently, whether they also see the previous leader as unhealthy. This reuses information every node already computes for its own roster, rather than adding a new check to run — it's simply asking "does your view agree with mine?" before acting on it alone.

If even one other member reports the previous leader as healthy from where it sits, the candidate backs off — the same way it would if the leader had answered the direct liveness check itself. If too few other members can be reached to form a real majority, the candidate also backs off rather than act on incomplete agreement; the next pass tries again. Only when enough of the pool's other members agree does fencing proceed.

This genuinely needs other members to work at all. With three or more nodes in a pool, it's a real second opinion — a candidate can no longer decide entirely on its own that another node should be powered off. With exactly two nodes and no witness, there's no third member to ask, so this step can't add anything: the pool falls back to the candidate's own view, same as before. A pool of exactly two nodes running the control plane on every node is inherently the hardest case for this kind of coordination — a genuine network split between the two looks identical, to each side, to the other one actually being down, and no amount of software on either side can tell the difference without a third vantage point. Three or more real nodes, or the witness role (2.3), is what actually gives this step real teeth: with a witness present, a node whose own control plane died but whose actual traffic-forwarding service stayed healthy is correctly left alone (the witness's own independent check vouches for it, since it health-checks the traffic-forwarding service directly rather than trusting the control plane's own self-report), while a genuinely unhealthy node is still correctly fenced.

The real safety mechanism: fencing

Before a candidate ever claims leadership, it powers off the previous leader through the cloud provider's own instance power-management API and polls until that shutdown is confirmed — either a genuinely offline status, or a not-found response meaning the instance no longer exists. If the power-off call fails, or confirmation never arrives in time, the candidate aborts the election outright rather than proceeding — an unconfirmed fence provides no real guarantee, so the system fails closed instead of optimistically continuing. A fenced node is left powered off, not automatically rebooted — an operator needs to investigate and boot it back up deliberately, the same as any other unhealthy node needing attention.

Layered on top: the randomized jitter above (reducing the odds of two candidates colliding at once), the direct liveness check just described, a write-then-reverify step immediately after claiming leadership, and a fresh leadership check immediately before every individual mutating call — not just once per pass — so a node that loses leadership mid-cycle stops mutating within one call's window, not one whole cycle's.

Live testing found a real edge in that write-then-reverify step: two candidates can race to fence the same dead leader with genuinely different completion times, and the faster one's own reverify check passes correctly — it really was the sole leader at that instant — only for the slower one's write to land moments later and quietly take over, also passing its own check correctly. For a short window, both believed they'd won, and both could act on it. An optional extra delay-then-recheck step closes most of that window in practice — waiting long enough to see whether a slower competitor shows up before ever acting on a freshly-won election — but it narrows this rather than eliminates it outright: a competitor slower than that wait can still land afterward. Closing it completely would need the kind of strict, always-available coordination service this design deliberately avoids standing up, for the reasons discussed throughout this section.

That per-call check isn't something the higher-level scaling/failover logic merely remembers to do on its own — it's enforced one layer lower, by the small internal component that actually talks to the cloud provider's API. Every function capable of changing cloud state (creating or deleting a node, updating a BGP IP-sharing assignment, reserving or releasing an IP) requires a passing leadership check to be handed to it as a condition of being called at all; there is no path to reach the cloud provider's API that skips this. A rejection there is treated as a distinct kind of event from an ordinary network or API failure — it means "stand down," not "retry" — so the two are never confused with each other in the system's own error handling or logs.

What if two nodes really do try to write at the exact same moment? (the "split-brain" scenario)

Since the lease record isn't an atomic compare-and-swap, two candidates could, in a narrow and short-lived window, both briefly believe they've won the same election — the design doesn't claim to make that mathematically impossible, only rare. What actually prevents both from mutating cloud state is the separate, per-call check described above: immediately before either one attempts a real mutating action (not once per pass, but freshly for that one specific call), it re-reads the lease record one more time. Only whichever one's check runs first against the current record is allowed to proceed; the other's check will already see the new leader and refuses to act.

Live testing found a real edge in that reasoning: two candidates racing to fence the same dead leader don't necessarily finish at the same speed. The faster one's own re-check passes correctly — it really was the sole leader at that exact instant — only for the slower one's write to land moments later and quietly take over, also passing its own re-check correctly. For a short window, both genuinely believed they'd won. An optional extra step closes most of that window in practice: after winning, wait a short, configurable delay, then check once more before ever acting on it — giving a slower competitor a real chance to show up before anything gets mutated. This narrows the window rather than eliminating it outright: a competitor slower than that wait can still land afterward, at which point the same per-call check described above is what catches it — as it did the first time this was observed live, blocking every pending action before any of them reached the cloud provider's API.

Honest limit, with a concrete scenario This is defense in depth, not mathematically perfect mutual exclusion the way a hardware-fenced active/passive pair would be. Concretely: imagine Node A can still reach the cloud provider's API — so it's still capable of making real mutating calls — but has lost its network path specifically to the Object Storage bucket holding the lease record, so it can't renew its lease and can't see anyone else has claimed leadership either. From Node B's side, Node A's lease simply looks expired; the direct liveness check above only helps if Node A can still answer a private-network request, which a node that's lost its path to Object Storage specifically (but nothing else) still can — so in the exact scenario this callout describes, that check would actually catch it and Node B would back off. The gap that's genuinely still open is narrower still: a leader that's lost both its path to the lease store and its path to the liveness check, while keeping a path to the cloud provider's mutating API — at that point Node B fences it (powers it off) and takes over, which is exactly the scenario fencing exists to handle safely, since Node A is physically powered off before Node B ever starts mutating anything. What's left unclosed is the brief window between Node A's own last leadership re-check (which passed) and the moment the fencing power-off command actually reaches and takes effect on Node A. If Node A happened to fire a mutating call inside that exact narrow window, both could very briefly be acting on the fleet at once. That window is measured in seconds — bounded by how often a node re-verifies its own leadership, which is immediately before every mutating call, not once per pass — not minutes, but it is real and not claimed to be zero.

The trade-off fencing accepts

A fenced node is powered off, not just demoted. Once the controller runs on the NAT nodes themselves rather than an isolated dedicated host, the node being fenced is also, at that moment, forwarding real NAT traffic — so a fencing event briefly interrupts that node's own data-plane role too. Buddy IP failover (Part IV) is what limits the blast radius of that specific interruption, exactly the same way it limits any other single node's failure.

What happens if the cloud provider's own API is the thing that's unreliable

Every mutating call the control plane makes to the cloud provider — a fencing power-off, provisioning or removing elastic capacity, registering an IP-failover pairing — passes through a circuit breaker first. After a run of consecutive network errors or server-side (5xx) failures against that API, the breaker opens: every further mutating call is refused outright, without even attempting it, for a short cooldown period. A single trial call is allowed through once the cooldown elapses, and a success there closes the breaker again; a failure reopens it. A request the provider's API itself rejects as malformed (a 4xx) never counts toward opening the breaker — that's a problem on this system's own side, not evidence the provider is having an incident.

None of the control plane's read-only work is affected — the roster keeps serving current fleet state to routing agents throughout. What pauses is exactly the set of actions that would otherwise be attempted against an already-degraded API: fencing can't power off a superseded leader, autoscaling can't add or remove capacity, and IP-failover pairings can't be (re)configured. This is a deliberate fail-toward-inaction choice, the same posture the rest of the fencing design already takes when it can't confirm something safely — pausing mutations during a provider-side incident is a smaller risk than continuing to act on unreliable information about which nodes are actually alive.

Every reason a node steps back, and the one reason it gets fenced

These are not the same thing, and it's worth keeping them apart. Stepping back means a node simply stops trying to act as leader for a pass — nothing is powered off, nothing else on the fleet is affected, and the node itself keeps doing every bit of its normal read-only work. Fencing is the one action in this whole system that reaches out and forcibly powers off a different instance. Only one specific situation ever leads to that: the previous leader's lease looks expired, the candidate acting on it is a genuine member of that pool, and the direct liveness check either got no answer or wasn't reachable at all.

The membership check exists to stop a node with no real stake in a pool from acting on its behalf — but a pool with no permanent capacity at all (every node in it elastic, none from a fixed baseline) can, in principle, churn all the way down to zero nodes. One piece of this carries forward past that instant, though: the lease a node writes for itself while winning this bootstrap election stays recognized as legitimate for as long as it holds it, even once the pool has gained its first real member. A bootstrap leader can never retroactively become a "member" of the pool it was elected to fill — by definition, nothing was ever a real member of a pool with zero real members — so if the fencing-target check started treating that same lease as suspicious the moment a real member showed up, the pool would simply trade one permanent deadlock for another: the pool's own brand-new first real node would find itself unable to ever take over from the bootstrap leader whose job was to get it provisioned in the first place. That first real node is exactly who's expected to eventually supersede the bootstrap leader — so its lease keeps being treated as legitimate specifically because of how it was won, independent of whatever the pool's membership looks like by the time someone actually tries to take over from it.

Why checking the named leader's identity matters Every check above assumes the lease record is telling the truth about who it names. In the every-node placement, the credential that writes this record is the same one every node in the pool holds — so a single compromised node, without ever touching the cloud provider's API directly, could write a lease naming a completely unrelated instance elsewhere on your account as "the previous leader," with an already-expired timestamp. Without checking that the named entity is actually a member of this pool, an otherwise perfectly healthy peer would carry out the fencing sequence above against a target it had no business touching — powering off something it was never protecting in the first place. This check closes that gap: before ever probing liveness or asking peers, a candidate first confirms the lease's named leader is a real, currently-known member of the specific pool it's about to act on. A record naming anything else is treated as untrustworthy on sight.

Finding out who's leading right now

Three ways to answer this, in order of how much effort they take:

  1. Ask any node's status endpoint directly. Every instance reports its own view of every pool it participates in — whether leader election is even on for that pool, this node's own id, whether it currently believes itself to be the leader, and the term it holds. Ask every node in a pool the same question and exactly one should answer "yes" at any given moment.
  2. Read it off the monitoring dashboard. The same information already reaches the metrics endpoint every node exposes, labeled by pool and node id — a dashboard panel (or an alert that fires if the fleet-wide sum across a pool is ever anything other than exactly one) needs no extra wiring, since this rides the same scrape path every other fleet metric already uses.
  3. Read the history in the logs. Both of the above tell you the current state; the logs tell you how it got there — every pass logs whether that instance considers itself leader or follower for each pool it manages, and a real handover logs the entire fencing narrative described above, start to finish.

2.5 Credentials

The control plane's cloud API token needs three scopes: read/write on instances, read/write on VPC, and read/write on networking — the last one specifically because buddy IP failover calls the provider's IP-sharing API, and because fencing uses the same instance power-management endpoints already covered by the instance scope.

Secrets are resolved from a narrowly-permissioned local file or an environment variable — never written into the shared, widely-distributed configuration file itself. In the single-host placement, this token lives on exactly one tightly firewalled instance. Once the controller runs on every node, the same token exists everywhere the controller runs — a real increase in how many places a sensitive credential lives, worth weighing deliberately against the single point of failure that placement removes.

A second, separate credential protects the roster API's own mutating routes (drain, and the live-override commands in Part X) — a shared bearer token every instance is generated with automatically at deployment time, resolved the identical way the cloud API token is. Every read from the roster API stays completely open, exactly as it always has — client instances and your monitoring stack never need to authenticate to fetch fleet status. Only the handful of write actions an operator deliberately triggers need it, and an instance with no token configured at all refuses every one of them outright rather than treating that as "no auth needed." See Part X's own operator-CLI section for how to retrieve and use this value from outside the fleet.

Part III

The Data Plane

The pieces that actually touch a customer's packets: the NAT node itself, and the client-side agent that decides which node to send traffic through.

3.1 NAT Nodes

A NAT node is an ordinary compute instance running a kernel-level packet filter and connection tracker (nftables), configured to masquerade — rewrite the source address of — every packet arriving on its VLAN interface out through its public interface. This is the literal thing a customer pictures when they hear "NAT gateway"; every other component in this book exists purely to deploy, scale, secure, or observe a fleet of these.

Nothing about a node's own state is durable. Its connection-tracking table, its firewall counters, and its interface statistics are all in-kernel and rebuilt fresh on every boot from configuration fetched at start time. A broken node is treated as fully disposable — destroyed and replaced by the fleet, never repaired from a backup, because there is nothing on it worth restoring.

What happens if a node stops

With no additional protection layered on, whichever connections were actively flowing through that node at the moment it died are lost — a client detects the loss and reroutes within seconds, but the in-flight TCP state itself is gone. With buddy conntrack sync and BGP IP failover both enabled (Part IV), a meaningful share of that traffic can instead continue through the node's live buddy.

3.2 The Client Routing Agent

A small, dependency-free agent runs on every private-subnet instance that needs NAT egress. It long-polls the roster URL and maintains a resilient multipath ("ECMP") route pointed at every node the control plane currently reports healthy.

Consistent hashing, not round-robin

The nexthop group it installs uses the kernel's resilient hashing mode, which is what gives the system its most important routing property: when a node leaves the healthy set, only the roughly 1/N share of flows that were hashed to that specific node get reshuffled — every other flow, on every other node, is completely undisturbed. A naive route replacement would instead reshuffle every flow on every membership change, resetting far more connections than the actual failure warranted.

Setting the hash policy itself

Getting real distribution out of that mechanism also requires the kernel to hash on enough of each packet to tell separate connections apart. The agent sets this itself at every startup — hashing on source and destination port in addition to the address pair — so that many separate connections to the very same destination spread across the whole pool instead of all landing on one node, the same five-tuple approach used by every hardware router and both hyperscalers' own NAT implementations.

The one thing it manages, and the one thing it never touches

The agent manages exactly one thing: the default route. By default, it installs one only on an instance that has no other path to the internet of its own; an instance that already has a public address or its own NAT path is left completely alone, since something else already owns that route. An operator can override this with the routing script's --force option (Part III, 3.3), which installs and starts the agent — and hands it the default route — regardless of what other path the instance already has, for a deliberate dual-path egress policy where NAT-fleet routing is wanted no matter what else the instance can reach. The agent never touches a VLAN or VPC interface's own connected route either way — those come from the kernel the instant the interface gets an address, independent of anything the agent does.

Fail-safe by design On a roster-fetch failure, the agent keeps its last-known-good membership rather than guessing. If the healthy set it holds ever becomes completely empty, it deliberately leaves the existing route in place rather than tearing egress down — a stale route beats no route at all.

A real constraint worth knowing before relying on --force The routing agent still needs to actually reach the roster URL to do anything, and that endpoint is deliberately scoped to the fleet's own private network — not the public internet. On a "Public + VLAN" instance with no VPC interface of its own, there is no network path to a roster URL given as a private address, and the fetch (or the agent's own later polling) will simply fail. Two ways around this: give the instance a VPC interface too so it has a real path to the control plane, or fetch the agent binary via --artifact-base-url (the object-storage bucket directly, reachable from the public internet) — but the agent still can't build a working route without eventually reaching the roster itself. If it can't, its own fail-safe leaves the existing route alone rather than guessing — a safe failure, but not a working one, so plan the network path before reaching for --force, not after.
Picking the roster URL's address: VPC or VLAN? Which address family to use depends on where the control plane runs (2.3), not on the client. Single dedicated host: the control plane now also carries a VLAN address on the default pool's VLAN — a client on that same VLAN can use it directly, VLAN-only included, with no VPC interface needed. A client on a different VLAN (a dedicated tenant pool with its own, separate VLAN) still needs its own VPC interface and the control plane's VPC private IP instead ("VPC + VLAN" or "VPC (1:1 NAT) + VLAN" above), since the control plane only joins one VLAN. Control plane running on every node: prefer a node's VLAN IP instead, even for a client that also has a VPC interface — every node already answers on VLAN, and VLAN is one flat network with nothing to route, simpler than the VPC path. On that placement, pass every node's VLAN address as one comma-separated --roster-url value rather than just one, for the fail-safe described in 2.2.
A VPC-attached instance now reaches every subnet in its VPC, not just its own A Linode instance's VPC interface only ever gets a kernel route to its own directly-connected subnet — nothing routed it to any other subnet in the same VPC automatically. A client on a different VPC subnet than the fleet's own nodes therefore couldn't reach the control plane's VPC address, even with the firewall correctly scoped to allow it (8.1) — the packet simply had nowhere to go, and fell back to the public interface's default route instead, where it was silently dropped. Every node and the control-plane host now route to every subnet in the environment's VPC automatically, closing this gap — a routing fix only, not a change to what the firewall actually permits.
--vpc-iface: restoring VPC sibling-subnet reachability a "VPC + VLAN" instance had before onboarding For a "VPC + VLAN" instance specifically, the VPC interface was its own default route before onboarding — with no public IP, VPC was its only path out, and that default route gave it real reachability to other subnets in the same VPC (Akamai's VPC fabric forwards a packet between sibling subnets via a plain on-link route through the VPC interface, no gateway address needed). Once onboarding hands the default route to the routing agent for internet egress over the VLAN, that implicit sibling-subnet reachability goes away as a side effect. Pass --vpc-iface <name> to restore it: this tells the routing agent which interface is VPC, and it then adds/removes explicit, non-default routes to whatever VPC subnets the roster reports — self-healing on every roster update, so a subnet added to the VPC later reaches this client automatically, no re-run needed. Never restore this by pointing the default route at the fleet's VPC addresses instead — the NAT nodes' VPC interface is deliberately scoped to connection-state sync only (1.3) and never carries client traffic to the internet, so that breaks internet egress outright.

3.4 Static VLAN Addressing

A VLAN carries no address-assignment mechanism of its own — there is nothing like DHCP running on it. Every address, on every node and every client, is a static assignment applied directly to the interface.

For client instances specifically, the address is chosen and applied entirely by an operator's own provisioning automation, run directly against the already-existing instance — this project provides no tooling or live collision check for that step at all. Whatever automation applies it is fully responsible for confirming the address isn't already in use elsewhere on the segment before applying it.

Rather than reserving a window of address space above wherever the fleet's own nodes happen to end, each pool instead owns a small, dedicated block of VLAN address space — nested inside the VLAN's full range — that only the fleet's own nodes (its scaling capacity, and the control-plane host when it's attached to that same VLAN, 2.3) ever draw an address from. A client address just needs to fall anywhere outside that block. This guarantees the fleet's own automatic address allocation can never wander into space meant for a manually assigned client, even though there is no per-client bookkeeping of which specific address outside that block is actually in use at any moment. Avoiding a collision with another already-assigned client is entirely up to whatever automation applies the address; the dedicated block is what protects against colliding with a future node.

The prefix length matters just as much as the address itself A client's VLAN address must be applied with the SAME prefix length the fleet's own nodes use across the whole VLAN — not just whatever prefix happens to fit the address on its own. Get this wrong (say, a narrower prefix that only covers a small slice of the VLAN) and the failure is silent from the configuration step's own output: the address applies without complaint, the routing agent installs and starts without error, and the client's own default route simply never actually changes to route through the fleet — nothing points back at the real cause. Underneath, the client's own kernel-connected route on its VLAN interface doesn't reach the wider address range a node's own address can live in, so the operating system refuses to route through it at all. The fix is the same address, re-applied with the correct, wider prefix.

4.2 Buddy Pairing: the 2-Node Pair and the 3-Node Triangle

Every reconcile pass, the currently healthy node set is sorted deterministically and paired up two at a time. With an even number of nodes, this produces exactly what it sounds like: ordinary mutual pairs, each member backing up the other. An odd number of nodes is where the interesting behavior lives.

The ordinary pair

Two nodes, A and B. Each independently: (1) announces its own public IP as primary, (2) stands ready to take over the other's IP as secondary, and (3) mirrors connection-tracking state with the other. This relationship is fully symmetric and fully bidirectional — there is no primary/backup role assigned to either member; both are simultaneously each.

The 3-node triangle

With three or more nodes and an odd count, the trailing three nodes — call them A, B, and C in sorted order — form a triangle instead of leaving one node with no partner at all:

  • A and B form a completely ordinary mutual pair, exactly as above.
  • B — the "hub" — additionally takes on C as a one-directional backup: B is ready to announce C's public IP and mirrors C's connection state, but the reverse is not true. C does not back up B, and does not back up anyone.

Every node in the pool ends up with at least one live backup this way — nobody is left fully exposed just because the pool's node count happens to be odd.

Why the hub relationship is directional for IP failover, but not for state sync

These are two different underlying constraints, and the triangle handles them differently on purpose:

  • IP failover is governed by the cloud provider's own IP-sharing rule: two different nodes may never both claim to be the secondary announcer for the same primary address — but nothing stops a single node from being the secondary for two different primaries at once. The triangle exploits exactly that: B can legitimately back up both A's and C's addresses simultaneously, while C backs up no one. This relationship stays directional by design.
  • Connection-state sync needs a real, two-way relationship on both ends — each side runs its own sync process pointed at the other, and either side may need the other's mirrored state at any moment. So for state sync specifically, the same underlying triangle shape is symmetrized: C also gets a real, live sync relationship pointed back at B. The hub node ends up running two completely independent, simultaneous sync processes — one per peer, each with its own configuration, lock, and control socket — while the odd node out ends up with exactly one real peer instead of none at all.

What happens as the pool scales

Pairings are recomputed from the current healthy node set on every single pass — deliberately simple rather than sticky or consistent-hashed, since a buddy resync only costs a few seconds of state-sync freshness for the affected nodes, not a routing disruption for every in-flight flow the way a client-facing membership change would.

4.3 Connection-State Sync

A daemon called buddy-sync (lng-buddy-sync.service) runs on every node, watching the roster for buddy reassignment and reconciling both the BGP announcer's secondary-route configuration and the connection-tracking sync process's peer configuration whenever a pairing changes.

While active, it continuously mirrors the node's live kernel connection-tracking table to its current peer or peers — usually one, two for a triangle's hub node running two independent sync processes at once.

The protocol, concretely

The actual state-mirroring is done by conntrackd, a standard Linux connection-tracking sync daemon — UDP, over the node's private VPC interface (eth1), one independent process per peer relationship (a triangle's hub runs two at once). Each relationship's exact port is derived deterministically from a base of 3780 plus a hash of the two peers' node IDs, so both ends always agree on the same port without needing to coordinate it. Each relationship runs as its own systemd instance, conntrackd@<peer-node-id>.service — systemctl list-units 'conntrackd@*' on any node shows every currently active relationship.

Where to check buddy health

The Grafana dashboard's buddy-pairing panel (Part VII, 7.3) shows paired-node coverage across the whole fleet at a glance. On a specific node, systemctl status lng-buddy-sync shows the daemon itself, and systemctl status conntrackd@<peer-node-id> shows one specific peer relationship; journalctl -u lng-buddy-sync -f logs every roster poll and every peer change live.

What happens if it stops

A node with no active sync peer is still completely healthy and still fully participating in ECMP rotation — this is a session-continuity mitigation, not a health signal, and should never be treated as equivalent to a node being down. The only practical consequence of losing sync is that a future failure of that specific node will reset in-flight connections outright instead of possibly continuing through a buddy that had a mirrored copy of the state.

How to restart it

systemctl restart lng-buddy-sync on the affected node. It carries no state of its own worth preserving — on restart, it re-derives its current peer assignment fresh from the roster on its very next check and re-establishes sync from there (each individual conntrackd@<peer> process is started and stopped automatically by buddy-sync itself as peers come and go — there's normally no reason to touch those directly). There is nothing to migrate and no manual reconciliation step.

What it stores

Only its own regenerable configuration — the BGP announcer's running configuration is rewritten on every pairing change, and a small status file exists purely for observability and is never read back by anything. The actual mirrored connection-tracking table lives only in kernel memory on both ends and is never written to disk anywhere.

4.4 BGP-Based IP Failover

A BGP routing daemon called FRR (frr.service) runs on every node, paired with the cloud provider's own IP-Sharing capability — together, this is what actually lets a buddy take over a dead node's public IP, not just its connection state.

The mechanism

From the moment it boots, every paired node is simultaneously doing two things: announcing its own public IP as the primary route, and — once buddy-paired — announcing its buddy's/buddies' public IP(s) as a secondary backup route. This is fully bidirectional and active from boot, not something that only activates once a failure is detected.

Two independent conditions must both clear before the cloud provider's IP-sharing API is actually called for a brand-new pairing: a short activation delay since the pairing itself was computed, and the announcing node's own BGP session having stayed continuously established for at least a minimum age. The first guards against granting the share before the node-side agent has had time to configure its own secondary announcement; the second guards against a subtler case — a node whose BGP session has only just come up (a reboot, a daemon restart, a route-reflector flap) can pass the first check instantly if the pairing itself is old, announcing a backup role before Akamai's route reflectors have had time to trust that session. A route reflector that hasn't yet trusted a freshly-established session can silently drop early announcements from it, so a backup role announced before that trust window closes risks not actually reaching the wider fabric — gating on measured session age, not just elapsed time since pairing, is what closes that gap.

What happens when a node dies

Its buddy's already-standing secondary announcement is what lets traffic addressed to the dead node's public IP keep reaching a live host — typically within a single BGP convergence cycle, since the backup route is already active rather than something that has to be established after the fact. Any TCP connection that was actively open through the dead node at the moment it died still resets; that is connection-state loss, a separate concern that only connection-state sync (previous chapter) addresses.

How to restart it

systemctl restart frr on the affected node is enough — its own self-announcement resumes automatically at boot with no manual step, and its buddy assignment is entirely independent of the daemon's own lifecycle, since that assignment is recomputed by the control plane, not stored locally. Check current session state with vtysh -c "show bgp summary" on the node itself.

Operational caution Changing a node's BGP router identity while sessions are already established forces a full session reset on every peer. The router identity is set once, at boot, and is never touched again during normal operation — there is no supported reason to change it live.

4.5 Anti-Affinity Placement

Buddy sync and BGP failover both assume the two members of a pair can actually fail independently. If both happen to land on the same underlying physical host, that assumption breaks — a single physical-host failure takes out an entire buddy relationship at once, with nothing left to fail over to.

Placement groups spread a pool's nodes across separate physical hosts to close exactly this gap. This is safe to turn on for an already-running pool without replacing a single node — existing nodes are simply updated in place to join a group. A pool larger than one group's node cap is split into multiple contiguous groups; this leaves one honest, structural residual gap: a buddy pair that happens to straddle the boundary between two groups gets no anti-affinity protection from each other, since group boundaries are drawn by creation order, not by buddy-pairing awareness. This is a deliberate trade-off that minimizes rather than eliminates that specific exposure, not an oversight.

4.6 Reserved (Sticky) Public IPs

By default, a replaced node comes back with a brand-new, ephemeral public address. For a deployment whose downstream partners whitelist specific IPs, that churn is unacceptable — reserved IPs fix a node's primary public address to one that survives instance replacement.

When a node backed by elastic (automatically provisioned) capacity is removed, its reserved address is deliberately not released — it stays reserved but idle, and the next node the pool provisions reuses it instead of minting a fresh one. Over a pool's lifetime this settles into a small, stable address set bounded by the pool's maximum elastic size, not by however many replacements have happened — exactly the stability a downstream whitelist needs. A durable per-pool ownership record is what makes reuse provably safe rather than a guess based on "currently unattached," since an unattached address elsewhere on the same account could easily belong to something unrelated.

4.7 Handling a Persistently Unhealthy Node

The count that actually matters against a pool's minimum node requirement is the number of currently healthy nodes, never the raw node count — a node that exists but is failing its own health check does not count toward satisfying the floor.

An elastic node that stays unhealthy past a configured threshold is drained and replaced automatically, with no human intervention required. A Terraform-managed floor node is treated completely differently and deliberately never auto-replaced under any circumstance — instead, the system compensates by provisioning additional elastic capacity to make up for the lost floor capacity, while leaving the actual broken floor node for an operator to investigate and fix by hand. This is a hard safety boundary, not an inconsistency: an automated system should never delete infrastructure a human explicitly declared should always exist.

4.8 The Trade-Off This Design Accepts

Worth stating plainly rather than glossing over: the active-active model trades away the simplicity of a fixed master/standby pair — where one continuously mirrored relationship gives genuinely zero session loss on failover — in exchange for horizontal scaling and full utilization, with no idle standby capacity sitting around unused.

Buddy connection-state sync combined with bidirectional BGP IP failover (this Part) narrows that gap substantially — a buddy takes over both a dead node's connection state and its public identity, in both directions of every pairing. It remains, honestly, a mitigation rather than an absolute guarantee: propagation carries real if small lag, and a genuinely correlated failure of both members of a pair at once has nothing left to fail over to unless anti-affinity placement (4.5) is also in use. A workload that truly cannot tolerate any connection reset under any circumstance at all has a real reason to weigh a simpler, pair-based model's stronger session-loss guarantee against this design's better scaling and utilization — they are optimized for different priorities, and that trade-off deserves to be made deliberately rather than assumed away.

5.2 The Autoscaling Algorithm

Every reconcile pass, four independent capacity signals are checked. Any single one crossing its line is enough to trigger a scaling evaluation — a single exhausted resource degrades real traffic regardless of what the others look like.

SignalScale-out triggerMeaning
Connection-tracking utilization≥ 70%The node's fixed-size connection table is nearly full — past 100%, new connections start failing outright.
Port headroom≤ 15%Fewer than 15% of usable source ports per destination remain free. Note the direction — low is the bad reading here, the mirror image of the others.
Throughput ratio≥ 85%The node is using 85% of its real, measured network bandwidth ceiling for its specific instance plan.
CPU / softirq ratio≥ 80%The single busiest CPU core, anywhere in the pool, is spending 80%+ of its time on network packet-processing work — catches packet-rate-driven saturation neither of the other signals sees coming.

Why CPU/softirq gets its own signal

A NAT gateway is fundamentally network-I/O-bound, and the busiest-core reading is deliberately not an average across cores or nodes. Which CPU core handles a given network card's packets is generally fixed by interrupt/queue affinity, not the ordinary process scheduler — so a flood of small packets can pin one specific core near 100% while every other core, on that node and every other node in the pool, sits comfortably idle. A node in that state can look completely healthy on connection-tracking, port usage, and even total throughput in bytes per second, while its actual packet-forwarding capacity is already maxed out. Averaging across cores or nodes would wash that signal out entirely; taking the single worst core anywhere in the pool is what actually catches it. This trigger only ever adds capacity — unlike connection-tracking utilization, it has no low-watermark side and never independently drives scale-in, since a quiet core for a pass or two is a much weaker signal that it's safe to shrink the pool than a sustained drop in connection count is.

The sizing formula

Required Capacity  =  Current Capacity  ×  (Current Metric ÷ Target Metric)

The whether-to-trigger decision uses the single worst node in the pool. The how-big-an-action decision, once triggered, uses the pool-wide aggregate instead — sizing off one hot node alone would over-provision for what might really be an uneven distribution problem on a single node rather than a genuine pool-wide shortfall.

Two guards against an overcorrection

  • Sustained-breach window. A metric has to stay past its threshold across two consecutive passes before it's trusted enough to size an action on — one noisy reading only starts a counter, it never triggers an action by itself.
  • Maximum step size. Even once trusted, a single scale-out action is capped at doubling current capacity, and a single scale-in action is capped at removing half of current elastic capacity — deliberately more conservative in the remove-capacity direction, since draining a node that turns out to still be needed is a worse mistake than a slightly slow scale-out. A formula result larger than the cap is fulfilled gradually, over more than one cycle, instead of taken in a single uncontrolled jump.

A cooldown period after every scaling action, independent of both guards above, blocks re-evaluation entirely for a while — giving freshly added capacity real time to start absorbing load before the next decision is made.

max_nodes as a true ceiling, not just a guardrail

Every reconcile pass also checks whether the pool's actual total node count is already above max_nodes — not just whether a scale-out would cross it. If it is, excess elastic capacity is drained back down immediately, regardless of cooldown or current demand, rather than waiting for a low-utilization reading to eventually correct it on its own. This covers a node count ending up above the ceiling for reasons that have nothing to do with load — most commonly, lowering max_nodes itself below the pool's current size via set-pool-scaling (10.2). That correction is a configuration-ceiling fix, not a scaling decision, so none of the guards above apply to it. Floor nodes are never touched this way — if floor nodes alone already meet or exceed max_nodes, only a terraform apply can resolve that.

A scale-out, start to finish

A pool at two nodes sees connection-tracking utilization spike to 90% on its hottest node. That single reading isn't enough on its own — the sustained-breach counter only reaches one. The load persists on the next pass; the counter is now satisfied, and the pool-wide aggregate works out to 85%. Against a 50% target, the formula computes 2 × (0.85 ÷ 0.50) = 3.4, rounded up to 4 nodes — a delta of two, which the doubling cap comfortably allows in one action. Two new nodes are provisioned in that single decision rather than two separate five-minute cycles of one node each. Cooldown then blocks any further evaluation while the new capacity boots, passes its own health checks, and starts absorbing real traffic.

Real capacity, not an assumption

The throughput signal is measured against the real, published network capacity of whichever instance plan the pool actually runs — looked up directly from the cloud provider rather than hardcoded, and cached since a plan's specification is effectively static. If that lookup itself ever fails, the fallback assumes a conservative, lower capacity figure rather than a generous one — a failure here makes the system slightly more eager to scale out, never blind to a real shortage.

5.3 Right-Sizing: Instance Types and Node Count

When in doubt, prefer more nodes over bigger ones. The active-active model makes horizontal growth genuinely cheap — there's no coordination overhead the way there would be with a fixed pair, where adding capacity meant standing up a whole new pair.

Sizing the connection-tracking table

nf_conntrack_max  ≥  1.3 × expected peak concurrent connections per node

The 30% headroom above the expected peak is what keeps a normal traffic spike from ever reaching the hard connection-tracking ceiling before the autoscaler has a chance to react.

Sizing for port exhaustion

Every public IP supports roughly 55,000 simultaneous connections to any single destination — the same structural ceiling AWS documents for its own NAT Gateway. A node can hold more than one public egress IP specifically to multiply this ceiling; only a node's primary address participates in IP failover, so additional addresses are a straightforward per-node allocation with no shared-failover behavior of their own.

Estimating the node count you actually need

Calculate two independent numbers and take the larger one as your floor:

  • Throughput-bound: peak aggregate expected traffic, divided by one node's real, published network-out capacity for the instance plan you intend to run.
  • Connection-bound: peak aggregate expected concurrent connections, divided by (per-node conntrack ceiling × 0.70) — the trigger threshold, not the raw maximum, since you want headroom before the alarm fires, not right up against it.

Add at least one extra node beyond that calculated minimum so that a single node's failure doesn't itself immediately push the pool over its own scale-out trigger.

Choosing an instance plan

Dedicated-CPU compute plans on Akamai Cloud scale up to roughly 40 Gbps inbound and 12 Gbps outbound per instance at the top end — a mid-tier dedicated-CPU plan is a reasonable, realistic default for a genuine production NAT node rather than the smallest available size, since a NAT gateway is fundamentally a networking-bound workload, not a compute-bound one. The system itself never guesses at a plan's real capacity — it queries the provider's own instance-type data directly, so whatever plan is actually chosen is what the autoscaling formula sizes against, not an assumption baked in ahead of time.

5.4 Vertical Scaling

Changing a node's instance plan — up or down — is always a deliberate, operator-initiated action naming one or more specific nodes by identifier; nothing in the system ever decides on its own that a node's size, as opposed to the pool's node count, should change.

What happens, step by step

  1. A disk-fit check runs first, before ever calling the resize API — comparing the target plan's disk allowance against the node's actual allocated disk. If it won't fit, nothing risky is attempted: the operator gets the exact manual remediation steps instead of a surprise mid-resize failure.
  2. The node is drained — excluded from the roster immediately, with existing connections given time to empty out naturally.
  3. A warm resize is attempted first (the instance stays up during migration, then reboots once complete) — automatically falling back to a cold resize if the provider rejects the warm attempt.
  4. The controller polls until the instance is confirmed running again, then un-drains it — it rejoins the roster once its own health checks pass, exactly like any node recovering from a transient failure.

Multiple named nodes are always processed one at a time, never in parallel, and the whole operation stops at the first node that fails rather than continuing to remove capacity from an already-short pool. A resized floor node needs a matching, explicit override recorded in the infrastructure-as-code configuration so a future apply doesn't silently revert the resize; an elastic node needs no such step, since it was never declared there to begin with.

5.5 Multi-Tenant Pools

A pool is the unit of both scaling and isolation. A tenant that needs guaranteed, isolated capacity — rather than sharing the default pool with everyone else — gets its own dedicated pool: its own VLAN, its own independent minimum/maximum bounds, completely isolated traffic, built from exactly the same mechanism as the shared pool, just under a different name.

6.2 Fetched-at-Boot Artifacts

A cloud provider's own boot-time configuration payload — the data handed to a fresh instance the moment it boots, sometimes called "user data" or "cloud-init" — has a hard, fixed size ceiling: 16,384 bytes, decoded. This project's own agent source code, on its own, already exceeds a meaningful fraction of that ceiling before a single optional feature is even turned on — the metrics exporter alone is around 32KB, the connection-sync daemon around 30KB, and the full control-plane package around 230KB. None of that fits inside a 16KB budget no matter how it's arranged.

What this actually is, concretely

Every file that's identical across every node — the metrics exporter, the connection-sync daemon, and the control-plane package itself — is uploaded to Object Storage exactly once per deployment, as a plain, public-read file, and re-uploaded automatically only when its actual content changes (so a redeploy that changes nothing skips the upload entirely). Instead of that content being embedded in a node's boot payload, the boot payload just contains one line telling the node where to fetch it from — something like:

curl -fsSL https://lng-artifacts.us-east-1.linodeobjects.com/lng-artifacts/exporter.py -o /opt/lng/exporter.py

Every node runs that same curl command at boot, for each of the shared files it needs, and only then starts the corresponding service. The boot payload itself shrinks from "the whole file" to "one short line," which is what actually solves the size problem.

Why public, not signed

These specific files — the exporter, the sync daemon, the control-plane package — never contain secrets. Actual secrets (API tokens, passwords) are always handled a completely different way: written directly into a small, narrowly-permissioned file on the node itself at boot, never uploaded anywhere. So making these particular files public-read isn't a security trade-off — it's what avoids a real practical problem: fetching a private file from Object Storage normally requires a signing client (credentials, a signature calculation) already installed on the machine doing the fetching. A brand-new, bare cloud image doesn't have that installed yet, and installing it just to pull the project's own non-secret source code would be extra complexity for no real security benefit — a plain public URL and a plain curl, as shown above, is the simplest thing that actually works on a fresh image.

What's compressed instead of uploaded separately

Not every file can go through this shared-upload path — some content is different for every single node and can't be uploaded once and reused. The clearest example is each node's own firewall ruleset: it embeds that node's own specific addresses, so node A's ruleset isn't node B's ruleset. Content like that has to stay directly inside that one node's own boot payload rather than being fetched from a shared file. To keep it from blowing the same 16KB budget, it's compressed (gzip) before being embedded — cloud-init already knows how to transparently decompress gzip'd boot payloads, so nothing extra needs to run on the node to unpack it. Compression alone shrinks a typical per-node configuration file dramatically (plain text compresses very well), which is normally enough to fit it comfortably inside the remaining budget after the shared files above have already been moved out.

How a node knows the fetched content wasn't tampered with

A plain curl to a public URL, on its own, only guarantees the connection itself was secure (HTTPS) — it says nothing about whether the file at that URL is genuinely the one this deployment's own infrastructure code actually uploaded. So every node fetches one more small file first — a short list mapping each shared file's name to a cryptographic fingerprint (SHA-256) of what that file's contents are supposed to be, computed directly from your own infrastructure code's local copy at deploy time, never from anything fetched over the network. Before running or installing anything it fetches, a node computes the same kind of fingerprint over what it actually downloaded and compares the two. A mismatch means the fetched content isn't what your own deployment produced, whatever the reason — and the node refuses to proceed rather than run something it can't verify. This check doesn't cover your dashboard's own definition file (it's data your monitoring tool renders, not something that runs), or each node's own firewall ruleset (unique per node, with nothing shared to check it against).

What happens if a node is missing a file it now needs

The list of shared files above is fixed into a node's boot payload the moment that node is created — it reflects whatever your infrastructure code's own file set looked like at that specific apply. An already-running node's boot-time list never updates itself after the fact; it's frozen at creation time. Normally that's fine, since the control plane also re-checks this same shared file set on every restart, independent of how it originally booted — but that re-check itself lives inside the control-plane package, so it can only run once the control plane has actually started.

To close that gap, the control plane's own startup sequence runs one small, separate step immediately before the control-plane process itself starts: it reads the current shared-file list straight out of the node's own configuration and fetches (through the exact same public-URL-plus-fingerprint path described above) anything on that list that isn't present on disk yet — before the control-plane process ever gets a chance to need it. A node whose original boot-time list predates a file the control plane now expects self-heals this way on its very next restart, with no manual fix and no need to recreate the node. If a fetch genuinely can't complete (a network problem, for instance), this step simply leaves that file missing and moves on — the control plane then fails to start exactly as it always would in that situation, and retries automatically a few seconds later, trying the fetch again each time.

6.3 The Leader-Election Lease

Only relevant when the control plane runs on every node: a small record naming the current leader, its term, and an expiry, readable by every controller instance. As covered in Part II, this record is a best-effort coordination hint, never the actual safety mechanism — that role belongs entirely to fencing. Losing this record costs, at most, one election cycle; it never represents a safety violation on its own.

6.4 Reserved-IP and Live Configuration Manifests

A pool's reserved-IP ownership manifest is a durable, per-pool list of every address that pool has ever reserved — the only thing that makes address reuse across node replacements provably safe rather than a guess, since an address being merely "unattached" says nothing about whether it actually belongs to this pool or to something completely unrelated sitting idle on the same account.

A separate, small live-configuration object lets an operator change certain operational behavior instantly and durably, with every connected client and every controller instance picking up the change within one round trip and with zero restarts required anywhere in the fleet. Four settings work this way today: whether client instances should also independently double-check node health rather than trusting the control plane's computed view alone; a pool's elastic min_nodes/max_nodes bounds; the whole-environment list of sibling VPC subnets a node needs an explicit route to (Part I, 1.2); and, per pool, static routes to a customer-operated IPsec/VPN gateway on that pool's own VLAN (10.2's list/add/remove/set-ipsec-routes). All four are also written by Terraform on every apply — whichever wrote most recently is what's actually in effect, and Terraform's own value always wins again on the next apply. See Part X, 10.2's set-client-config/set-pool-scaling/set-vpc-sibling-subnets/*-ipsec-routes for the live-override side of this.

7.5 What the Health Check Actually Verifies

Every node's own health endpoint runs a genuine end-to-end check every single time it's called, not a cached result: IP forwarding is confirmed enabled, the NAT ruleset's own specific expected rules are confirmed present in the node's live table — not just that the table object itself exists, which stays true even after every chain, rule, and counter inside it has been stripped out by something external — and, the check that actually matters most, a real outbound request is sent out through the node's own public interface and its success is confirmed.

That last check is what makes both client routing decisions and the fleet's roster genuinely trustworthy. A node can be perfectly reachable on the network while its NAT path is quietly broken underneath — a plain reachability check would completely miss that; only an actual end-to-end request catches it. The per-check breakdown metric exposes exactly which individual check failed, so a diagnosis never requires logging into the node itself.

This check answers "can this node forward and NAT traffic," not "is it doing so right now" — a node with no clients currently sending it traffic passes every check above correctly, since nothing about its own configuration is broken. nftables_accepts_total (7.2) is the metric for that separate question: a sustained zero rate on a node that's supposed to be carrying real traffic is genuine evidence something is wrong, distinct from this endpoint's own verdict.

Security

8.1 The Firewall Model

Every node's public and VPC interfaces sit behind a default-deny cloud firewall — inbound_policy = DROP as the catch-all, with only the specific ports below explicitly allowed. Nodes never accept an inbound connection initiated from the internet at all; NAT and forwarding are unidirectional by construction, not merely by firewall policy. Outbound traffic is unrestricted from every node (outbound_policy = ACCEPT) — nothing here limits what a node itself can reach.

The VLAN interface is handled completely differently, because the cloud provider's own firewall layer never inspects VLAN traffic at all — it simply isn't in that path. The node's own local packet-filter ruleset (nftables, not the cloud firewall) is the entire security boundary for VLAN traffic instead, and it's written accordingly: it keeps the metrics port open there (client instances need to reach it) while explicitly excluding administrative access from that interface.

Whatever you change, re-run terraform plan first and read it — a firewall rule is exactly the kind of change worth reviewing before it goes live.

8.2 Credential Scope

The control plane's own cloud API token needs exactly three scopes — read/write on instances, read/write on VPC, and read/write on networking — and nothing broader. The networking scope specifically is what allows both BGP IP-sharing calls and the fencing mechanism's instance power-management calls; no additional scope beyond it is required for fencing.

The client routing agent needs one elevated local capability on the instance it runs on — the ability to manage the kernel's own routing table — and nothing else; it never needs any cloud API credential of its own at all.

8.3 Secrets Management (SOPS + age)

Every real secret this project handles — the cloud API token, the instance root password, the Object Storage key pair, the Grafana admin password — is encrypted at rest with SOPS and age, a modern, widely-adopted, purpose-built pair for exactly this problem. Nothing about this requires standing up or operating a separate secrets-management service, a database, or an always-on process — the encrypted file is just a file, committed alongside the rest of this environment's Terraform, and decryption happens only at the two specific moments something actually needs the plaintext.

Two independent layers exist, solving two different problems, using two different keypairs. Layer 1 protects secrets between the moment they're written and the moment terraform apply runs. Layer 2 protects the same secrets between the moment they reach a running fleet and the moment natctl actually uses them. Confusing the two — or their keypairs — is the one mistake worth actively avoiding; the rest of this section keeps them clearly separated throughout.

Layer 1 — Terraform-time: secrets.enc.json

What's stored, and where. terraform/environments/example/secrets.enc.json holds every Terraform-level secret — the cloud API token, root password, Grafana admin password, Object Storage key pair — as individually-encrypted JSON fields, plus (once Layer 2 below is turned on) the Layer-2 bundle's own private key. The file lives in the repository, committed like any other source file. This is safe specifically because of what "individually-encrypted" means: every value is ciphertext (SOPS's own ENC[AES256_GCM,...] format), decryptable only by the holder of a matching age private key. Reading the raw file — in the repository, in a diff, in a code review — shows only that ciphertext, never a real value.

How retrieval and decryption actually happen. Terraform reads the file directly at plan/apply time through the sops Terraform provider (data "sops_file" "secrets" in main.tf). That provider does the decryption itself, in memory, inside Terraform's own process — the plaintext value is never written to a temporary file, never passed through a shell command, and never appears in terraform plan/apply output, the same treatment any variable marked sensitive already gets. The decrypted values are exposed to the rest of the Terraform configuration as ordinary local values (local.linode_token, local.root_pass, and so on) and flow from there into whichever resource needs them, exactly as a plain variable would have before.

Decryption key and who can hold it. The decrypting key is an age keypair generated by whoever operates this deployment — the private half stays on that operator's own machine (or wherever terraform apply actually runs from) and is never itself committed; the public half is the only thing recorded in the repository (.sops.yaml), since a public key carries no risk in being visible. Multiple operators can each hold their own keypair — .sops.yaml lists every public key allowed to decrypt the file, and adding a new operator re-wraps the same underlying data key for their public key without touching or re-encrypting any individual secret value.

Editing a value. Running sops secrets.enc.json (with the operator's own private key available) decrypts the whole file to a scratch buffer in the operator's editor, lets them change whatever field needs changing, and re-encrypts the entire file back to disk on save — the plaintext exists only transiently, in the editor process's own memory, never written anywhere unencrypted.

Layer 2 — Runtime: the secrets bundle

The problem this layer solves. natctl needs these same credentials at its own process startup, on every node it runs on — not just once, at Terraform apply time, on the machine running Terraform. Writing them to a plaintext file on every node's disk (/etc/natctl/env, the long-standing, still-fully-supported mechanism) is itself a real, auditable exposure: a plaintext file readable by anything running as root on that node is a different — and, on a fleet of many nodes, wider — risk surface than one encrypted file on one operator's machine. Layer 2 is opt-in (off by default, secrets_bundle_url empty) and shrinks that on-node exposure to the smallest thing that can possibly work.

Storage: what actually gets published, and where. An operator builds one bundle — a single JSON object containing every credential natctl needs, in plaintext at the moment it's assembled — and immediately re-encrypts that whole object as one age-encrypted binary blob (not SOPS's own per-field format; a plain, whole-file age --encrypt). That blob is uploaded to Object Storage as a public-read object. Public-read sounds alarming for something with "secrets" in the name, until the actual content is considered: it's ciphertext, indistinguishable from random bytes to anyone without the matching private key. This mirrors the exact trust model this project already uses for every other fetched-at-boot artifact (Part VI) — public readability was never the security boundary for those either; possession of the right key (or, for those artifacts, matching the right hash) is.

Retrieval — the runtime query mechanism. natctl fetches this bundle with one plain HTTP(S) GET, at process startup, before it does anything else — before it even finishes parsing its own configuration file. This is a one-shot read, not a poll: the bundle is fetched once when the process starts and never re-fetched while that process keeps running. A value that changes after a process has already started (a rotated credential, a freshly built bundle) only takes effect the next time that specific natctl process restarts — the identical "read once at startup" behavior almost every other part of this project's own configuration already has.

The decrypt step, in detail. Once the ciphertext blob is in memory, natctl decrypts it by invoking the age command-line tool directly (a subprocess call, not a new library dependency — every node already needs the age binary present) and pointing it at one local file: this node's own age private key. That decrypted plaintext — the JSON object an operator assembled at build time — is parsed and applied straight into this process's own environment variables, immediately, with no intermediate file ever written to disk. Every existing credential-resolution path in the codebase (an explicit configuration field, an environment variable, the plaintext /etc/natctl/env file) keeps working completely unchanged; this bundle is simply one more, earlier source for the same environment variables those paths already read. A value already present in the environment is never overwritten by the bundle — this is what lets a single credential be overridden locally, on one node, without touching or rebuilding the published bundle at all.

The one piece of secret material a node still needs on disk, and why it's different from what came before. Decrypting the bundle requires an age private key, and that key has to live somewhere a fresh node can read it at boot — there's no way around a node needing some local secret to bootstrap trust in anything fetched over the network. What changed is the shape and scope of that one remaining secret: instead of every real credential sitting in one plaintext file, exactly one small, narrowly-scoped key sits there — a key that can decrypt nothing except this one bundle, and is otherwise completely inert. This is a deliberate, honestly-stated trade-off, not a claim that on-disk secret material has been eliminated: it's reduced from "every credential, directly usable" to "one minimal key, useless for anything else."

Which servers actually run this, and how it behaves across the whole fleet. Every instance that runs natctl at all gets this same treatment identically: every floor node and the quorum-witness instance (when natctl_on_node_enabled is true), the single dedicated control-plane host (when it's false), and every elastic node natctl itself later provisions. An instance that never runs natctl — a plain private-subnet client, a customer's own IPsec gateway — never receives this key at all, because there's nothing on it that would ever need to decrypt anything.

High availability and node churn. Because every node that needs this key gets the exact same one (not a per-node unique key), replacing any single node is a non-event for this mechanism: a Terraform-recreated floor node or witness receives the identical key on its next apply, the same way it always has; a fresh elastic node natctl provisions on the fly receives a byte-for-byte copy of the SAME key the provisioning node itself already holds, copied forward automatically as part of that node's own creation — no separate key-distribution step, no coordination between nodes, and no single point of failure in the key material itself, since every node that has it has the complete, independently-usable copy. Losing any one node — even the one that most recently provisioned others — has no effect on any other node's ability to decrypt the bundle; each one carries its own working copy.

Rotating a secret once this is live. Update the value at Layer 1 (the encrypted secrets.enc.json), rebuild the bundle from the new plaintext, re-publish it to the same URL, then restart natctl on whichever nodes should pick up the change — a rolling, one-node-at-a-time restart if the fleet should never have every node simultaneously restarting, or a fleet-wide restart if it should. Nothing about rotation requires touching any node's own on-disk age key; only the bundle's content changes.

Failure behavior. Any failure in this whole chain — the bundle can't be fetched, the local key is missing, decryption fails, the result isn't valid JSON — is treated as "this optional, additional credential source didn't work" rather than a fatal startup error: natctl logs the failure and continues starting up exactly as it would have if this mechanism didn't exist, falling through to every other credential source already in place. If the environment genuinely ends up with no usable credentials from any source, the existing, unrelated "no API token configured" startup check is what catches that — this mechanism doesn't duplicate or bypass it.

What this explicitly does not close. A cloud provider's own API token — the one used to create an instance in the first place — can always read back that instance's own boot-time configuration for as long as the instance exists; this is a property of the cloud platform's own metadata service, unrelated to anything either encryption layer here does, and neither layer claims to address it.

9.3 Deployment Sequence

  1. Provision the fleet: the floor nodes for each pool, the control-plane host (or, if the every-node placement is chosen, nothing dedicated at all), and the two firewalls covering the node and control-plane traffic.
  2. Confirm the fleet is healthy: every floor node passes its own health check and appears in the roster with a healthy status.
  3. Install the routing agent on every private-subnet instance that needs egress, pointed at the pool's roster URL.
  4. Open the monitoring dashboard and confirm every node is reporting metrics and showing healthy.

9.4 Onboarding a Client Instance

Once a private instance exists, has its VLAN interface attached at the account level, and has a real static VLAN address applied by your own automation (this project provides no tooling for that step, see 3.4), a single configuration step against that instance finishes the job: it verifies the address is really there, installs and starts the routing agent only if the instance genuinely needs one, and points it at the correct pool's roster URL. The instance is now a fully participating client, spreading its egress traffic across every currently healthy node in that pool.

If the instance has no internet path of its own and you don't already have a copy of the configuration script on hand, fetch it directly from the control plane instead of copying it over separately — it's served the same way the compiled routing agent itself is, over the fleet's own private network: curl -fsSL http://<roster-host>:8099/agents/install-nat-client.sh -o install-nat-client.sh.

This project also creates a purpose-built, SSH-only firewall specifically for client instances — attach it to whatever your own automation creates, via the client_firewall_id Terraform output (terraform output client_firewall_id).

Day-2 Operations

The checklist worth reviewing before calling a deployment production-ready, the procedures for the operational tasks that come up routinely, and where to look first when something looks wrong.

10.1 Pre-Production Checklist

  • Metrics are being scraped from every node, the dashboard is loaded, and alert rules are active.
  • The control plane is running with a valid, correctly scoped API token.
  • Every private-subnet instance that needs egress has a healthy routing agent installed.
  • Minimum/maximum node bounds are reviewed per pool — these are the real safety limits on automatic scaling, not defaults to leave unexamined.
  • The connection-tracking table size is sized against expected peak concurrent connections per node.
  • Firewall rules are reviewed: default-deny confirmed, only documented ports open — remembering the cloud firewall never covers VLAN traffic, only the node's own local ruleset does.
  • If buddy sync is wanted, the roster URL configuration matches consistently everywhere it's referenced; if it isn't wanted, it's left empty everywhere so the sync daemon is never installed at all.
  • The unhealthy-node replacement threshold is reviewed per pool — the default is a reasonable starting point, not something to leave unexamined for a workload sensitive to brief capacity dips.
  • If BGP IP failover is enabled, the correct BGP data-center identifier is confirmed for the region, and automatic IP-share configuration is left on unless there's a specific reason to run the first pairing by hand.
  • Every manually assigned client address falls inside its pool's reserved window and was applied through the configuration script's duplicate-address safety check, never picked and applied blind.
  • Anti-affinity placement is considered for any pool where a correlated physical-host failure taking out a whole buddy pair is a real, meaningful concern.
  • If reserved IPs are in use and addresses already exist from a prior deployment, they're handed to the pool explicitly rather than letting it mint entirely new ones.
  • Terraform state uses a remote backend with locking (backend.tf.example, an S3-compatible Object Storage bucket with native lockfile support) if more than one operator, or one operator with more than one open session, will ever run terraform apply against this environment — a fresh checkout otherwise uses a local state file with no locking at all, so two concurrent applies have nothing stopping them from corrupting state or double-provisioning.

10.2 The Operator CLI (natctl-cli)

Every command below is a real, complete invocation against a live deployment — not a paraphrase. This is the tool for day-2 questions and actions the dashboard can show you but can't take for you.

What it is, and why it's a separate binary from the daemon

natctl itself (Part II, 2.1) is a long-running daemon — it never takes commands, it just runs its reconcile loop forever, on its own, from the moment it starts. natctl-cli is a completely separate program: a one-shot tool an operator runs by hand, once, to ask a question or take a single action, then exits. Both are built from the same underlying fleet-management logic, so what natctl-cli status reports is exactly what the daemon itself currently believes — it's not a second, independent source of truth, just a different way of reaching the one that already exists.

Getting it

Already installed at /usr/local/bin/natctl-cli on whichever host runs the natctl daemon in your deployment — every NAT node if natctl_on_node_enabled = true, or the observability host if it's false. SSH into that host and run natctl-cli --help directly — no download step needed.

To run it from somewhere else instead — your own laptop, a bastion host, or any machine that isn't running natctl itself — download natctl-cli from this release's GitHub Release page (the same page this repository's own README links you to for the other four compiled binaries), then:

chmod +x natctl-cli

That machine just needs to reach the Linode API and, for the commands that read live fleet state, the roster (Part II, 2.2). It needs no Python interpreter and no dependencies installed — it's a single, self-contained native binary, the same as natctl itself.

The mutation token, when running commands that actually change something

drain, set-pool-scaling, set-client-config, set-vpc-sibling-subnets, add-ipsec-route, remove-ipsec-route, set-ipsec-routes, rotate-root-pass, rotate-linode-token, and rolling-restart all send a request the roster API only accepts with the correct bearer token (Part II, 2.5) — status, nodes, check-orphans, and list-ipsec-routes are pure reads and need nothing extra. Running the CLI on a fleet node itself needs no setup — it reads the same value the daemon already has. Running it from anywhere else, export it first:

export NATCTL_API_MUTATION_TOKEN=$(terraform output -raw natctl_api_mutation_token)
natctl-cli --config config.yaml drain --pool shared --node-id shared-elastic-3

A missing or wrong value comes back as a plain 401 with a clear message — never a silent no-op.

The --config flag, on every command

Every subcommand needs --config <path-to-config-file> — the same configuration file the daemon itself reads (Part II, 2.5). --config is a top-level flag, not a per-subcommand one, so it goes right after natctl-cli, before the subcommand name: natctl-cli --config /etc/natctl/config.yaml status, not natctl-cli status --config /etc/natctl/config.yaml (the latter fails with "unrecognized arguments"). /etc/natctl/config.yaml — not natctl.yaml — is the actual path the daemon itself reads its own config from on a live node, so pointing natctl-cli at it there means you're always reading the live, in-effect configuration. natctl-cli reads the file fresh on every invocation and never modifies it. If you're running the CLI from a machine other than a live fleet node, you'll need your own local copy of that file (and the credentials it references) — see Part II, 2.5 for exactly what it contains and how secrets are kept out of the parts of it that get distributed widely.

status — the one-line fleet-wide health check

natctl-cli --config /etc/natctl/config.yaml status

Why: the fastest possible answer to "is everything okay right now," with nothing to open, load, or log into. When: first, before anything more specific — the natural opening move of any troubleshooting session, or a quick sanity check before/after a change.

shared: 3 node(s), 3 healthy
dedicated-acme-corp: 3 node(s), 3 healthy

When: the moment status shows fewer healthy nodes than expected, to see exactly which node it is and what its current public-facing address is — the natural next step, not a replacement for status.

drain — retire one elastic node on your own schedule

natctl-cli --config /etc/natctl/config.yaml drain --pool shared --node-id shared-elastic-103

Why: you want a specific elastic node gone now, rather than waiting for the autoscaler to eventually decide it's no longer needed. When: rolling a patch across the fleet (10.4 below), moving load off a node ahead of planned maintenance elsewhere on it, or simply correcting a scale-out you no longer want.

The named node is excluded from the roster immediately — new connections stop landing on it at once — and deleted once its live connection count actually empties out, or once drain_timeout_seconds elapses, whichever comes first. Existing connections are allowed to finish; nothing is severed.

It refuses outright on a Terraform floor node, by design — floor capacity is Terraform's to manage, not natctl's (Part V, 5.1). Lower the floor count instead (edit that pool's floor_nodes field in terraform.tfvars's pools map, then terraform apply) if you actually want to remove permanent capacity.

resize — change a node's instance plan in place

natctl-cli --config /etc/natctl/config.yaml resize --pool shared \
  --node-id shared-3 --instance-type g6-dedicated-8

Why: a node's own traffic has genuinely outgrown its current plan. When: persistently high CPU/softirq or bandwidth against that one specific node — not a pool-wide capacity problem, which autoscaling already handles on its own without you touching this command at all.

Works identically on a floor or elastic node, and never deletes the node — it drains it, resizes the underlying instance, then rejoins it to the pool, all in one invocation. See Part V, 5.4 for the full mechanics (warm resize, falling back to cold automatically if Linode rejects the warm attempt, and what to do if a downsize doesn't fit on-disk).

--node-id is repeatable for more than one node in the same invocation — --node-id shared-3 --node-id shared-elastic-7 — but nodes are always processed strictly one at a time, and the whole operation stops at the very first failure rather than continuing against a pool that's already short a node.

If the resized node is a Terraform floor node, the command prints the exact override block to add to your .tfvars immediately after — do it before the next terraform apply, or Terraform will see drift and try to revert the resize back to the pool's base instance type.

If this fleet's controller runs on every node with leader election on (Part II, §2.3–2.4), this command prints a loud warning before proceeding: a one-shot CLI invocation has no identity of its own in that election, so it can't confirm it isn't racing the daemon's own elected leader on the same node. Run it during a quiet window for that pool to avoid any chance of both acting on the same node at once — this caveat doesn't apply at all to the single-dedicated-host control plane (an opt-in alternative — see natctl_on_node_enabled in Part IV).

rotate-root-pass — reset root_pass on already-provisioned nodes

umask 077 && printf '%s' "$(openssl rand -base64 24)" > /tmp/new-root-pass.txt
natctl-cli --config /etc/natctl/config.yaml rotate-root-pass --pool shared \
  --new-password-file /tmp/new-root-pass.txt
shred -u /tmp/new-root-pass.txt

Why: root_pass is normally set once, at each node's own creation time, from your Terraform config — there's otherwise no way to change it on a node that's already running short of replacing the instance outright. When: you suspect the value leaked, or as routine credential hygiene, and want to rotate it without rebuilding anything.

--new-password-file is required — the new password is never accepted as a bare CLI argument, since a secret passed as an argv value is trivially exposed via shell history and ps. Omit --node-id to rotate every node currently in the pool (one at a time, same as resize never running two in parallel); pass it (repeatable) to target specific nodes instead. Each node is drained before the reset, then genuinely powered off, reset, and powered back on — Linode's password-reset API rejects a running instance outright, so there's no lower-downtime path for this specific operation the way resize has an optional warm migration — and un-drained after, whether the reset succeeded or not.

Once the live rotation succeeds, the new value is also stored durably (the same live-override mechanism set-pool-scaling uses) so every natctl instance managing this pool picks it up within one reconcile pass, and any future elastic-node provision uses it immediately. A later terraform apply will overwrite this back to whatever terraform.tfvars says for this pool's root_pass — update that value too if you want the rotation to stick long-term.

rotate-linode-token — push a freshly-minted Linode API token to the whole environment

umask 077 && printf '%s' "<the new token value>" > /tmp/new-linode-token.txt
natctl-cli --config /etc/natctl/config.yaml rotate-linode-token \
  --new-token-file /tmp/new-linode-token.txt
shred -u /tmp/new-linode-token.txt

Why: the token every natctl instance uses to talk to the Linode API is set once, at deployment time, with no built-in way to change it afterward. When: you suspect it leaked, or as routine credential hygiene, and want every instance in the environment to converge on a replacement without restarting anything.

Not self-rotation: a Linode API token cannot list, create, or widen the scope of any token — including the one it's currently using — so there is nothing for natctl to do on its own here. You mint the replacement yourself, through your own separately-privileged session (the Cloud Manager UI, or your own linode-cli identity — never this deployment's own token), and this command's only job is pushing that already-minted value out. --new-token-file is required — the token is never accepted as a bare CLI argument, same reasoning as rotate-root-pass's --new-password-file.

No --pool flag: the Linode API token is a whole-environment credential, not a per-pool one — every pool a given natctl process manages shares one underlying API client. The instance that answers the request applies the new token to itself immediately, in-process; every other instance in the environment — other pools in the same process, and every peer under the every-node control-plane placement — picks it up on its own next reconcile pass. The old token is left valid at Linode's side; this command never revokes anything, so confirm the new one is working before you revoke the old one yourself.

rolling-restart — pick up a freshly-published natctl fix, staged and bake-checked, one node at a time

natctl-cli --config /etc/natctl/config.yaml rolling-restart --pool shared
natctl-cli --config /etc/natctl/config.yaml rolling-restart --pool shared --canary-count 1
natctl-cli --config /etc/natctl/config.yaml rolling-restart --pool shared --bake-seconds 60

Why: every node fetches its own natctl package once, at boot, and never again — a fix published afterward has zero effect on an already-running node until it's naturally replaced. When: a fix has been published and you want already-running nodes to pick it up without waiting for a rebuild. Requires auto_update_enabled (Part IX, 9.2) to be set on the deployment first — refuses with a clear error on any node where it isn't.

Restarts every node in the pool one at a time: tells each node's own control plane to re-fetch and verify its artifact (the same SHA-256 integrity check boot-time provisioning already applies) against the deployment's published manifest, and only restarts on a successful, verified match — a failed or tampered fetch never touches the currently-running code, and the command reports the failure instead of restarting into a broken state. Waits for that same node to come back healthy, then bake-checks it: samples its own reported pool health a few more times across --bake-seconds (default 90 for the wait, 30 for the bake) before trusting the restart and moving to the next node — a real signal that the new code is actually managing the pool correctly, not just that the process came back. If that check fails, the command automatically rolls that one node back to the version it was running before, and stops the rollout there — the rest of the pool is left untouched. At most one node's control plane is ever offline at a time either way; the data plane (NAT/masquerade traffic) is completely unaffected throughout, since the control plane and the forwarding path are independent processes. --node-id (repeatable) targets specific nodes instead of the whole pool.

--canary-count N restarts only the first N nodes and stops there once they're confirmed healthy, printing what to run next for the rest — expose a fix to a small cohort first, confirm it, then continue, rather than every node picking it up in one pass.

Safe to run against the pool's current leader (Part II, 2.3) if leadership is enabled — a node that comes back quickly enough simply resumes its own still-valid claim with no interruption; a slower restart hands off to another node exactly the way an ordinary failure would, with no operator coordination needed either way.

An automatic counterpart exists too: once auto_update_enabled is on, every node also checks periodically on its own whether a newer artifact has been published, and restarts itself automatically (after a random short delay, so a whole fleet doesn't restart in the same instant) — rolling-restart is for triggering that pickup immediately and deliberately, rather than waiting for the next automatic check. That automatic path carries its own safety net too: a version that crashes before it can confirm itself healthy is rolled back automatically the next time that node starts up, without any operator having to notice or intervene.

check-orphans — find elastic nodes a rebuild left behind

natctl-cli --config /etc/natctl/config.yaml check-orphans --pool shared
natctl-cli --config /etc/natctl/config.yaml check-orphans   # every pool at once, omit --pool

Why: terraform destroy only ever knows about the resources Terraform itself created — floor nodes. It has no idea an elastic node exists at all, since natctl provisions those dynamically, entirely outside Terraform's view. A rebuild can leave a real, billable elastic instance running from the previous environment with nothing left pointing at it. When: before and after any terraform destroy/apply rebuild of an environment — before, to see what already exists; after, to confirm the rebuild didn't leave anything behind.

Lists every node it currently sees, flags any elastic node that's unhealthy and not already draining as a SUSPECT ORPHAN, and tells you how to verify and clean one up. It's read-only — it never deletes anything itself, just reports, so it's always safe to run.

One honest limitation, stated plainly: this is a single, one-shot pass, not the long-running daemon's own continuously-updated view — a flagged node's unhealthy status reflects only the instant you ran the command, not how long it's actually been that way. Correlate against what you know you just created (your own terraform apply output) before deciding anything is genuinely orphaned.

set-client-config — override client fallback-probe behavior fleet-wide, live

natctl-cli --config /etc/natctl/config.yaml set-client-config --pool shared \
  --fallback-probe-enabled true --fallback-probe-interval 10

natctl-cli --config /etc/natctl/config.yaml set-client-config --pool shared --clear

Why: every connected client trusts the roster's own computed health by default (Part II, 2.2) rather than independently probing each node itself — correct for almost every deployment, since it means a client never adds duplicate probe traffic the control plane is already generating. When: the rare occasion you judge that trust unacceptable for a specific pool (a single-node pool already turns the probe on automatically where it matters most, Part IV — this command is for deliberately overriding the default elsewhere, not for the case that's already handled).

Flips the fallback probe on or off, and sets its interval, for every currently-connected client in that pool at once — without touching natctl.yaml or restarting anything anywhere. --clear reverts to whatever the pool's own static configuration says. Every connected client picks up the change within one long-poll round-trip (Part II, 2.2) — seconds, not a deploy cycle.

Unlike every other subcommand here, this one doesn't build a local view of the fleet at all — it sends a real HTTP request straight to a running natctl process's own API. It defaults to talking to localhost (the common case: running this from the same host natctl runs on, or against a specific node in the every-node placement mode), so pass --natctl-url explicitly if you're operating from anywhere else.

set-pool-scaling — override a pool's elastic bounds fleet-wide, live

natctl-cli --config /etc/natctl/config.yaml set-pool-scaling --pool shared \
  --min-nodes 3 --max-nodes 8

Why: the durable path ("Adjust elastic bounds," 10.3 below) needs a full terraform apply — correct for a bound change you intend to keep, but slower than a genuine incident calls for. When: a real, right-now capacity emergency — raise max_nodes immediately, then still go make the same change in terraform.tfvars afterward so it survives the next apply (see the trade-off below).

Same HTTP-to-a-running-instance mechanism as set-client-config above — it writes the exact same small object Terraform itself writes on every apply, so there's no separate override layer to reason about, just last-write-wins. Every controller managing this pool re-reads it the very next reconcile pass (roughly 15 seconds). The next terraform apply, for any reason, overwrites it back to whatever terraform.tfvars currently says — this command is the fast, temporary path, not a replacement for keeping Terraform's own value correct.

set-vpc-sibling-subnets — override the sibling-VPC-subnet list fleet-wide, live

natctl-cli --config /etc/natctl/config.yaml set-vpc-sibling-subnets \
  --cidrs "10.0.0.0/13,10.8.0.0/16,10.9.0.0/24"

natctl-cli --config /etc/natctl/config.yaml set-vpc-sibling-subnets --clear

Why: a newly-created sibling subnet in the same VPC (Part I, 1.2) needs an explicit route on every node and every client before it's actually reachable — normally a Terraform concern (it auto-discovers every subnet in the VPC on each apply), but this command gets a genuinely new subnet flowing immediately, without waiting on a full apply. When: a subnet was just added to the VPC outside of this project's own Terraform (by hand, or by another team's automation sharing the same VPC) and needs to be reachable right now.

No --pool flag — this setting is a property of the whole environment, not any one pool, since every pool shares the same VPC. Every controller re-reads it the next reconcile pass, and it feeds both directions of reachability described in Part I, 1.2: a node's own route to the new subnet, and (via the roster) every connected client's self-healing route to it too. --clear empties the override; it does not restore Terraform's own discovered value — run terraform apply for that, since Terraform always re-derives this list live from the VPC's actual subnets rather than reading back anything natctl-cli wrote. A client removing its own sibling-subnet routes specifically in response to --clear takes one extra poll beyond that — it waits for the roster to report the empty list twice in a row before actually removing anything, so a single transient empty reading (for example, right after a controller restart) can never be mistaken for a deliberate clear.

Same last-write-wins relationship with Terraform as set-pool-scaling above: the next apply, for any reason, recomputes and overwrites this object from live VPC discovery.

Refuses by default if the new list — or the empty list --clear produces — would no longer cover this environment's own control-plane addresses: dropping the one CIDR a client's NATCTL_ROSTER_URL actually lives in would cut every client's route to natctl itself, with no automatic recovery. The check runs twice — once in the CLI before it even makes the HTTP call, and again independently on the natctl side, so a stale or older daemon doesn't leave you unprotected. Pass --force to override it deliberately; it's sent through to the server too, so the write always succeeds once you pass it.

list / add / remove / set-ipsec-routes — route a pool's clients to a customer-operated IPsec/VPN gateway

natctl-cli --config /etc/natctl/config.yaml list-ipsec-routes --pool shared

natctl-cli --config /etc/natctl/config.yaml add-ipsec-route --pool shared \
  --cidr 10.50.0.0/16 --gateway 192.168.100.5

natctl-cli --config /etc/natctl/config.yaml remove-ipsec-route --pool shared --cidr 10.50.0.0/16

natctl-cli --config /etc/natctl/config.yaml set-ipsec-routes --pool shared \
  --route 10.50.0.0/16:192.168.100.5 --route 10.60.0.0/16:192.168.100.5
natctl-cli --config /etc/natctl/config.yaml set-ipsec-routes --pool shared --clear

What this is for: a customer's own IPsec/VPN gateway — an instance they operate themselves, on this pool's own VLAN — that some destinations should route through instead of straight out to the internet. This project never runs IPsec software itself and never terminates a tunnel on a NAT node; it only tells every client on the pool how to reach the gateway once it already exists. Per pool, unlike set-vpc-sibling-subnets above — a dedicated gateway for one tenant's own pool doesn't require touching any other pool's routes.

add-ipsec-route reads the pool's current list, then writes the whole thing back with your entry included — running it again for a --cidr that's already routed replaces its --gateway, so it's also how you change one; no need to already know or repeat the rest of the list. remove-ipsec-route is the same read-modify-write in reverse, and errors instead of silently succeeding if the --cidr you named isn't actually there. set-ipsec-routes is the bulk equivalent — declare the whole list (or --clear it) in one call, the better fit for a scripted reset than a one-off edit.

Every controller managing this pool re-reads the change the next reconcile pass, and every connected client picks it up on its next roster poll after that — no restarts needed anywhere. Refuses by default (both in the CLI and, independently, server-side) if a --gateway isn't actually inside this pool's own VLAN CIDR — client-agent has no other interface to reach it on, so an out-of-range gateway is always a mistake. Pass --force to override it deliberately.

Same last-write-wins relationship with Terraform as every other live override here: add the route to this pool's own ipsec_routes field in your terraform.tfvars if you want it to survive the next apply, the same way a durable set-pool-scaling change needs its own tfvars update too.

10.3 Common Procedures

Every procedure below assumes nothing beyond a working deployment — each command is the exact, complete step, not a paraphrase of one.

Raise the floor

  1. Edit the target pool's floor_nodes field in terraform.tfvars's pools map, then from the Terraform environment directory: 
    terraform apply
    (pools is a map, so a single-field CLI -var override isn't practical here — edit the file directly.)
  2. Confirm the new node(s) reach a running state and pass their own health check (Part VII).

Every connected client picks up the new node automatically on its next roster refresh — no other action is needed anywhere.

Adjust elastic bounds (min_nodes / max_nodes)

Durable (the change survives the next apply, which is why this is the default path):

  1. Edit that pool's max_nodes field in terraform.tfvars's pools map (or floor_nodes for the pool's minimum — the same field "Raise the floor" above uses), then from the Terraform environment directory: 
    terraform apply

This writes the new value to a small, dedicated object the control plane rereads every reconcile pass — the very next pass, roughly 15 seconds later, is already sizing against it. No restart, and — unlike changing the floor node count's own boot-time settings below — no existing node of any kind is touched: the apply is a plain, in-place update to that one object, nothing else.

Fast, temporary (10.2's set-pool-scaling) — for a real, right-now capacity emergency, when even one terraform apply cycle is too slow:

natctl-cli --config /etc/natctl/config.yaml set-pool-scaling --pool shared \
  --min-nodes 3 --max-nodes 8

Writes the exact same object the Terraform path above writes — last-write-wins, no separate override layer. Update terraform.tfvars too afterward if the change should stick; the next apply, for any reason, overwrites it back to whatever the file currently says.

Adjust other autoscaling tuning (watermarks, sustained-breach window, step caps, cooldown)

  1. Edit the relevant autoscale: setting (Part V, 5.2) in the control plane's own configuration file (natctl.yaml).
  2. Restart the service so it re-reads the file: 
    systemctl restart natctl

These settings are genuinely boot-time configuration, unlike a pool's min_nodes/max_nodes above — a restart is required for a change to take effect.

Manually drain and remove an elastic node

natctl-cli --config /etc/natctl/config.yaml drain --pool shared --node-id shared-elastic-103

The named node is immediately excluded from the roster and deleted once its live connection count empties out, or once a configured drain timeout elapses, whichever comes first. A floor node can never be drained this way by design — the command refuses; reduce the floor's declared count instead (above). See 10.2 above for the full picture of when to reach for this.

Resize a node's instance plan

natctl-cli --config /etc/natctl/config.yaml resize --pool shared \
  --node-id shared-3 --instance-type g6-dedicated-8

--node-id can be repeated for more than one node — see the full mechanics (drain, warm/cold resize, rejoin) in Part V, 5.4. Nodes are always processed one at a time, and the operation stops at the very first failure rather than continuing against a pool that's already short a node.

Add an extra egress IP to a running node

  1. Raise egress_ips_per_node in Terraform and apply — this allocates the address but does not yet wire it into the node's live NAT rules.
  2. SSH into the specific node and run: 
    /path/to/scripts/add-egress-ip.sh --ip <new-ip> --bucket-index 1 --bucket-count 2
  3. Confirm with nft list table inet lng_nat on that node.

This currently only works for floor nodes — elastic nodes are provisioned single-IP.

Enable BGP IP failover for a pool

This is the one procedure in day-2 operations that carries real reachability risk if rushed.

  1. Confirm buddy sync (Part IV, 4.3) is already active for the pool.
  2. Look up the correct BGP data-center identifier for your region and set it, along with ip_failover_enabled = true, in Terraform for the pool.
  3. terraform apply. This installs and starts FRR on every node in the pool with self-announcement already active — it does not yet call the cloud provider's IP-sharing API.
  4. Watch buddy-sync take over from here automatically (its default activation delay lets the announcing side come up first): journalctl -u lng-buddy-sync -f on a paired node should show its buddy assignment, then shortly after, journalctl -u natctl should log that it called the IP-sharing API.
  5. Confirm sessions actually establish: vtysh -c "show bgp summary" on a paired node — peers should show Established, not stuck on Active.
  6. Test a real failover from an external host before trusting it in production: ping a node's public IP continuously, then systemctl stop frr on that node and confirm the ping keeps answering (now via its buddy). systemctl start frr to fail back.

Get a newly-added VPC subnet reaching nodes and clients

Durable: terraform apply — every apply re-discovers every subnet actually in the VPC and rewrites the sibling-subnet list from scratch, no tfvars edit needed for this one specifically.

Fast, temporary (10.2's set-vpc-sibling-subnets) — for a subnet just added outside this project's own Terraform run (by hand, or by another team sharing the VPC) that needs to be reachable before the next apply:

natctl-cli --config /etc/natctl/config.yaml set-vpc-sibling-subnets \
  --cidrs "10.0.0.0/13,10.8.0.0/16,10.9.0.0/24"

No --pool flag — one list, shared by the whole environment. Every controller picks it up the next reconcile pass, which also republishes it to every connected client via the roster (Part I, 1.2). A later terraform apply still overwrites this back to its own live-discovered value.

Enable the every-node control-plane placement

  1. Confirm the API token already has the scopes in Part II, 2.5 — no new scope is needed for this specifically.
  2. Set natctl_on_node_enabled = true in Terraform and apply. This recreates every floor node (Part II, 2.3) and turns natctl off on the dedicated observability host.
  3. Confirm exactly one leader: journalctl -u natctl -f on any node should show exactly one node logging that it's now the leader, and every other node logging that it's a follower.
  4. Confirm every node still answers reads regardless of leadership: curl http://<any node's private IP>:8099/status.

10.4 Troubleshooting Playbook

Each entry assumes you're starting from zero context on this specific alert — what it means, and the exact steps to actually resolve it.

A port-exhaustion alert fires

  1. Open the dashboard's port-headroom panel (Part VII, 7.3) to identify the specific node and public IP that's actually saturated.
  2. If the whole pool is under pressure (every node's headroom is low, not just one): the autoscaler should already be scaling out on its own. Check journalctl -u natctl for whether it's blocked — either still inside its cooldown window after a recent scaling action, or already at the pool's configured maximum node count (Part V, 5.2). If it's at maximum and still under pressure, raise max_nodes for the pool (see "Adjust elastic bounds" above).
  3. If only one node is hot while others have headroom: this is expected at low connection counts — ECMP hashing isn't perfectly even across a small number of flows, and it self-corrects as volume grows. If it persists under real sustained load, give that specific node an extra egress IP ("Add an extra egress IP" above) to multiply its own port ceiling.

A pool-below-floor alert fires

  1. Run natctl-cli --config /etc/natctl/config.yaml nodes --pool shared — this shows every node and whether it's actually healthy, not just present. The floor check is against healthy count specifically, so a node that exists but is failing its health check doesn't count.
  2. If an elastic node is missing or unhealthy: it should self-heal automatically once it's been unhealthy past the configured threshold (default 900 seconds / 15 minutes) — watch for a log line like "elastic node ... has failed health checks for >=Ns — draining for replacement" in journalctl -u natctl. If that line never appears, check the API token's scope and any provisioning errors in the same log (a bad instance type, a region quota, etc.). An elastic node that disappears from the cloud provider's own API entirely (a crash, a host failure, a manual shutdown) rather than staying visible-but-unhealthy is cleaned up the same way, on the same threshold — look for "elastic node ... vanished from discovery ... — deleting its orphaned instance" instead.
  3. If a floor node is unhealthy: this is never auto-replaced by design — the pool instead runs with extra elastic capacity compensating for it, which is expected, not an error. Fix the actual floor node yourself: SSH in and investigate (check systemctl status nat-exporter and journalctl -u nat-exporter first, since that's what the health check itself depends on), or replace the instance through a targeted re-apply of just that node.
  4. If a floor node is simply missing entirely (not present at all, not just unhealthy): that's infrastructure drift, not something natctl can or should fix — run terraform plan and reconcile it the normal way.

A node has no sync buddy

  1. Confirm buddy sync is actually turned on for the pool and its roster-URL configuration matches everywhere it's referenced (Part IV, 4.3).
  2. On the node itself: systemctl status lng-buddy-sync should show it active, and journalctl -u lng-buddy-sync -f should show it polling the roster. If the service isn't running at all, systemctl restart lng-buddy-sync and watch the log for it picking up a peer assignment.
  3. Remember this is a mitigation, not a health signal — an unpaired node is still fully healthy and fully in ECMP rotation. Don't page on this alone; it only means a future failure of that node won't have a warm buddy to fail over to yet.

A client isn't picking up a fleet change

  1. Confirm the client can reach the roster URL at all: curl http://<control-plane private IP>:8099/fleet/<pool> from the client instance itself. If this fails outright, it's a network/firewall problem, not a routing-agent problem.
  2. On the client: systemctl status lng-client-agent and journalctl -u lng-client-agent -f — it logs every roster refresh and every change to its healthy-node set live.
  3. Remember a node present in the roster but reporting unhealthy is excluded from routing regardless of how fresh the roster itself is — check the node's own health first (Part II, 2.1) before assuming the client is the problem.

Rolling a security patch across the fleet

  1. Elastic nodes: drain-and-replace is simplest — drain each one ("Manually drain and remove an elastic node" above) and let the pool provision fresh, already-patched replacement capacity as it naturally scales.
  2. Floor nodes: patch one at a time, since there's no automatic drain for these. For each node: drain it manually (there's no built-in command for this on a floor node — coordinate it yourself, e.g. a temporary firewall rule, or SSH in and stop nat-exporter so its health check starts failing, which the routing agents pick up within seconds), patch and reboot it, confirm curl http://<node>:9200/healthz reports healthy again, then move to the next node.

10.6 How to Update Any Field

10.5 tells you what each field does; this is the actual procedure for changing one safely on a live deployment.

Which host(s) you need to touch depends on your placement mode

Single dedicated host (the default, Part II, 2.3 — natctl only runs on the observability instance): exactly one file, /etc/natctl/config.yaml on that host.

natctl_on_node_enabled: true: every floor and elastic node in that pool runs its own independent natctl process, each with its own /etc/natctl/config.yaml, read once at that process's own startup. A YAML-only field (anything not flagged "live-overridable" in 10.5) has to be changed on every single one of those nodes — editing it on just one node only changes that one node's own behavior, not the fleet's. This also affects future elastic nodes: a brand-new elastic node's own baked-in config comes from whichever node is currently the leader, using that leader's own in-memory config as of its last restart — so as long as every node gets the same edit-and-restart (which you should be doing anyway, for consistency), future provisioning stays correct automatically, with no separate step needed.

The procedure, per host

  1. Back up the file first — a single cp, not a real backup system, but enough to make a bad edit trivially reversible: 
    cp /etc/natctl/config.yaml /etc/natctl/config.yaml.bak
  2. Make your edit. This repository ships compiled binaries with no Python interpreter installed on the node — there's no python3 -c "import yaml..." syntax check available locally on the node itself. If you want to validate the YAML is well-formed before touching a live node, do it on your own machine first (or against your own copy of docs/natctl.example.yaml), then copy the verified file over.
  3. Restart natctl: 
    systemctl restart natctl
  4. Confirm it came back up clean — a bad edit (invalid YAML, a field set to a value natctl rejects) surfaces here, not at edit time: 
    systemctl status natctl      # should show "active (running)", not "failed"
journalctl -u natctl -n 50   # look for a normal reconcile-pass log line, not a startup traceback
  5. If it failed to come back up, restore the backup and restart again: 
    cp /etc/natctl/config.yaml.bak /etc/natctl/config.yaml
systemctl restart natctl

Under natctl_on_node_enabled, do this one node at a time, not all at once — if a bad edit is going to take a node down, you want to find that out with the rest of the fleet still healthy and serving traffic, not discover it after every node has already restarted simultaneously with the same mistake.

10.7 Where to Look First

In rough order of likelihood: a private-subnet instance's routing agent isn't running or can't reach the roster URL; the control plane's API token has expired or lost a scope; or the minimum/maximum bounds are misconfigured for actual current load. The architecture and this book describe exactly how the system is supposed to behave — when real behavior diverges from that, that gap is always the right starting point for debugging, not a sign the design itself is wrong.

10.8 Control-Plane Recovery

Every scenario below is about restoring decisions, not restoring connectivity. In all of them, the NAT data plane keeps forwarding traffic untouched the whole time — nodes don't ask the control plane for permission to forward a packet, and the routing agent keeps using its last-known-good roster rather than dropping traffic the moment a fetch fails. What actually pauses is new elastic capacity, zombie-node replacement, buddy/failover reassignment, and — under the every-node placement — leadership itself.

What's genuinely irreplaceable, and what isn't

Your own natctl.yaml is the one thing nothing here can regenerate for you — keep it in version control like any other infrastructure-as-code input. Historical dashboard metrics are the single most valuable, least-reproducible thing the control plane holds — losing that data store loses yesterday's throughput numbers for good, with nothing else in the system to recompute them from. The dashboard layout and alert rules themselves, by contrast, are provisioned fresh from files already shipped with this project and reappear automatically on any fresh start — only hand-made panels, user accounts, and active alert silences are lost if that specific data is destroyed without your own separate backup. Everything else — the fleet's own live state, the leader-election lease, the scrape-target list — is disposable and rebuilds itself from the cloud provider's live API within one reconcile pass; losing it costs a little time, never correctness.

Single dedicated host

The controller process crashed or hung, but the host itself is finesystemctl restart natctl — it's already configured to restart itself on failure, so this is usually already resolved by the time you notice. No data to restore; the very next pass rebuilds fleet state from the live API.

ScenarioRecovery
A single node diesUsually nothing to do — this is the ordinary election/fencing sequence described earlier in this part working as intended. Confirm exactly one node reports itself as leader afterward, then investigate why the dead one lost its lease before powering it back on — a fenced node stays off deliberately until you do that yourself.
The shared lease store becomes unreachable for the whole fleet, not just one nodeEvery node in the pool correctly refuses to assume it's leader while it can't confirm that — a stricter, fleet-wide version of "the control plane goes quiet" rather than one instance's outage. A node was fenced and needs to come backConfirm it's actually safe to bring back — not still in whatever condition caused it to lose its lease in the first place — then power it back on yourself. It rejoins as a follower automatically with no special "rejoin" step.
Enough nodes die at once that survivors can't reach a majority to corroborate a fencing decisionTell two situations apart first, since the fix differs: if the missing nodes are genuinely gone, the pool's own membership shrinks to match as the survivors keep discovering the fleet, and this typically resolves itself within a couple of passes. If they're actually still running but network-partitioned away from the survivors, they never drop out of that count, and the survivors can stay stuck indefinitely — confirm which case it is by checking each node's actual status directly with the cloud provider, and if it's a genuine, slow-to-heal partition, you can break the deadlock yourself by powering the unreachable nodes off (this is you performing the same safety action the system would otherwise do on its own) — only do this if you're confident they aren't still safely serving traffic on their own side of the split.
The shared lease record itself becomes corrupted or unreadableEvery node hits the same error reading it, on every pass, and the pool never elects anyone. Inspect the object directly through your object-storage tooling; if it's genuinely unreadable, delete it outright. The very next pass on every node sees no lease at all — the exact same safe path a brand-new pool's first-ever election already uses — and a new leader emerges within one election cycle, no differently than day one.
More than one node reports itself as leader for the same pool, and it isn't resolving within a pass or two on its own (this is what's usually called "split-brain")This should never persist past a couple of passes under normal conditions — if it does, something is actively preventing the two from ever seeing each other's writes to the shared lease store, which is rarer and more serious than an ordinary node-to-node network split. Read the lease record directly to see which identity it currently names — that record is the source of truth by construction, not either node's own belief — stop the controller on the other one, resolve the underlying connectivity problem, then let it rejoin normally.

Building a brand-new control plane from nothing

Use this for a genuine disaster, or a deliberate decision to start fresh — migrating accounts, moving regions, or simply no longer trusting the state in an existing coordination bucket. This assumes your NAT node fleet already exists (or is being rebuilt at the same time) and just needs a control plane pointed at it again.

Before you start, decide what to do about the coordination bucket if you're reusing one from a previous control plane. Reusing it is safe by construction — a stale, leftover record from the old control plane is now correctly recognized as stale rather than mistaken for a still-living leader — but if you'd rather start guaranteed-clean instead of relying on that self-correction, delete that pool's lease object from the bucket first; it's harmless if it was never there.

  1. Single dedicated host: apply your infrastructure as code with the every-node placement turned off (the default) and object storage configured. Verify: the controller service is active, the roster shows every expected node, the dashboard shows live data within a couple of scrape intervals, and every alert rule shows as loaded and evaluating.
  2. Every-node placement: apply your infrastructure as code with the every-node placement turned on and object storage configured — the same bucket serves both the fleet's fetched-at-boot software and the leader-election lease. Verify a single leader emerges within one election cycle (a brand-new deployment has no previous leader to fence at all, so this should only take as long as the built-in jitter delay, plus the settle delay if you've configured one) — check every node's own status and confirm exactly one reports itself as leader.
  3. Either way, once the control plane is up: confirm every client instance's routing agent reconnects and repopulates its own routing table without needing any reconfiguration of its own; trigger a real scale-out and confirm a new node actually gets provisioned and wired into failover, not just evaluated on paper.

What you cannot get back if you skipped your own backups: prior dashboard history, anything hand-made in the dashboard tool beyond what the provisioned files recreate, and any active alert silences from before. Your own natctl.yaml is never at risk from this procedure as long as you kept your own copy — this project never treats it as something needing its own backup schedule, by design; that responsibility stays with you, the same as any other infrastructure-as-code input.

Appendix

Glossary

Every term of art used anywhere in this book, alphabetized, with a one-paragraph definition as the term is used in this system and a pointer to the chapter that treats it in depth.

A.1 Terms of Art

Definitions are written to be read standalone — a term encountered mid-chapter can be looked up here without reading anything else first. Where a definition depends on another term in this list, that term is named in the text so it can be followed.

Activation delay
The wait natctl observes between computing a brand-new buddy IP-failover pairing and actually calling the provider's IP-sharing API for it (60 seconds by default), tracked independently per node-and-buddy-address relationship. It guarantees the node that will announce a backup route has had time to configure that announcement before the shared address is switched into BGP-only delivery — the mechanism that protects against an address going dark at the moment sharing is first enabled. Part IV, 4.4
Active-active
The fleet model in which every node in a pool forwards real traffic all the time. There is no master, no standby, and no shared floating address that all pool traffic funnels through; capacity is fully utilized and a single tenant can burst across the whole pool. Contrast with an active/passive pair, where one member idles until the other fails. Part I, 1.4; Part IV, 4.8
admin_cidrs
The operator-supplied list of source address ranges (an office, VPN, or bastion egress range) permitted to reach SSH and the monitoring dashboards. Every administrative firewall rule is scoped to this list; it is never left open to the whole internet by default. Part VIII, 8.1
Anti-affinity placement
Spreading a pool's nodes across separate underlying physical hosts, via placement groups, so that both members of a buddy pair cannot be taken out by one physical-host failure. Opt-in, and safe to enable on a running pool without replacing any node. Part IV, 4.5
Artifact (fetched at boot)
Any file a node downloads from Object Storage at boot rather than carrying embedded in its boot-time configuration — the metrics exporter, the connection-sync daemon, the control-plane package, and static service definitions. Needed because the provider caps boot-time configuration at 16,384 bytes, which the project's own software exceeds many times over. Each artifact's integrity is checked against a SHA-256 fingerprint before use. Part VI, 6.2
Autoscale watermark
A configured threshold on one autoscaling signal. A high watermark is the scale-out trigger (connection-tracking utilization at or above 70%, throughput at or above 85%, busiest-core softirq at or above 80%); a low watermark is a scale-in trigger (connection-tracking utilization at or below 30%). Port headroom is the inverted case — its trigger fires when free ports fall below 15%. A watermark starts a breach streak; only a sustained breach produces an action. Part V, 5.2
BGP (Border Gateway Protocol)
The routing protocol by which networks on the internet announce to one another which address ranges they can deliver traffic to, and by which routers decide where to forward a packet: toward whoever is currently announcing its destination. In this system each node runs a BGP daemon (FRR) that announces the node's own public IP, and its buddy's, to the provider's route reflectors. Part 0, 0.2 (g); Part IV, 4.4
Breach streak
The count of consecutive reconcile passes on which a given autoscaling signal has been past its watermark. A scaling action is only sized and taken once the streak reaches the configured sustained-breach requirement (two passes by default); a single noisy reading only starts the counter. Exposed as a metric per signal. Part V, 5.2; Part VII, 7.2
Buddy / buddy pairing
Another node that a given node continuously mirrors its live connection-tracking state with, and stands ready to take over the public IP of. Pairings are recomputed from the currently healthy node set on every reconcile pass by sorting the nodes and pairing them two at a time; an odd count forms a triangle. A node without a buddy is still fully healthy and fully in rotation — pairing is a session-continuity mitigation, not a health signal. Part II, 2.1; Part IV, 4.2
Buddy IP failover
The opt-in mechanism by which a node's buddy takes over its public IP when it dies, using FRR and the provider's BGP-based IP Sharing. Every paired node simultaneously announces its own address as primary and its buddy's as secondary, from the moment the pairing exists, so a failure needs no new action to redirect traffic — the standing secondary announcement simply becomes the best available route. Part IV, 4.4
buddy-sync
The daemon (lng-buddy-sync.service) running on every node that watches the roster for changes to this node's buddy assignment and reconciles two things in response: the set of conntrackd peer processes it runs, and FRR's secondary-route announcements. It carries no durable state of its own and re-derives everything from the roster on restart. Part IV, 4.3
CIDR
Classless Inter-Domain Routing notation — an address range written as a starting address and a prefix length, such as 10.60.32.0/20 (4,096 addresses) or 192.168.100.0/24 (256 addresses). The prefix length is what a machine uses to decide whether a destination is local or must be routed. Part 0, 0.2 (a)
Client / client instance
A private-subnet instance that sends its outbound internet traffic through the NAT pool. It lives on the pool's VLAN with a static VLAN address, runs the client routing agent, and holds no public IP of its own (in the two interface shapes where the agent manages its default route). Part III, 3.3
Client routing agent (client-agent)
The small, dependency-free service (lng-client-agent.service) on every client instance. It long-polls the roster and maintains the client's default route as a resilient ECMP nexthop group across every node the control plane currently reports healthy. It manages exactly one thing — the default route — and on any failure to reach the roster keeps its last-known-good state rather than tearing routing down. Part III, 3.2
Cloud Firewall
Stateful packet filtering performed by the provider in front of an instance's public and VPC interfaces, before traffic reaches the operating system. It does not filter VLAN traffic at all; on the VLAN interface, a node's own nftables ruleset is the entire security boundary. Part 0, 0.2 (e); Part VIII, 8.1
Connection-state sync
Continuous mirroring of a node's kernel connection-tracking table to its buddy, performed by one conntrackd process per peer relationship over UDP on the VPC interface, so that a buddy taking over a dead node's public IP also holds the table entries needed to keep that node's still-open connections alive. Useless without buddy IP failover, and vice versa. Part IV, 4.3
conntrack (connection tracking)
The Linux kernel table that records one entry per connection passing through a NAT node — the connection as the private side sent it, and what a reply must look like to be matched back to it. It is the actual mechanism of NAT: replies are looked up against it to find the private address to rewrite back to, and a packet matching no entry is dropped. Its fixed maximum size (nf_conntrack_max) is the primary capacity ceiling the autoscaler watches. Part 0, 0.2 (i); Part V, 5.2 and 5.3
conntrackd
The standard Linux connection-tracking synchronization daemon. This system runs one instance per buddy relationship as a systemd template unit, conntrackd@<peer-node-id>.service, each on its own deterministically derived UDP port (a base of 3780 plus a hash of the two peers' node IDs, within the range 3780–4779). Part IV, 4.3
Control plane
The components that make decisions and never touch a customer packet directly: natctl (the fleet controller and roster API) and the metrics/dashboard/alerting stack. If the entire control plane is down, already-provisioned nodes keep forwarding traffic; only new decisions pause. Part II (component map)
Cooldown
The period after any scaling action (300 seconds by default) during which no further scaling evaluation happens at all, so newly added capacity has time to boot, pass health checks, and start absorbing load before the next decision is made. Part V, 5.2
Data plane
Everything that either forwards actual traffic or steers a client toward whatever is forwarding it: the NAT nodes themselves (nftables/masquerade), the metrics exporter and health endpoint on each node, connection-state sync, FRR, and the client routing agent. Grouped this way because failures here directly affect customer traffic. Part II (component map); Part III
Dedicated pool
A pool provisioned for a single tenant that needs isolated or reserved capacity — its own VLAN, its own floor and elastic bounds, its own leader election, fully separate traffic — built from exactly the same mechanism as the shared pool under a different name. Part I, 1.4; Part V, 5.5
Default route
The route a machine uses for any destination it has no more specific route for — in practice, everything internet-bound. On a client instance, this is the one route the client routing agent manages, as an ECMP route across healthy nodes. On a NAT node, the default route always points out the public interface, never the VPC one. Part III, 3.2 and 3.3
Drain
Retiring a node gracefully: it is excluded from the roster immediately so no new connections land on it, and removed only once its live connection count empties out or a timeout (drain_timeout_seconds, 180 by default) elapses. Elastic nodes are drained by the autoscaler, by the unhealthy-node replacement path, or by an operator with natctl-cli drain; floor nodes are never drained automatically. Part V, 5.4; Part X, 10.2
ECMP (Equal-Cost Multi-Path)
A Linux kernel routing feature that lets one route name several next hops of equal preference, choosing among them per connection by hashing the packet's flow identity so every packet of one connection takes the same path. Every client's default route is an ECMP route across the pool's healthy nodes. Part 0, 0.2 (h); Part III, 3.2
ECMP hash policy
The kernel setting that determines which packet fields feed the multipath hash. The client routing agent sets it at every startup to include source and destination ports alongside the address pair (the five-tuple), so many separate connections to the same destination spread across the pool instead of all landing on one node. Part III, 3.2
Egress IP
The public address a fleet's outbound traffic appears to come from — on a NAT node, the address on eth0. A pool's set of egress IPs is what a downstream partner allow-lists. Each node has one by default; egress_ips_per_node adds more per node to multiply available source ports, though only the primary participates in IP failover. Part 0, 0.2 (f); Part V, 5.3
Elastic node
A node natctl provisioned itself in response to load, within a pool's min_nodes/max_nodes bounds, tagged lng-elastic to distinguish it from the floor. Elastic nodes are drained and removed by the autoscaler as load falls, and automatically replaced if persistently unhealthy. Part V, 5.1; Part IV, 4.7
Ephemeral port
A source port chosen from the operating system's dynamic range for an outbound connection. A NAT node has a finite supply per public IP toward any single destination (on the order of 55,000 to 64,000), which is the ceiling behind port exhaustion. Part V, 5.3
Fallback probe
An opt-in, per-client direct health check of each node, in addition to trusting the roster's own health verdict. When on, a node is usable only if both the control plane and the client's own probe agree it is healthy. Off by default because every client and node share one VLAN segment; switched on automatically for a pool whose live node count is exactly one. Overridable fleet-wide, live, with set-client-config. Part II, 2.2; Part X, 10.2
Fencing / STONITH
Powering off the previous leader through the provider's instance power-management API, and polling until that shutdown is confirmed, before a candidate ever claims leadership — "shoot the other node in the head." It is the actual safety mechanism of leader election; the lease record is only a coordination hint. An unconfirmed fence aborts the election rather than proceeding. A fenced node stays off until an operator deliberately brings it back. Part II, 2.4
Five-tuple
The five fields that together identify one connection: source address, destination address, source port, destination port, and protocol. Identical for every packet of one connection, which is what makes it the right hashing key for ECMP and the natural key of a conntrack entry. Part 0, 0.2 (h)
Floor node
A node declared and created by your infrastructure-as-code — fixed baseline capacity. natctl never deletes, drains, or replaces a floor node under any circumstance; an unhealthy one is compensated for with extra elastic capacity and left for an operator to repair. Part V, 5.1; Part IV, 4.7
Follower
In the every-node control-plane placement, any natctl instance that is not the current leader. A follower runs the full read-only pipeline — discovery, health checks, buddy computation, roster serving — identically to the leader, and stops short only of performing mutating cloud calls. Part II, 2.3
FRR (FRRouting)
The open-source BGP routing daemon (frr.service) on every node that announces the node's own public IP as primary and its buddy's as secondary to the provider's route reflectors. Its running configuration is rewritten by buddy-sync on every pairing change; vtysh -c "show bgp summary" shows live session state. Part IV, 4.4
Health check (/healthz)
The endpoint on every node's metrics exporter (port 9200) that natctl calls once per reconcile pass. It runs three real checks each time — IP forwarding enabled, the NAT ruleset's specific expected rules actually present (not just that the ruleset object exists), and an actual outbound HTTPS request out the public interface succeeding — and all three must pass. The roster's healthy field is this verdict. Proves the node can forward traffic, not that it currently is — see nftables_accepts_total for that. Part II, 2.1; Part VII, 7.5
Hub
In a triangle, the node that both forms an ordinary mutual pair with one node and additionally provides a one-directional backup for a third. A hub runs two independent conntrackd processes and announces two secondary routes. Part IV, 4.2
IP Sharing
The Akamai Cloud capability by which a second instance is registered as a legitimate destination for another instance's public IP, after which the provider delivers that address to whichever registered instance is actively announcing it over BGP. One primary and at most one secondary per shared address; only a real public IP on the instance's own interface is eligible. Part 0, 0.2 (g); Part IV, 4.4
Layer 2 / Layer 3
Layer 2 is the local segment on which devices address each other directly by hardware (MAC) address with no router between them — a VLAN. Layer 3 is the IP layer, where routers forward packets by destination address between segments — a VPC. Part 0, 0.2 (c)
Leader
In the every-node control-plane placement, the one natctl instance per pool currently permitted to make cloud-mutating calls — creating or deleting a node, updating an IP-sharing assignment, reserving an address. Every other instance is a follower. Leadership is per pool, never fleet-wide. Part II, 2.3 and 2.4
Leader election
The process by which, in the every-node placement, exactly one natctl instance per pool becomes leader: candidates notice an expired lease, wait a random jitter, re-check the lease, probe the previous leader directly, ask peers for corroboration, fence the previous leader, and only then claim the lease. Defense in depth around fencing, not a mathematically perfect mutual-exclusion guarantee. Part II, 2.4
Lease
A small JSON record in Object Storage naming a pool's current leader, its term, and its last renewal time, valid for 45 seconds per renewal by default. It is a shared bulletin board every instance can read — a best-effort hint, deliberately not the source of correctness, since writing it is not an atomic compare-and-swap. Part II, 2.4; Part VI, 6.3
Long-poll
A roster request with ?wait=true&since=<roster_version>, which the server holds open without answering until the roster actually changes or roughly 25 seconds pass. Still an ordinary HTTP request the client initiates — nothing is pushed — but it gives near-instant reaction to changes with near-zero traffic while nothing is changing. Part II, 2.2
Masquerade
The nftables NAT action that rewrites a packet's source address to the address of the interface it is leaving through, and tracks the connection so replies are rewritten back. It is what a NAT node does to every packet arriving on its VLAN interface and leaving its public one. With a reserved IP configured, an explicit source-NAT to that specific address is used instead, to avoid ambiguity when an interface carries more than one address. Part III, 3.1
Mutation token
The shared bearer token protecting the roster API's few mutating routes (drain and the three live-override commands). Generated automatically at deployment, resolved from a narrowly-permissioned local file or environment variable, never stored in the widely distributed configuration file. An instance with none configured refuses every mutating request. All roster reads stay open. Part II, 2.5; Part X, 10.2
NAT (Network Address Translation)
Rewriting a packet's addresses in transit — here, replacing a private source address with a public one on the way out, recording the mapping, and reversing it on the reply — so machines with private-only addresses can reach the internet without holding public addresses themselves. Outbound-initiated by construction. Part 0, 0.1
NAT node
An ordinary Linux compute instance with three interfaces — eth0 public, eth1 VPC, eth2 VLAN — running an nftables ruleset that masquerades VLAN traffic out its public IP. Nothing on it is durable; a broken node is destroyed and replaced, never repaired from a backup. Part I, 1.3; Part III, 3.1
natctl
The fleet controller — a single long-running service (natctl.service) that repeats the reconcile pass on a timer: discover nodes by tag, health-check each, compute buddy pairings, evaluate autoscaling, publish the roster. It also serves the roster HTTP API on port 8099. Entirely stateless: every pass rebuilds the fleet's state from the live provider API and health probes. Part II, 2.1
natctl-cli
The separate, one-shot operator command-line tool built from the same fleet-management logic as the daemon: status, nodes, drain, resize, rotate-root-pass, rotate-linode-token, rolling-restart, check-orphans, set-client-config, set-pool-scaling, set-vpc-sibling-subnets, list-ipsec-routes, add-ipsec-route, remove-ipsec-route, set-ipsec-routes. Takes --config as a top-level flag before the subcommand. Part X, 10.2
Nexthop group (resilient)
The Linux kernel object the client routing agent uses for its ECMP route: a named group of next hops with a fixed table of hash buckets. In resilient mode, removing one next hop reassigns only the buckets that pointed at it, so only roughly 1/N of flows move when one of N nodes leaves — every other connection stays where it was. Each node's nexthop ID is a stable hash of its VLAN address, and the group is updated in place rather than recreated. Part III, 3.2
nftables
The Linux kernel packet-filtering and NAT framework. On every node it provides both the masquerade rule that performs NAT and the local input rules that are the only security boundary on the VLAN interface. Each node's ruleset embeds its own addresses and is therefore generated per node. Part III, 3.1; Part VIII, 8.1
Object Storage
The provider's S3-compatible storage, and the one place every piece of durable, non-kernel, non-in-memory state in this system lives: fetched-at-boot artifacts, per-node firewall configurations, the leader-election lease, the reserved-IP ownership manifest, and the live fleet-wide operational settings. A bucket is required for every deployment. Part VI
Pass / reconcile pass
One full run of natctl's control loop, every 15 seconds by default: discover, health-check, compute buddy pairings, evaluate autoscaling, publish the roster — always in that order, always from scratch. Nothing about one pass depends on a previous pass beyond the live state it just re-discovered. Part II, 2.1
Pool
A named set of NAT nodes sharing one VLAN, one set of scaling bounds, and one roster — the unit of both scaling and isolation. A deployment has a default shared pool and may add dedicated pools per tenant. Each pool is one call of the same infrastructure module under a different name. Part I, 1.4; Part V, 5.5
Port exhaustion / port headroom
Port exhaustion is running out of free source ports on a public IP toward a given destination, at which point new connections fail. Port headroom is the fraction still free — an autoscaling signal (scale-out when it drops below 15%) and an alert condition (warning when it drops below 10%), so exhaustion is raised before it happens rather than diagnosed after. Part V, 5.2; Part VII, 7.4
Private IP
In the roster and CLI output, a node's VPC-side address (its eth1) — for example 10.60.32.20. Distinct from the node's VLAN address (vlan_ip) and its public address. Part II, 2.2
Public IP
An internet-routable address. On a NAT node, the real public address on eth0 — deliberately never a VPC 1:1 NAT address, because only a real public IP is eligible for BGP-based IP Sharing. Part 0, 0.2 (f); Part I, 1.3
Quorum
Agreement from enough of a pool's other members that a candidate's own view is trustworthy, sought before fencing: if any reachable member reports the previous leader healthy, or too few members can be reached to form a majority, the candidate backs off. Meaningful with three or more voters; two nodes alone cannot distinguish a network split from a dead peer, which is what the witness role exists to fix. Part II, 2.3 and 2.4
Reserved IP
A standalone public IPv4 allocation that outlives any single instance, opt-in per pool (reserved_ip_enabled). It fixes each node's primary public address so a replaced node comes back with the same address, keeping a downstream allow-list valid. An elastic node's reserved address is kept idle rather than released when the node is removed, and reused by the next node provisioned; a per-pool ownership manifest makes that reuse provably safe. Part IV, 4.6; Part VI, 6.4
Roster
The JSON snapshot of a pool natctl computes as the last step of every reconcile pass and serves from GET /fleet/<pool>: every node's identifier, three addresses, health verdict, and buddy relationships, plus the pool's live client settings and a roster_version that changes only when the content does. Lives entirely in memory and is rebuilt every pass. Part II, 2.2
Roster URL
The address a client, buddy-sync, or the monitoring stack is configured with to fetch a pool's roster — for example http://10.60.32.5:8099/fleet/shared. May be a comma-separated list; the client routing agent tries each in turn, which is what protects a freshly starting client from a single unreachable address. Part II, 2.2; Part III, 3.3
Route reflector
The provider-side BGP router a node's FRR daemon establishes its session with. It accepts a node's announcements for a shared address only once a matching IP-sharing registration exists, and delivers each shared address to whichever registered node is currently announcing it. Part IV, 4.4
Shared pool
The default pool every tenant uses unless given dedicated capacity. Mechanically identical to a dedicated pool. Part I, 1.4
Sibling subnet
Another subnet in the same VPC as the one a node or client is attached to. An instance's VPC interface only ever receives a kernel route to its own directly-connected subnet, so reaching a sibling requires an explicit route; this system discovers every subnet in the VPC and routes nodes and clients to all of them automatically, with a live override available. Part III, 3.3; Part X, 10.2
Softirq (CPU/softirq ratio)
The share of a CPU core's time spent on kernel network packet processing. The autoscaler watches the single busiest core anywhere in the pool — not an average — because network interrupt handling is pinned to specific cores, so a flood of small packets can saturate one core while everything else looks idle. Scale-out only; never drives scale-in. Part V, 5.2
Split-brain
Two natctl instances both believing themselves leader of the same pool at the same time. Made rare rather than impossible by election jitter, the direct liveness check, peer corroboration, fencing, a post-election settle delay, and a fresh leadership check before every individual mutating call. Detectable from the leader-election metrics (a per-pool leader count other than exactly one) and by reading the lease record directly. Part II, 2.4; Part X, 10.8
Subnet
A contiguous range of IP addresses, written in CIDR notation, within a larger network — a VPC is divided into subnets. Every NAT node and the control plane share one VPC subnet in this book's examples. Part 0, 0.2 (a)
Sustained-breach window
The requirement that an autoscaling signal stay past its watermark for a configured number of consecutive passes (two by default) before it is trusted enough to size an action on. One noisy reading starts a breach streak; it never triggers an action by itself. Part V, 5.2
Tag
A provider-side label on an instance. Every node in a pool carries lng, lng-fleet, and lng-pool-<pool-name>; nodes natctl provisioned also carry lng-elastic. Discovery, every pass, is one API call filtering on the pool tag — never a lookup against anything natctl stores itself. Part II, 2.1
Term
The monotonically increasing number identifying one leadership tenure in a pool's election. Every genuine re-election increments it; a step change in the term metric on more than one node at once is the visible signature of a real handover. Part II, 2.4; Part VII, 7.2
Three-interface node
The layout every NAT node uses: eth0 public (internet egress, the address a buddy fails over), eth1 VPC (connection-state sync only, never client traffic), eth2 VLAN (transparent NAT for the client fleet). Each interface has exactly one job. Part I, 1.3
Throughput ratio
A node's measured network throughput divided by the real, published bandwidth capacity of its specific instance plan, looked up from the provider rather than assumed. An autoscaling signal with a scale-out trigger at 85%. Part V, 5.2
Triangle
The buddy arrangement for an odd healthy node count of three or more: the trailing three nodes in sorted order form one ordinary mutual pair plus a one-directional backup from the pair's second member (the hub) to the third node, so no node is left without a backup. For connection-state sync specifically, the third node also syncs back to the hub, since sync needs both ends. Part IV, 4.2
VLAN
A private Layer 2 broadcast segment on Akamai Cloud, joined by label. Any attached instance can forward for any other, which is why the client fleet and each node's client-facing interface live here. Carries no address-assignment mechanism (all addresses are static) and is not filtered by Cloud Firewall. Part 0, 0.2 (c); Part III, 3.4
VPC (Virtual Private Cloud)
An isolated Layer 3 private network you define inside the provider, divided into subnets. This project brings its own VPC rather than creating one. Used for node-to-node connection-state sync and for reaching the control plane; not usable for the NAT path itself, because the fabric will not transit-route one instance's internet traffic through another. Part 0, 0.2 (b); Part I, 1.2
Witness node
An optional small, permanent instance (witness_enabled, default plan g6-nanode-1) that runs natctl in a vote-and-health-check-only mode for the every-node control-plane placement: it corroborates leader-election decisions and independently health-checks the pool's real nodes, but never forwards traffic, holds a public IP, joins buddy pairing, or claims leadership. It gives a two-node pool a real third voter; it adds nothing to a pool that already has three or more real nodes. Part II, 2.3
Zombie node
A node the provider reports as running while its own health check fails continuously. The pool's minimum is always measured in healthy nodes, so a zombie never counts toward it; an elastic zombie is drained and replaced after a configured threshold, while a floor zombie is compensated for with extra elastic capacity and left for an operator. Part IV, 4.7
