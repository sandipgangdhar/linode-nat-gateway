Part I

Architecture & Design

What a NAT gateway pool actually is on Akamai Cloud, the one networking fact that shapes every other design decision in this book, and why every node carries three interfaces instead of one.

1.1 What This Is

A NAT gateway pool is a set of independently active compute instances, each holding its own public egress IP, that a whole private subnet shares for outbound internet access — the same job AWS NAT Gateway or GCP Cloud NAT do, built instead from primitives you own and operate directly: Compute Instances, a VPC, a VLAN, Cloud Firewall, and BGP-based IP Sharing.

Every node in a pool forwards real customer traffic all the time — there is no active/passive pair and no idle standby capacity waiting for a failure. Private-subnet instances run a small routing agent that spreads their outbound traffic across every currently healthy node in the pool using ordinary Linux multipath routing (ECMP). A separate control-plane service continuously health-checks the fleet, hands out the current node list to every client, and grows or shrinks the pool automatically as load changes.

A purpose-built metrics exporter gives every node full visibility into its own connection-tracking table, port allocation, throughput, and packet drops — considerably more granular than either hyperscaler's own NAT monitoring.

Why a shared, static IP pool matters

Every VPC-member instance already gets a private interface and, if it wants one, its own individual 1:1 NAT to a public address — a clean building block, but not what most real deployments need. A partner or vendor firewall allow-list, or a compliance regime that requires all egress to be auditable and traceable to a small, known set of addresses, needs a whole private subnet funneled through a small, shared, static pool of egress IPs instead of one address per instance. That single requirement — a shared, controllable, observable egress boundary — is the reason this whole system exists.

1.2 The Constraint That Shapes Everything

A VPC fabric will not transit-route a packet through a peer VPC instance out to a non-VPC destination. A private instance sitting in the same VPC as a NAT node cannot simply add a route pointing at that node's VPC address and expect its traffic to reach the internet through it — the fabric drops it.

This single fact is why the private client fleet rides a completely separate Layer-2 fabric — a Linode VLAN — instead of VPC. A VLAN has no such restriction: any device attached to it can forward traffic through any other device on the same segment, exactly the behavior a NAT gateway needs from its clients. It is also why every node in the fleet carries not one but three purpose-built interfaces, each doing exactly one job, described next.

1.4 Active-Active, Pools, and Isolation

Every node in a pool is independently active — there is no master, no standby, no shared floating IP that all traffic funnels through. A pool is the unit of both scaling and isolation: the default shared pool serves every tenant that doesn't need dedicated capacity, and a tenant that does gets its own dedicated pool — its own VLAN, its own scaling bounds, fully isolated from every other tenant's traffic, but built from the exact same mechanism, not separate code.

Because every node is active all the time, one heavy tenant's traffic can burst across the entire pool rather than being capped at whatever a single pair could carry — the direct fix for the single biggest limitation of an active/passive design.

Part II

The Control Plane

The fleet's brain: how it discovers nodes, how the roster URL that every client and every dashboard depends on actually works, where it runs, and how it stays available.

2.1 The Fleet Controller

A single control-plane service is the fleet's brain. Every pass, it discovers every instance tagged as belonging to a pool, runs a real health check against each one, computes which nodes are paired as failover "buddies," provisions or removes elastic capacity within its configured bounds, and serves the roster that every routing agent, every sync daemon, and the metrics pipeline all depend on.

Nothing about the fleet controller is read back from a database. Every pass rebuilds the entire fleet's state from scratch, directly from live cloud-provider discovery and each node's own health probe. This single design choice is what makes the control plane genuinely disposable: if it restarts, or is temporarily unavailable, it has nothing to recover — the very next pass reconstructs an accurate picture of the fleet on its own.

What actually stops if the control plane goes down Already-provisioned nodes keep forwarding traffic untouched — they don't ask permission to do their job. What pauses is new decisions: provisioning or removing elastic nodes, reassigning failover buddies, replacing a persistently unhealthy node, and roster freshness beyond whatever every client already cached.

2.2 The Roster URL

Every routing decision in the system — which nodes a client should send traffic through, which peer a node should mirror connection state with, which target Prometheus should scrape — ultimately traces back to one HTTP endpoint: GET /fleet/<pool>, served by the fleet controller.

What it actually is

It is a plain HTTP endpoint, not a separate service or a piece of infrastructure that gets "provisioned." The moment the fleet controller starts and binds its listening port, that endpoint exists — creating the roster URL is simply a byproduct of deploying and starting the control plane itself, nothing more. Its response is a JSON document: the current node list for that pool, each node's address and current health state, and an integer version number that increments any time the underlying picture actually changes.

How it's kept fresh

Every reconcile pass — discover instances, health-check each one, recompute buddy pairings, evaluate whether the pool should scale — ends with the controller recomputing an in-memory roster snapshot and diffing it against the previous pass. Only a real change bumps the version number and wakes anyone waiting on it; a pass with nothing new to report is a no-op from the roster's point of view. There is no separate "update the roster" step to remember — publishing the roster is simply what every reconcile pass ends in.

Long-polling: near-instant reaction, near-zero idle traffic

A plain GET /fleet/<pool> always returns immediately with whatever the current snapshot is — nothing about that behavior changes. Add ?wait=true&since=<version>, and the connection is instead held open until either something actually changes or roughly 25 seconds pass, whichever comes first. A routing agent that uses this holds one open connection and reacts within a fraction of a second of any real fleet change, while producing essentially zero request volume during a quiet period — the same blocking-query pattern used by mature service-discovery systems elsewhere in the industry.

Health is authoritative here, not advisory

The roster response carries each node's already-computed healthy/unhealthy verdict directly, and every routing agent trusts that verdict by default rather than independently re-probing every node on its own. This is a deliberate, structural simplification, not a shortcut: every node and every client sit on the same physical VLAN Layer-2 segment, so reachability is essentially uniform across every client — there is no realistic scenario where a client's own probe would see something the control plane's own health check missed. An operator who wants the old belt-and-suspenders behavior anyway can turn on an additional local probe per client; when it's on, a node only counts as usable if both the control plane and the client's own check agree.

How the roster URL itself stays available

This depends entirely on where the control plane runs (see the next chapter). Run on a single dedicated host, there is exactly one instance answering roster requests — a control-plane single point of failure for freshness, not for traffic already flowing. Run on every node instead, every single node answers roster reads identically and correctly regardless of which one currently holds write authority over the fleet — at that point the roster URL is effectively as available as the fleet itself, since any surviving node can answer it.

What happens if a client can't reach it

A routing agent that fails to reach the roster URL never blackholes existing traffic. It keeps serving whatever roster it last successfully fetched, and if the set of healthy nodes it's holding onto is ever completely empty, it deliberately leaves the existing route in place rather than tearing egress down entirely. The failure mode of an unreachable control plane is "traffic keeps flowing on stale information," never "traffic stops."

Running the controller on every node is possible because it is entirely stateless — everything it computes is derived fresh from live discovery and health checks each pass, never read back from storage. The one real problem this placement introduces is the one every active-active control plane has to solve: more than one instance could try to mutate cloud state at the same moment. That problem, and how it's solved, is the next chapter.

2.4 Leader Election and Fencing

When the controller runs on every node, read-only work — discovery, health checks, buddy-pairing computation, serving the roster — runs on every instance all the time, regardless of leadership. Only the calls that actually change cloud state (provisioning a node, updating a BGP IP-sharing assignment) are gated to a single leader at a time.

The lease is a bulletin board, not the safety mechanism

Leadership is tracked via a lease record — a small object naming the current leader, its term, and an expiry — stored durably so every instance can read the same value. That record is deliberately treated as a best-effort hint, never as the actual source of correctness: a lease alone cannot guarantee only one writer is active at a time under every possible network condition.

The real safety mechanism: fencing

Before a candidate ever claims leadership, it powers off the previous leader through the cloud provider's own instance power-management API and polls until that shutdown is confirmed — either a genuinely offline status, or a not-found response meaning the instance no longer exists. If the power-off call fails, or confirmation never arrives in time, the candidate aborts the election outright rather than proceeding — an unconfirmed fence provides no real guarantee, so the system fails closed instead of optimistically continuing.

Layered on top: randomized timing before a candidate ever attempts an election (reducing the odds of two candidates colliding at once), a write-then-reverify step immediately after claiming leadership, and a fresh leadership check immediately before every individual mutating call — not just once per pass — so a node that loses leadership mid-cycle stops mutating within one call's window, not one whole cycle's.

Honest limit This is defense in depth, not mathematically perfect mutual exclusion the way a hardware-fenced active/passive pair would be. A network partition that isolates the current leader from the lease store, but not from the cloud API it's calling, is a scenario this design does not fully close.

The trade-off fencing accepts

A fenced node is powered off, not just demoted. Once the controller runs on the NAT nodes themselves rather than an isolated dedicated host, the node being fenced is also, at that moment, forwarding real NAT traffic — so a fencing event briefly interrupts that node's own data-plane role too. Buddy IP failover (Part IV) is what limits the blast radius of that specific interruption, exactly the same way it limits any other single node's failure.

2.5 Credentials

The control plane's cloud API token needs three scopes: read/write on instances, read/write on VPC, and read/write on networking — the last one specifically because buddy IP failover calls the provider's IP-sharing API, and because fencing uses the same instance power-management endpoints already covered by the instance scope.

Secrets are resolved from a narrowly-permissioned local file or an environment variable — never written into the shared, widely-distributed configuration file itself. In the single-host placement, this token lives on exactly one tightly firewalled instance. Once the controller runs on every node, the same token exists everywhere the controller runs — a real increase in how many places a sensitive credential lives, worth weighing deliberately against the single point of failure that placement removes.

Part III

The Data Plane

The pieces that actually touch a customer's packets: the NAT node itself, and the client-side agent that decides which node to send traffic through.

3.1 NAT Nodes

A NAT node is an ordinary compute instance running a kernel-level packet filter and connection tracker (nftables), configured to masquerade — rewrite the source address of — every packet arriving on its VLAN interface out through its public interface. This is the literal thing a customer pictures when they hear "NAT gateway"; every other component in this book exists purely to deploy, scale, secure, or observe a fleet of these.

Nothing about a node's own state is durable. Its connection-tracking table, its firewall counters, and its interface statistics are all in-kernel and rebuilt fresh on every boot from configuration fetched at start time. A broken node is treated as fully disposable — destroyed and replaced by the fleet, never repaired from a backup, because there is nothing on it worth restoring.

What happens if a node stops

With no additional protection layered on, whichever connections were actively flowing through that node at the moment it died are lost — a client detects the loss and reroutes within seconds, but the in-flight TCP state itself is gone. With buddy conntrack sync and BGP IP failover both enabled (Part IV), a meaningful share of that traffic can instead continue through the node's live buddy.

3.2 The Client Routing Agent

A small, dependency-free agent runs on every private-subnet instance that needs NAT egress. It long-polls the roster URL and maintains a resilient multipath ("ECMP") route pointed at every node the control plane currently reports healthy.

Consistent hashing, not round-robin

The nexthop group it installs uses the kernel's resilient hashing mode, which is what gives the system its most important routing property: when a node leaves the healthy set, only the roughly 1/N share of flows that were hashed to that specific node get reshuffled — every other flow, on every other node, is completely undisturbed. A naive route replacement would instead reshuffle every flow on every membership change, resetting far more connections than the actual failure warranted.

Setting the hash policy itself

Getting real distribution out of that mechanism also requires the kernel to hash on enough of each packet to tell separate connections apart. The agent sets this itself at every startup — hashing on source and destination port in addition to the address pair — so that many separate connections to the very same destination spread across the whole pool instead of all landing on one node, the same five-tuple approach used by every hardware router and both hyperscalers' own NAT implementations.

The one thing it manages, and the one thing it never touches

The agent manages exactly one thing: the default route. It installs one only on an instance that has no other path to the internet of its own; an instance that already has a public address or its own NAT path is left completely alone, since something else already owns that route. It never touches a VLAN or VPC interface's own connected route — those come from the kernel the instant the interface gets an address, independent of anything the agent does.

Fail-safe by design On a roster-fetch failure, the agent keeps its last-known-good membership rather than guessing. If the healthy set it holds ever becomes completely empty, it deliberately leaves the existing route in place rather than tearing egress down — a stale route beats no route at all.

3.3 Connecting a Client Instance

3.4 Static VLAN Addressing

A VLAN carries no address-assignment mechanism of its own — there is nothing like DHCP running on it. Every address, on every node and every client, is a static assignment applied directly to the interface.

For client instances specifically, the address is chosen by an operator (or the operator's own provisioning automation) and applied by a short configuration step run directly against the already-existing instance. Immediately before applying it, that step runs a live duplicate-address probe against the exact address on the exact VLAN segment — a last-moment collision check that catches an address already answering on the segment, whether it belongs to a node or another client, at the one moment it actually matters, rather than relying on a human to remember to check first.

A block of VLAN address space, sized by however many client addresses are expected to be hand-assigned over the deployment's lifetime, is reserved immediately above the range the fleet uses for its own nodes — this guarantees the fleet's own automatic address allocation can never wander into space meant for a manually assigned client, even though there is no per-client bookkeeping of which specific address inside that block is actually in use at any moment. The duplicate-address probe is what protects against colliding with another already-assigned client; the reserved block is what protects against colliding with a future node.

Part IV

High Availability

Four independent, layered mechanisms, each closing a specific gap the layer below it leaves open — including exactly how a two-node buddy pair differs from a three-node triangle.

None of these layers require the ones above them — ECMP alone is a complete, working system. Each additional layer is a deliberate trade of a little more operational complexity for a smaller and smaller blast radius on any single failure.

4.2 Buddy Pairing: the 2-Node Pair and the 3-Node Triangle

Every reconcile pass, the currently healthy node set is sorted deterministically and paired up two at a time. With an even number of nodes, this produces exactly what it sounds like: ordinary mutual pairs, each member backing up the other. An odd number of nodes is where the interesting behavior lives.

The ordinary pair

Two nodes, A and B. Each independently: (1) announces its own public IP as primary, (2) stands ready to take over the other's IP as secondary, and (3) mirrors connection-tracking state with the other. This relationship is fully symmetric and fully bidirectional — there is no primary/backup role assigned to either member; both are simultaneously each.

The 3-node triangle

With three or more nodes and an odd count, the trailing three nodes — call them A, B, and C in sorted order — form a triangle instead of leaving one node with no partner at all:

  • A and B form a completely ordinary mutual pair, exactly as above.
  • B — the "hub" — additionally takes on C as a one-directional backup: B is ready to announce C's public IP and mirrors C's connection state, but the reverse is not true. C does not back up B, and does not back up anyone.

Every node in the pool ends up with at least one live backup this way — nobody is left fully exposed just because the pool's node count happens to be odd.

Why the hub relationship is directional for IP failover, but not for state sync

These are two different underlying constraints, and the triangle handles them differently on purpose:

  • IP failover is governed by the cloud provider's own IP-sharing rule: two different nodes may never both claim to be the secondary announcer for the same primary address — but nothing stops a single node from being the secondary for two different primaries at once. The triangle exploits exactly that: B can legitimately back up both A's and C's addresses simultaneously, while C backs up no one. This relationship stays directional by design.
  • Connection-state sync needs a real, two-way relationship on both ends — each side runs its own sync process pointed at the other, and either side may need the other's mirrored state at any moment. So for state sync specifically, the same underlying triangle shape is symmetrized: C also gets a real, live sync relationship pointed back at B. The hub node ends up running two completely independent, simultaneous sync processes — one per peer, each with its own configuration, lock, and control socket — while the odd node out ends up with exactly one real peer instead of none at all.

What happens as the pool scales

Pairings are recomputed from the current healthy node set on every single pass — deliberately simple rather than sticky or consistent-hashed, since a buddy resync only costs a few seconds of state-sync freshness for the affected nodes, not a routing disruption for every in-flight flow the way a client-facing membership change would.

4.3 Connection-State Sync

A daemon runs on every node, watching the roster for buddy reassignment and reconciling both the BGP announcer's secondary-route configuration and the connection-tracking sync process's peer configuration whenever a pairing changes.

While active, it continuously mirrors the node's live kernel connection-tracking table to its current peer or peers — usually one, two for a triangle's hub node running two independent sync processes at once.

What happens if it stops

A node with no active sync peer is still completely healthy and still fully participating in ECMP rotation — this is a session-continuity mitigation, not a health signal, and should never be treated as equivalent to a node being down. The only practical consequence of losing sync is that a future failure of that specific node will reset in-flight connections outright instead of possibly continuing through a buddy that had a mirrored copy of the state.

How to restart it

Simply restart the service. It carries no state of its own worth preserving — on restart, it re-derives its current peer assignment fresh from the roster on its very next pass and re-establishes sync from there. There is nothing to migrate and no manual reconciliation step.

What it stores

Only its own regenerable configuration — the BGP announcer's running configuration is rewritten on every pairing change, and a small status file exists purely for observability and is never read back by anything. The actual mirrored connection-tracking table lives only in kernel memory on both ends and is never written to disk anywhere.

4.4 BGP-Based IP Failover

A BGP routing daemon on every node, paired with the cloud provider's own IP-Sharing capability, is what actually lets a buddy take over a dead node's public IP — not just its connection state.

The mechanism

From the moment it boots, every paired node is simultaneously doing two things: announcing its own public IP as the primary route, and — once buddy-paired — announcing its buddy's/buddies' public IP(s) as a secondary backup route. This is fully bidirectional and active from boot, not something that only activates once a failure is detected.

A short activation delay is deliberately built into forming a brand-new pairing before the cloud provider's IP-sharing API is actually called — this guarantees the announcing side is genuinely up and its BGP session already established before the share takes effect, which is the mechanism that actually protects against a real outage during pairing formation rather than a bare hope that timing works out.

What happens when a node dies

Its buddy's already-standing secondary announcement is what lets traffic addressed to the dead node's public IP keep reaching a live host — typically within a single BGP convergence cycle, with proven zero packet loss in both directions during a live failover exercise. Any TCP connection that was actively open through the dead node at the moment it died still resets; that is connection-state loss, a separate concern that only connection-state sync (previous chapter) addresses.

How to restart it

Stopping and starting the BGP daemon on a node is enough — its own self-announcement resumes automatically at boot with no manual step, and its buddy assignment is entirely independent of the daemon's own lifecycle, since that assignment is recomputed by the control plane, not stored locally.

Operational caution Changing a node's BGP router identity while sessions are already established forces a full session reset on every peer. The router identity is set once, at boot, and is never touched again during normal operation — there is no supported reason to change it live.

4.5 Anti-Affinity Placement

Buddy sync and BGP failover both assume the two members of a pair can actually fail independently. If both happen to land on the same underlying physical host, that assumption breaks — a single physical-host failure takes out an entire buddy relationship at once, with nothing left to fail over to.

Placement groups spread a pool's nodes across separate physical hosts to close exactly this gap. This is safe to turn on for an already-running pool without replacing a single node — existing nodes are simply updated in place to join a group. A pool larger than one group's node cap is split into multiple contiguous groups; this leaves one honest, structural residual gap: a buddy pair that happens to straddle the boundary between two groups gets no anti-affinity protection from each other, since group boundaries are drawn by creation order, not by buddy-pairing awareness. This is a deliberate trade-off that minimizes rather than eliminates that specific exposure, not an oversight.

4.6 Reserved (Sticky) Public IPs

By default, a replaced node comes back with a brand-new, ephemeral public address. For a deployment whose downstream partners whitelist specific IPs, that churn is unacceptable — reserved IPs fix a node's primary public address to one that survives instance replacement.

When a node backed by elastic (automatically provisioned) capacity is removed, its reserved address is deliberately not released — it stays reserved but idle, and the next node the pool provisions reuses it instead of minting a fresh one. Over a pool's lifetime this settles into a small, stable address set bounded by the pool's maximum elastic size, not by however many replacements have happened — exactly the stability a downstream whitelist needs. A durable per-pool ownership record is what makes reuse provably safe rather than a guess based on "currently unattached," since an unattached address elsewhere on the same account could easily belong to something unrelated.

4.7 Handling a Persistently Unhealthy Node

The count that actually matters against a pool's minimum node requirement is the number of currently healthy nodes, never the raw node count — a node that exists but is failing its own health check does not count toward satisfying the floor.

An elastic node that stays unhealthy past a configured threshold is drained and replaced automatically, with no human intervention required. A Terraform-managed floor node is treated completely differently and deliberately never auto-replaced under any circumstance — instead, the system compensates by provisioning additional elastic capacity to make up for the lost floor capacity, while leaving the actual broken floor node for an operator to investigate and fix by hand. This is a hard safety boundary, not an inconsistency: an automated system should never delete infrastructure a human explicitly declared should always exist.

Part V

Scaling

How the pool grows and shrinks automatically, the exact formula behind every scaling decision, and how to right-size a pool from real, calculable numbers instead of guesswork.

5.1 Two Tiers of Capacity

TierManaged byBehavior
FloorInfrastructure-as-code, an operatorFixed baseline capacity. Never auto-scaled, never auto-replaced — always exactly what was declared.
ElasticThe fleet controller, automaticallyGrows and shrinks within a configured minimum and maximum, in direct response to real load.

Start the floor minimal — a single node is a perfectly reasonable starting point — and let real, observed demand justify raising it. Elastic capacity exists precisely so the floor doesn't need to be sized for a burst that may never come.

5.2 The Autoscaling Algorithm

Every reconcile pass, three independent capacity signals are checked. Any single one crossing its line is enough to trigger a scaling evaluation — a single exhausted resource degrades real traffic regardless of what the other two look like.

SignalScale-out triggerMeaning
Connection-tracking utilization≥ 70%The node's fixed-size connection table is nearly full — past 100%, new connections start failing outright.
Port headroom≤ 15%Fewer than 15% of usable source ports per destination remain free. Note the direction — low is the bad reading here, the mirror image of the other two.
Throughput ratio≥ 85%The node is using 85% of its real, measured network bandwidth ceiling for its specific instance plan.

The sizing formula

Required Capacity  =  Current Capacity  ×  (Current Metric ÷ Target Metric)

The whether-to-trigger decision uses the single worst node in the pool. The how-big-an-action decision, once triggered, uses the pool-wide aggregate instead — sizing off one hot node alone would over-provision for what might really be an uneven distribution problem on a single node rather than a genuine pool-wide shortfall.

Two guards against an overcorrection

  • Sustained-breach window. A metric has to stay past its threshold across two consecutive passes before it's trusted enough to size an action on — one noisy reading only starts a counter, it never triggers an action by itself.
  • Maximum step size. Even once trusted, a single scale-out action is capped at doubling current capacity, and a single scale-in action is capped at removing half of current elastic capacity — deliberately more conservative in the remove-capacity direction, since draining a node that turns out to still be needed is a worse mistake than a slightly slow scale-out. A formula result larger than the cap is fulfilled gradually, over more than one cycle, instead of taken in a single uncontrolled jump.

A cooldown period after every scaling action, independent of both guards above, blocks re-evaluation entirely for a while — giving freshly added capacity real time to start absorbing load before the next decision is made.

Sustained-breach passes2Consecutive breached passes required before a reading is trusted for sizing
Max scale-out step100% of current sizeNever more than doubling in a single action
Max scale-in step50% of elastic capacityNever removes more than half the current elastic node count at once
Cooldown300 secondsMinimum time between any two scaling actions

A scale-out, start to finish

A pool at two nodes sees connection-tracking utilization spike to 90% on its hottest node. That single reading isn't enough on its own — the sustained-breach counter only reaches one. The load persists on the next pass; the counter is now satisfied, and the pool-wide aggregate works out to 85%. Against a 50% target, the formula computes 2 × (0.85 ÷ 0.50) = 3.4, rounded up to 4 nodes — a delta of two, which the doubling cap comfortably allows in one action. Two new nodes are provisioned in that single decision rather than two separate five-minute cycles of one node each. Cooldown then blocks any further evaluation while the new capacity boots, passes its own health checks, and starts absorbing real traffic.

Real capacity, not an assumption

The throughput signal is measured against the real, published network capacity of whichever instance plan the pool actually runs — looked up directly from the cloud provider rather than hardcoded, and cached since a plan's specification is effectively static. If that lookup itself ever fails, the fallback assumes a conservative, lower capacity figure rather than a generous one — a failure here makes the system slightly more eager to scale out, never blind to a real shortage.

5.3 Right-Sizing: Instance Types and Node Count

When in doubt, prefer more nodes over bigger ones. The active-active model makes horizontal growth genuinely cheap — there's no coordination overhead the way there would be with a fixed pair, where adding capacity meant standing up a whole new pair.

Sizing the connection-tracking table

nf_conntrack_max  ≥  1.3 × expected peak concurrent connections per node

The 30% headroom above the expected peak is what keeps a normal traffic spike from ever reaching the hard connection-tracking ceiling before the autoscaler has a chance to react.

Sizing for port exhaustion

Every public IP supports roughly 55,000 simultaneous connections to any single destination — the same structural ceiling AWS documents for its own NAT Gateway. A node can hold more than one public egress IP specifically to multiply this ceiling; only a node's primary address participates in IP failover, so additional addresses are a straightforward per-node allocation with no shared-failover behavior of their own.

Estimating the node count you actually need

Calculate two independent numbers and take the larger one as your floor:

  • Throughput-bound: peak aggregate expected traffic, divided by one node's real, published network-out capacity for the instance plan you intend to run.
  • Connection-bound: peak aggregate expected concurrent connections, divided by (per-node conntrack ceiling × 0.70) — the trigger threshold, not the raw maximum, since you want headroom before the alarm fires, not right up against it.

Add at least one extra node beyond that calculated minimum so that a single node's failure doesn't itself immediately push the pool over its own scale-out trigger.

Choosing an instance plan

Dedicated-CPU compute plans on Akamai Cloud scale up to roughly 40 Gbps inbound and 12 Gbps outbound per instance at the top end — a mid-tier dedicated-CPU plan is a reasonable, realistic default for a genuine production NAT node rather than the smallest available size, since a NAT gateway is fundamentally a networking-bound workload, not a compute-bound one. The system itself never guesses at a plan's real capacity — it queries the provider's own instance-type data directly, so whatever plan is actually chosen is what the autoscaling formula sizes against, not an assumption baked in ahead of time.

5.4 Vertical Scaling

Changing a node's instance plan — up or down — is always a deliberate, operator-initiated action naming one or more specific nodes by identifier; nothing in the system ever decides on its own that a node's size, as opposed to the pool's node count, should change.

What happens, step by step

  1. A disk-fit check runs first, before ever calling the resize API — comparing the target plan's disk allowance against the node's actual allocated disk. If it won't fit, nothing risky is attempted: the operator gets the exact manual remediation steps instead of a surprise mid-resize failure.
  2. The node is drained — excluded from the roster immediately, with existing connections given time to empty out naturally.
  3. A warm resize is attempted first (the instance stays up during migration, then reboots once complete) — automatically falling back to a cold resize if the provider rejects the warm attempt.
  4. The controller polls until the instance is confirmed running again, then un-drains it — it rejoins the roster once its own health checks pass, exactly like any node recovering from a transient failure.

Multiple named nodes are always processed one at a time, never in parallel, and the whole operation stops at the first node that fails rather than continuing to remove capacity from an already-short pool. A resized floor node needs a matching, explicit override recorded in the infrastructure-as-code configuration so a future apply doesn't silently revert the resize; an elastic node needs no such step, since it was never declared there to begin with.

5.5 Multi-Tenant Pools

A pool is the unit of both scaling and isolation. A tenant that needs guaranteed, isolated capacity — rather than sharing the default pool with everyone else — gets its own dedicated pool: its own VLAN, its own independent minimum/maximum bounds, completely isolated traffic, built from exactly the same mechanism as the shared pool, just under a different name.

6.2 Fetched-at-Boot Artifacts

A cloud provider's own boot-time configuration payload — the data handed to a fresh instance the moment it boots — has a hard, fixed size ceiling. This project's own agent source code, on its own, already exceeds a meaningful fraction of that ceiling before a single optional feature is even turned on.

The fix: every file that's identical across every node — the metrics exporter, the connection-sync daemon, and the control-plane package itself — is uploaded to object storage exactly once per deployment, as a plain, public-read object, and re-uploaded automatically only when its actual content changes. Every node then fetches its copy over a plain HTTP request at boot, instead of having that content embedded directly in its boot payload.

Public, not signed — a deliberate choice

None of these fetched files contain secrets. Actual secrets are always injected separately, as small, per-node files with narrow permissions — this design never changes that. A plain public-read object plus a plain HTTP fetch avoids the need for a cloud-signing client to be preinstalled on a completely bare image just to pull this project's own non-secret source code.

What's compressed instead of uploaded separately

Everything that must stay embedded directly in a node's own boot payload — because it's genuinely unique to that one node, like its firewall ruleset, or because it carries a secret and therefore can never be public — is compressed before being embedded, which by itself comfortably closes most of the remaining size gap for a typical configuration.

6.3 The Leader-Election Lease

Only relevant when the control plane runs on every node: a small record naming the current leader, its term, and an expiry, readable by every controller instance. As covered in Part II, this record is a best-effort coordination hint, never the actual safety mechanism — that role belongs entirely to fencing. Losing this record costs, at most, one election cycle; it never represents a safety violation on its own.

6.4 Reserved-IP and Live Configuration Manifests

A pool's reserved-IP ownership manifest is a durable, per-pool list of every address that pool has ever reserved — the only thing that makes address reuse across node replacements provably safe rather than a guess, since an address being merely "unattached" says nothing about whether it actually belongs to this pool or to something completely unrelated sitting idle on the same account.

A separate, small live-configuration object lets an operator change certain fleet-wide operational behavior — for example, whether client instances should also independently double-check node health rather than trusting the control plane's computed view alone — instantly and durably, with every connected client and every controller instance picking up the change within one round trip and with zero restarts required anywhere in the fleet.

7.5 What the Health Check Actually Verifies

Every node's own health endpoint runs a genuine end-to-end check every single time it's called, not a cached result: IP forwarding is confirmed enabled, the NAT ruleset is confirmed loaded — and, the check that actually matters most, a real outbound request is sent out through the node's own public interface and its success is confirmed.

That last check is what makes both client routing decisions and the fleet's roster genuinely trustworthy. A node can be perfectly reachable on the network while its NAT path is quietly broken underneath — a plain reachability check would completely miss that; only an actual end-to-end request catches it. The per-check breakdown metric exposes exactly which individual check failed, so a diagnosis never requires logging into the node itself.

Part VIII

Security

The firewall boundary on every interface, and exactly what credential scope every moving part actually needs.

8.1 The Firewall Model

Every node's public and VPC interfaces sit behind a default-deny cloud firewall — nothing is reachable that isn't explicitly listed. Nodes never accept an inbound connection initiated from the internet at all; NAT and forwarding are unidirectional by construction, not merely by firewall policy.

The VLAN interface is handled completely differently, because the cloud provider's own firewall layer never inspects VLAN traffic at all — it simply isn't in that path. The node's own local packet-filter ruleset is the entire security boundary for VLAN traffic, and it is written accordingly: it keeps the metrics port open there (client instances need to reach it) while explicitly excluding administrative access from that interface.

The control plane's own host — wherever it runs — exposes its administrative and dashboard ports only to an explicitly configured administrator address range, never to the open internet by default, and exposes its roster API only to the private network the fleet actually lives on.

8.2 Credential Scope

The control plane's own cloud API token needs exactly three scopes — read/write on instances, read/write on VPC, and read/write on networking — and nothing broader. The networking scope specifically is what allows both BGP IP-sharing calls and the fencing mechanism's instance power-management calls; no additional scope beyond it is required for fencing.

The client routing agent needs one elevated local capability on the instance it runs on — the ability to manage the kernel's own routing table — and nothing else; it never needs any cloud API credential of its own at all.

Part IX

Deployment

What's required before the first deploy, the deployment sequence itself, and how a real customer instance gets connected once the fleet exists.

9.1 Prerequisites

  • A cloud account with API access, and a token scoped exactly as described in the Security part above.
  • An existing VPC and at least one subnet, sized with headroom for every pool's own address range — this project intentionally never creates the VPC itself, only reads it back.
  • An object storage bucket, created ahead of time — required for every deployment, since fetched-at-boot artifacts (Part VI) depend on it unconditionally, not only in the every-node control-plane placement.
  • An SSH key pair for administrative access, and an explicit administrator address range for the control-plane host's dashboard and SSH access.

9.2 Deployment Sequence

  1. Provision the fleet: the floor nodes for each pool, the control-plane host (or, if the every-node placement is chosen, nothing dedicated at all), and the two firewalls covering the node and control-plane traffic.
  2. Confirm the fleet is healthy: every floor node passes its own health check and appears in the roster with a healthy status.
  3. Install the routing agent on every private-subnet instance that needs egress, pointed at the pool's roster URL.
  4. Open the monitoring dashboard and confirm every node is reporting metrics and showing healthy.

9.3 Onboarding a Client Instance

Once a private instance exists and has its VLAN interface attached at the account level, a single configuration step against that instance finishes the job: it applies the operator-supplied static VLAN address (after the duplicate-address safety probe described in Part III), installs and starts the routing agent only if the instance genuinely needs one, and points it at the correct pool's roster URL. The instance is now a fully participating client, spreading its egress traffic across every currently healthy node in that pool.

Part X

Day-2 Operations

The checklist worth reviewing before calling a deployment production-ready, the procedures for the operational tasks that come up routinely, and where to look first when something looks wrong.

10.1 Pre-Production Checklist

  • Metrics are being scraped from every node, the dashboard is loaded, and alert rules are active.
  • The control plane is running with a valid, correctly scoped API token.
  • Every private-subnet instance that needs egress has a healthy routing agent installed.
  • Minimum/maximum node bounds are reviewed per pool — these are the real safety limits on automatic scaling, not defaults to leave unexamined.
  • The connection-tracking table size is sized against expected peak concurrent connections per node.
  • Firewall rules are reviewed: default-deny confirmed, only documented ports open — remembering the cloud firewall never covers VLAN traffic, only the node's own local ruleset does.
  • If buddy sync is wanted, the roster URL configuration matches consistently everywhere it's referenced; if it isn't wanted, it's left empty everywhere so the sync daemon is never installed at all.
  • The unhealthy-node replacement threshold is reviewed per pool — the default is a reasonable starting point, not something to leave unexamined for a workload sensitive to brief capacity dips.
  • If BGP IP failover is enabled, the correct BGP data-center identifier is confirmed for the region, and automatic IP-share configuration is left on unless there's a specific reason to run the first pairing by hand.
  • Every manually assigned client address falls inside its pool's reserved window and was applied through the configuration script's duplicate-address safety check, never picked and applied blind.
  • Anti-affinity placement is considered for any pool where a correlated physical-host failure taking out a whole buddy pair is a real, meaningful concern.
  • If reserved IPs are in use and addresses already exist from a prior deployment, they're handed to the pool explicitly rather than letting it mint entirely new ones.

10.2 Common Procedures

Raise the floor

Increase the declared floor node count and re-apply the infrastructure configuration. Every connected client picks up the new node automatically on its next roster refresh — no other action is needed anywhere.

Adjust elastic bounds

Change the minimum/maximum node bounds or any autoscaling setting for the pool and restart the control plane — the new bounds take effect on its very next reconcile pass.

Manually drain and remove an elastic node

A specific elastic node can be told to drain directly — it's immediately excluded from the roster and deleted once its live connection count empties out, or once a configured drain timeout elapses, whichever comes first. A floor node can never be drained this way by design; reduce the floor's declared count instead.

Resize a node's instance plan

Name the node (or nodes) and the target plan — see the full mechanics in Part V. Nodes are always processed one at a time, and the operation stops at the very first failure rather than continuing against a pool that's already short a node.

Add an extra egress IP to a running node

Extra IPs multiply a node's available port ceiling. This is currently available for floor nodes only — elastic nodes are provisioned single-IP.

Enable BGP IP failover for a pool

This is the one procedure in day-2 operations that carries real reachability risk if rushed. Confirm buddy sync is already active for the pool, set the correct region's BGP identifier, and enable the feature. Automatic IP-share configuration then handles registering the actual failover relationship as pairings form — verify by watching the BGP daemon's own session state move from connecting to established shortly after a pairing forms, and by testing an actual failover from an external host in both directions before trusting it in production.

Enable the every-node control-plane placement

Confirm the API token's scope, enable the setting, and re-apply. Confirm exactly one node's logs show it actively claiming leadership and every other node logging that it's a follower — every node should still answer read-only roster and status requests regardless of which one holds leadership.

10.3 Troubleshooting Playbook

A port-exhaustion alert fires

Check the dashboard's port-headroom panel to identify the specific saturated node and IP. If the whole pool is under pressure, the autoscaler should be scaling out on its own — check whether it's blocked by cooldown or an already-reached maximum. If only one node is hot while others have headroom, that's expected at low connection counts and self-corrects as volume grows; if it persists, consider giving that node an extra egress IP.

A pool-below-floor alert fires

Check how many nodes are actually healthy, not just present — the floor check is against healthy count specifically. A missing or unhealthy elastic node should self-heal automatically past its configured threshold; if it isn't, check the control plane's own logs and its API token's scope. A floor node that's unhealthy is never auto-replaced by design — the pool instead runs with extra elastic capacity compensating for it, which is expected behavior, not an error condition; the floor node itself still needs a human to fix it.

A node has no sync buddy

Confirm the pool actually has buddy sync enabled and its roster URL configuration is consistent. On the node itself, confirm the sync daemon is actively running and logging roster polls. Remember this is a mitigation, not a health signal — an unpaired node is still fully healthy and fully in rotation; it should never be treated as equivalent to a down node.

A client isn't picking up a fleet change

Confirm the client can actually reach the roster URL at all. Check the routing agent's own logs for roster refreshes and healthy-set changes. Remember that membership and health can refresh on different cadences depending on configuration — a node present in the roster but failing its own health check is excluded from routing regardless of how fresh the membership list itself is.

Rolling a security patch across the fleet

Patch elastic nodes first via drain-and-replace — the pool naturally provisions fresh replacement capacity. For floor nodes, patch one at a time: drain it manually, patch and reboot it, confirm its health check passes again, then move to the next node — there is no automatic drain for floor nodes, since the system never touches them on its own.

10.4 Where to Look First

In rough order of likelihood: a private-subnet instance's routing agent isn't running or can't reach the roster URL; the control plane's API token has expired or lost a scope; or the minimum/maximum bounds are misconfigured for actual current load. The architecture and this book describe exactly how the system is supposed to behave — when real behavior diverges from that, that gap is always the right starting point for debugging, not a sign the design itself is wrong.

A.2 Where the Hyperscalers Still Win

Being candid: a fully managed NAT service is genuinely zero-ops. No operating-system patching, no capacity-planning judgment calls, no failover drills to run, no on-call for a kernel panic on a NAT node. Operating this system instead means operating real compute instances — the trade being made is control, cost, and observability depth in exchange for taking on real operational ownership. That ownership is made as low-friction as realistically possible, but it is never nothing.

A.3 The Trade-Off Inside the Design Itself

Separate from the comparison against the hyperscalers, there's a trade-off internal to the active-active model itself, worth stating plainly rather than glossing over: it trades away the simplicity of a fixed master/standby pair — where one continuously mirrored relationship gives genuinely zero session loss on failover — in exchange for horizontal scaling and full utilization, with no idle standby capacity sitting around unused.

Buddy connection-state sync combined with bidirectional BGP IP failover narrows that gap substantially — a buddy takes over both a dead node's connection state and its public identity, in both directions of every pairing. It remains, honestly, a mitigation rather than an absolute guarantee: propagation carries real if small lag, and a genuinely correlated failure of both members of a pair at once has nothing left to fail over to unless anti-affinity placement is also in use. A workload that truly cannot tolerate any connection reset under any circumstance at all has a real reason to weigh a simpler, pair-based model's stronger session-loss guarantee against this design's better scaling and utilization — they are optimized for different priorities, and that trade-off deserves to be made deliberately rather than assumed away.
